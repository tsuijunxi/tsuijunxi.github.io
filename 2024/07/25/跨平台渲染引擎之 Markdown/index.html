背景

English Abstract: This article describes how to build a cross-platform native markdown rendering library for iOS and Android. Instead of relying on WebView, the renderer uses a C++ core for parsing, layout, Atom/Box tree construction, event dispatching, text layout, image loading, and platform rendering adapters. It is aimed at chat-style AI responses and other dynamic markdown content on mobile.

在ChatGPT火遍天际之际，许多应用程序都试图以聊天机器人的形式接入访问它。由于ChatGPT的回复文本是markdown格式，所以移动端上需要支持markdown语法，调研良久发现：

  1. 很多方案都是基于WebView的方式来实现的，这对于移动平台会存在性能不佳的问题；
  2. iOS方向的CocoaMarkdown 是为数不多的Native渲染库，但是其功能不够全面，且不易扩展；
  3. Android方向有一款架构比较优秀的库 Markwon，遗憾的是只支持单端。

最终我决定构建一款适合于移动双端接入的跨平台渲染引擎，并命名为Markdown。本文将介绍如何实现一个markdown 跨平台渲染库，如果你对跨平台技术感兴趣的话，那么一起来享受这趟跨平台之旅吧。

为了区分，小写markdown指语法，大写Markdown指SDK。

实现原理

跨平台基石

首先来讨论下跨平台的基石问题：Markdown是一个重渲染的SDK，从根本上无法避免和UI打交道，而C/C++本身并不擅长此类工作，它更擅长的是一些逻辑性的非UI工作。那么为什么可以用C/C++来实现呢？这套跨平台方案之所以可行，就在于 C/C++ 层抽象了一系列接口，使得排版和渲染可以摆脱对具体平台的依赖，在 C/C++ 层就可以拿着虚拟的画板和画笔，统一完成排版和渲染工作，而双端只需要做好这些接口的适配，在真正排版和绘制前进行绑定即可。

它带来的优势：

  1. 双端可以保证几乎同样的渲染效果；
  2. 双端只需要开发和维护一份逻辑代码；
  3. C/C++语言本身四通八达，非常容易扩展到其它平台；

当然它也有自己的劣势：

  1. 要对C/C++比较熟悉，但众所周知C/C++是一门不太友好的语言；
  2. 很多东西得摆脱对具体平台的依赖，意味着有些东西不能开箱即用。

架构图

如图所示，Markdown引擎架构主要由平台无关层和平台相关层构成：

  1. 蓝色区域为平台无关层，使用C/C++实现，是Markdown的核心模块，主要实现markdown 文本的解析、排版和渲染；

    1. iOS平台使用objc进行实现；

    2. Android平台使用Kotlin进行实现；

未来如果有其它平台的需求，例如Flutter平台，可以进行规划适配。Flutter的适配不是指通过传统的Channel方式和iOS/Android平台通信，而是通过FFI让Dart和C++直接通信。

如何构建节点树？

语法树的构建遵守如下进栈和出栈的规则：

  1. 当发生enterBlock和enterSpan回调时，代表解析到节点开始，进行入栈操作：
    1. 根节点mRootNode为首个解析到的节点，只更新1次；
    2. mCurrentNode为当前的栈顶节点，每当解析到新的节点A，mCurrentNode会将该A添加为孩子，并将A赋值给mCurrentNode，代表栈顶节点已发生变化。

以无序列表为例：

  1. 当发生leaveBlock和leaveSpan回调时，代表节点解析结束，进行出栈操作。出栈之后需要更新mCurrentNode节点，这里为了保持入栈和出栈的一致性，会做一些平衡检查。
  1. 当发生foundText回调时，代表解析到叶子节点，当前栈顶节点直接将其添加为孩子节点即可。

这个过程会一直递归下去，直到解析完成，最后可以通过 mRootNode 得到整个节点树。

排版

前面的步骤最终形成了一颗Box的多叉树。解析完的Box都在C++层，并且C++层有天然虚拟的画板和画笔，只需要在画板上开绘就行。所以在绘制之前，需要进行排版，明确各元素的最终位置。

流式 Box 拆分

通常情况下，markdown元素的布局都是流式的，然而画板的宽度是有限的，所以要解决的第一个问题，就是如何根据给定的画布宽度，对Box树进行换行拆分。

如图，假设这就是Box树：

  1. 白色节点是root，

  2. 淡蓝色节点为第1个孩子节点，

  3. 橘红色节点为第2个孩子节点，同时它有3个孩子节点，分别为黄色、天蓝色和紫色；

  4. 蓝色节点为第3个孩子节点。

假设现在要排版第一行，根据屏幕宽度，发现橘红色节点需要进行拆分，由于橘红色节点有子节点，所以需要递归，通过观察可以黄色节点需要归属到当前行，而紫色节点肯定无法归属到当前行，比较麻烦的是天蓝色节点，它是一个节点，又没有子节点，所以需要判断它是否可拆分

块元素内部提前排版

markdown中有一些块元素，例如表格、列表或者引用，对外会占据整个宽度，对外表现为一个整体，拆分之后仍然独占一行。然而这些块元素的内部子元素也有换行的情况，因此这些块元素需要进提前将内部子元素排版好。

  1. 引用

如上图所示，以"Quote"为例，最左边有和文本等高的灰色直线，排版的时候要把直线以及直线之后的空白处预留出来，因此要把上下文中的宽度减去预留位置的宽度。

  1. 表格

如图，关于表格的排版，要更加复杂一些：

  1. 首先要确定整个表格各个列的宽度，从而决定整个表格的宽度。有的情况下，表格的整个宽度都不及给定的宽度，而有的情况下表格的宽度则超出了给定的宽度。那么如何来决定表格各个列的宽度呢？

    1. 循环计算各列的最大宽度

    2. 将各列的宽度相加

      1. 如果和未超过给定宽度，则不作任何处理；

      2. 否则计算各列的比例百分比，用百分比乘以给定宽度，作为最后每个列的宽度.

    3. 每个表格单元中的内容都需要根据当前列的宽度，进行Box拆分

  2. 另外表格的每一列都有自己的对齐规则：左对齐、居中对齐、右对齐，这些规则需要根据 markdown 语法进行解析。

行内对齐

关于对齐情况，要么左对齐，要么右对齐，或者居中。此时应对策略是：

  1. 左对齐，根据给定宽度，计算右侧空白区域，然后使用StrutBox进行填充；

  2. 右对齐，根据给定宽度，计算左侧空白区域，然后使用StrutBox进行填充；

  3. 居中对齐，根据给定宽度，计算左右两侧空白区域，然后使用StrutBox进行填充；

  4. 两端对齐，根据给定宽度，计算每两个字符之间的空隙，然后使用StrutBox进行填充；

排版规则（细节中的魔鬼）

类似于阅读引擎，Markdown 引擎中的文本排版有很多相似的默认规则。但不同于普通的流式文本，Markdown 的文本排版始终行驶在一个 Box 的多叉树上，遵守这些排版规则需要付出比较相对高昂的代价。

  1. 中文都是换行点；

  2. 避首避尾标点都不是换行点；

  3. 连续破折号不是换行点；

  4. 空格都是换行点；

  5. 英文单词不是换行点；

  6. 部分英文标点不是换行点；

符号分离禁则

以下标点符号，在行间应为一体，视作一个字符存在，不能为了适配分行而拆成两行。

  1. 破折号：––

  2. 省略号：……和······

  3. 竖直双引号：“xxx”，xxx为一个英语单词。

  4. 缩写：例如 I’m、You’re 等

这些问题的解决方案如下：在 MDTextNode 中对文本拆分的时候进行的，提前进行绑定，在排版的时候被当成一个整体来对待。

行尾行首禁则

为了保持阅读顺畅、体验一致，多数标点符号的位置有限制，通常一个标点符号依其性质，禁止出现在行首或行尾：

  1. 点号（顿号、逗号、句号、冒号、分号、叹号、问号）、结束引号、结束括号、结束双书名号（书名号乙式）、连接号、间隔号、分隔号不能出现在一行的开头。

  2. 开始引号、开始括号、开始单双书名号等符号，不能出现在一行的结尾。

“推出式”避头尾 vs “优先推入式”避头尾

  1. “推出式”避头尾是大部分排版系统的做法，以避头标点为例，若此标点被排到了行首，“推出式”的做法是从上一行拉一个字放在本行。然而这么做的话，上一行的字间距被拉大，打断了阅读节奏，如左图所示。

  2. “优先推入式避头尾”，通过将本行内的标点宽度进行挤压后，腾出了空间给本来排不到的逗号，确保了字间距的恒定。然后只有在本行内标点无法压缩出足够空间时，才会选择“推出式”的处理方式。以避头尾标点为例，“优先推入式”避头尾在这种情况下会将本行内标点宽度挤压，为避头尾的标点腾出空间，如右图所示。

有的情况下，空白字符会位于某些行的行首，此时应将行首的空白字符剔除。

标点符号的宽度调整

连续标点符号的调整

无论文本整体采用何种风格，当夹注符号与其他符号连续排列时，或者夹注符号重复出现（如开始+开始，结束+结束，或者结束+开始）时，都应该进行原则上的调整，以使文字体裁更加紧凑、易读。原则上的调整度应为：如果任意两个相邻标点符号占用2个字宽，应当缩减成1.5个字宽。在此原则上，允许排版风格进一步调整让两个符号只占1个字宽。挤压方向判定原则上应该让开始、结束夹注符号应紧靠被夹注的内容。

具体的挤压规则如下：

  1. 【结束夹注符】后面是：开始夹注符、结束夹注符、顿、逗、句(包括全宽句点）、冒、分，就挤；

  2. 【开始夹注符】后面是：开始夹注符，就挤；

  3. 【顿、逗、句】后面是：开始夹注符、结束夹注符，就挤；

  4. 【分、冒】后面是：开始夹注符，就挤；

行首行尾标点挤压

当标点符号出现在行首或行尾时，以下的空隙调整规则使文字体裁更加紧凑、易读。

  1. 当行首出现开始夹注符号，可以缩减该符号始侧二分之一个汉字大小的空白。

  2. 原本占一个字宽的标点出现在行尾时，应缩减该符号末侧二分之一个汉字大小的空白。

如何支持 RTL？

RTL 是 Right-to-left 的缩写，其意为人们书写阅读习惯是从右向左，朝左继续的，常见的 RTL 语言有阿拉伯语，希伯来语等。iOS 从 9.0 开始提供了系统方案支持 RTL 界面，主要是提供了 leading 和 trailing 的 UILayoutGuide 来替代需要在 RTL 中翻转的场景下的 left 和 right，以及 UIView 的 semantic attributes —— 也就是说在 RTL 环境中，leading 等同于 right，trailing 等同于 left，而在一般环境下反之。有些解决方案使用 Window 镜像的方案来适配 RTL，然而有些元素是不可翻转的，例如文本类元素，因为文本类元素无条件需要正面对着观众。因此 UILabel、UITextView、YYLabel 等组件，默认就属于 不可翻转的元素。

那么自定义的Markdown 引擎又应该如何来处理 RTL 问题呢？

  1. Markdown 中有大量的文本类元素，不可翻转，那么就需要自己处理文本元素 RTL 逻辑；

  2. Markdown 还包括大量的其它元素，例如引用、表格、列表等，也需要适配 RTL 规则。

如何使用？

文本

引擎会针对每个段落，使用其第一个字符作为排列顺序的判断依据。比如文本 “مرحبا 你好”，因为第一个字符是阿拉伯语字符，所以会使用 RTL 规则处理。同理，如果文本是“你好 مرحبا“，因为第一个字符是中文，则会使用 LTR 规则

  1. 如果使用 LTR 规则，那么逐行扫描每一行中 RTL 的区域，并将这些区域中的 RTL 文本进行首尾翻转；

  2. 如果使用 RTL 规则，则要进行下面的步骤：

    1. 逐行扫描每一行中的 RTL 区域，并将其中 RTL 区域中的文本首尾翻转；

    2. 逐行扫描每一行中的 LTR 区域，将 LTR 区域最后的标点符号和空格分别移动到该区域首部位置；

    3. 以前面扫描出来的的区域为单位，循环移位；

引用

  1. 灰色竖直线要靠右排版；
  2. 其中的文字要整体右对齐；

列表

对于列表

  1. 黑色圆点整体靠右排版；
  2. 其中的文字要整体右对齐；

表格

对于表格：

  1. RTL 首先要整体靠右对齐；
  2. 表格的列也是从右往左排，例如 LTR 的第一列数字，在 RTL 中属于第三列
  3. 对齐方式也需要适配，例如 LTR 中的左对齐，在 RTL 变成了右对齐

区域选中

作为一个富文本渲染组件，自然需要和用户进行交互，而常见的交互操作首当其冲便是区域选中，由于是自定义组件，所以这个功能也需要开发实现。区域选中的功能原理比较简单：给定一片区域，如果某个元素在这块区域中，则进行染色，否则不进行处理。原理虽然简单，但是实践起来却是不易，接下里逐步描述实现过程

长按确定起点和终点

通常来说，区域选中都是通过长按来实现的，长按过程中有一些状态的变化，当长按结束后且未被取消，就可以获取起点和终点

修改起点和终点

当某个区域被选中后，仍然可以响应touch事件来拖拽起始或者结束锚点，从而改变选中区域

根据起点和终点确定区域

当给定起点和终点后，会发现仅仅通过两个点来定义一片区域会造成一些错误

如图所示，如果起点为sp，终点为ep，那么橙色区域则为两坐标点之间的区域，而浅绿色方格则为文字所在的方格，很明显这种情况下按照坐标来计算的话，这些文字方格是未被包含在区域中的，是无法被选中的，但是从实际体验上来说，是希望这些方格被选中的。所以硬计算坐标会有明显的缺陷。

换一个思路，如果某个点定位到某个方格中，则代表该方格被选中，在这种情况下，可以重新校正起点和终点：

  1. 将起点所在方格的左上角坐标设置为新的起点
  2. 将终点所在方格的右下角坐标设置为新的终点

那么新的选中区域如下所示，期望选中的方格都可以被选中

上述情况只是单行，多行又有新的问题，如果将区域人为地按照行来进行分割，会造成计算的错误，因为其中某些理应被选中的文字可能会占据多行，可能会出现无法归属的情况，导致未被选中，因此最终采取了补全方案：

  1. 将选中区域的左上角和右下角补全，整体区域作为\(S_1\)
  2. 将补全的区域作为\(S_2\)和 \(S_3\)
  3. 那么方格被选中的条件为：\(S_1\)包含该方格 && \(S_2\)和 \(S_3\)不包含该方格

该方案可以同时适应单行和多行的情况，非常便于理解和计算。

根据给定区域计算确定包含元素

确定好区域后，就可以遍历 Box 树进行匹配了，这里直接采用多叉树的前序遍历方式。当获取到这些包含着区域内的 box 之后，进行坐标转换，直接绘制即可。

平台适配

iOS

OC/C++ 混编

iOS 的平台适配是通过 OC/C++ 混编方式实现的，只需要将文件命名为.mm 形式，就可以在一个文件中同时访问 OC 和 C++ 的 API 。关于 OC/C++ 混编，有一些注意事项需要了解：objc++ 没有为 OC 类增加 C++ 的功能，也没有为 C++ 增加 OC 的功能，例如：不能用 OC 语法调用 C++ 对象，也不能为 OC 对象增加构造函数和析构函数，也不能将 this 和 self 互相替换使用。类的体系结构是独立的，C++ 类不能继承 OC 类，OC 类也不能继承 C++ 类。

更多的OC/C++ 混编细节可以参考我之前的一篇微信公众号投稿文章： 《深入理解 OC/C++ 闭包》。

每个接口都对应着一个实现类，混编可以在 .mm 中同时书写 OC 和 C++，非常直接了当。

Android

分层实现

Android平台的适配需要借助JNI来实现Kotlin和C/C++两种语言的相互通信，所以设计为3层：

  1. Kotlin 层的API层

  2. JNI 通信层

  3. C/C++ 的实现层

不同于 iOS，这里每个接口同时对应一个 C++ 的实现类（xxx_Android）和一个 Kotlin 的实现类。这是由于 Android无法做到混编，无论是 C++ 的实现类还是 Kotlin 的实现类，都无法单独完成接口适配的工作。二者必须通过 JNI 相互配合，弥补对方不足，绑定成一个整体来完成适配工作。

定制化

有些情况下，业务侧可能对某些节点有着不同的理解和呈现方式，Markdown作为一个SDK，在面对多个业务接入的情况下，还是需要遵守标准的渲染方式，那么如何来缓解这种矛盾呢？

解决问题的办法就是提供一种方式，让业务侧提供节点的实现UI，并将这种实现注入到引擎，注入的UI要参与Markdown的排版过程，最终被引擎绘制到画布上。

抽象View接口

第一步是定义 View 接口：getWidth、getHeight和 getDepth 用于布局，setX、setY和 getNativeView用于渲染。 这里列出的纯虚方法都是缺一不可的。

定义View_iOS

第二步是实现接口View。 对于 iOS，定义了 View_iOS，实现逻辑非常简单易懂。 唯一值得一提的是在 setX/setY/getNativeView 方法中调用了 invokeRenderBlockIfNeeded 方法。 这样做的原因是允许布局和渲染逻辑在不同的线程中完成，显然引擎不想在子线程中解析期间操作 UI。 实际上，在排版过程中并没有生成真正的视图。
