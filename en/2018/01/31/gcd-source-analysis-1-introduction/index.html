Preface

In everyday iOS development, GCD isolates us very well from direct interaction with threads, or pthread. What we usually deal with are queues and blocks. After using it for a long time, it is easy to stop feeling the presence of threads at all.

I had long wanted to find an opportunity to study the lower layers of GCD and appreciate the essence of its design. After some initial research, I found that materials analyzing GCD source code were scarce and scattered, making it difficult to form a complete understanding. One possible reason is that business demand does not strongly require this knowledge; the existing GCD APIs are already enough for most work. Even so, my curiosity about the underlying principles of GCD could not be stopped. On impulse, I decided to dig myself a hole and write a GCD source-code analysis series, describing my own understanding of GCD’s internals.

Choosing the GCD Version

The first step was choosing which version of the GCD source code to analyze. After comparing versions vertically, I found that later versions became larger and larger, with a rapidly increasing number of files and increasingly unfriendly source style. They were filled with a large number of macro-based build options, which made the code mentally expensive to read and not very helpful for understanding the core mechanism. After comparing multiple versions, I finally chose libdispatch-84.5.5.

These are all the project files in that version. It is small, but complete enough; it still contains everything in GCD.

Preparation

Before reading the GCD source code, we need to understand some related basics.

Atomic Operations

Before analyzing the source code, first look at some atomic-operation macros. You do not need to memorize them; just keep an impression and look them up later when needed.

  • __sync_lock_test_and_set((p), (n)) sets *p to value and returns the previous value of *p.
  • __sync_bool_compare_and_swap((p), (o), (n)) provides atomic compare-and-swap: if *p == o, write n into *p. Here p is the address, o is the old value, and n is the new value.
  • __sync_add_and_fetch((p), 1) increments by 1 first, then returns.
  • __sync_sub_and_fetch((p), 1) decrements by 1 first, then returns.
  • __sync_add_and_fetch((p), (v)) adds v first, then returns.
  • __sync_sub_and_fetch((p), (v)) subtracts v first, then returns.
  • __sync_fetch_and_or((p), (v)) returns first, then performs OR.
  • __sync_fetch_and_and((p), (v)) returns first, then performs AND.

__builtin_expect

Processors generally use a pipeline model, and some contain multiple logical execution units. The system can fetch multiple instructions in advance and process them in parallel. But when it encounters a branch, it may need to fetch instructions again, which is slower than continuing with already-prefetched instructions.

Because programmers are often bad at branch prediction, this built-in function, __builtin_expect, helps programmers provide branch-prediction hints and optimize programs. Its first parameter, EXP, is an integer expression, and the return value of the built-in function is also EXP. C is a compile-time constant. Its meaning is: I expect the value of EXP to equal constant C; the compiler should optimize based on that expectation.

Basic Data Structures

dispatch_object_t

dispatch_object_t is a union, so it can represent every data type inside that union.

Pay attention to __attribute__((transparent_union)). This is a typical transparent union. A transparent union weakens C’s type-checking mechanism and works somewhat like an implicit cast. With it, dispatch_object_s behaves like a C++ base class, making function parameter passing in C much more convenient.

At the lower level, types do not really exist in the same way we usually think about them. A transparent union breaks some of the constraints that types impose on us, allowing data to be viewed from a lower-level perspective. But it also weakens C’s type checking, which can lead to serious errors.

dispatch_object_s

dispatch_object_s is the base structure of the entire GCD system, and it is very important. Some fields are briefly explained in the comments. As the analysis goes deeper, we will gradually understand why each of these fields exists.

dispatch_continuation_s represents a task. Blocks passed to dispatch_async are usually wrapped into this data type.

If dc_vtable is less than 127, then the object is a continuation. Otherwise, the object has a private layout and memory management rules. The first two words must align with normal objects.

dispatch_queue_s

The difference between dispatch_queue_s and dispatch_object_s is that dispatch_queue_s adds DISPATCH_QUEUE_HEADER and dq_label[DISPATCH_QUEUE_MIN_LABEL_SIZE]. This also tells us that queue names should be shorter than 64 characters.

pthread_key_t

In a multithreaded environment, data space is shared, so global variables are also shared by all threads. But sometimes an application needs thread-private global variables: values that are valid only inside a certain thread but can still be accessed across multiple functions. For example, each thread may need to maintain its own linked list while using the same functions to operate on it.

The simplest way is to use thread-specific data structures with the same name but different variable addresses. This kind of data structure is called Thread-Specific Data, or TSD.

GCD defines four keys:

pthread_key_create

_dispatch_thread_key_init_np calls pthread_key_create:

This function allocates an entry from the TSD pool and assigns its value to key for later access. If destr_function is not empty, when the thread exits through pthread_exit(), destr_function() is called with the data associated with key, allowing allocated buffers to be released.

No matter which thread calls pthread_key_create(), the created key is accessible to all threads. But each thread can fill that key with a different value according to its own needs. These values are thread-specific and maintained independently for each thread. This is equivalent to providing a global variable with the same name but different values per thread.
