JSPatch's dealloc Sorrow

Posted on 2018-01-21 | In iOS
Words count in article: 43k | Reading time ≈ 2:37
中文 / English

Preface

As a lightweight hotfix solution, JSPatch once solved many pain points for app hotfixes. It even became extremely popular and looked ready to dominate the hotfix field. But because it violated Apple’s rules, it was banned, and many companies became afraid to continue using such indirect workarounds.

Although the ending of JSPatch is regrettable, as iOS engineers there are still many excellent ideas inside it worth studying. Today I mainly want to analyze JSPatch’s dealloc problem.

What Is dealloc Sorrow?

Anyone who once integrated JSPatch has probably had this requirement: if a released online version has resources that were not released correctly in dealloc, or if the release logic itself has a problem, then we need to rewrite the dealloc method. This requirement is reasonable. However, JSPatch at the time struggled with this problem:

    1. After replacing dealloc with JavaScript, when dealloc is called, self is wrapped as a weakObject and passed to JS, which causes a crash.
    1. If the current object is not wrapped, the JS replacement for dealloc can run successfully, but the native dealloc is not called, so the object is not released and memory leaks.

Later, the author Bang came up with a solution:

    1. When dealloc is called, do not wrap self as a weakObject; wrap it as an assignObject and pass it to JS.
    1. When calling ORIGdealloc, because selectorName has changed, ARC does not recognize it as a dealloc method, so ARC needs to be tricked.

When I first saw this solution, I was genuinely impressed. The only flaw is that it still did not completely solve JSPatch’s dealloc problem. Why? Because this solution leaves one issue behind: the JavaScript dealloc method and the Objective-C dealloc method are both called.

Imagine this: if the Objective-C dealloc method has a bug, I only want the JS dealloc method to run after hotfixing with JSPatch. I do not want the Objective-C dealloc to run, while still correctly releasing object memory. But after the current JSPatch hotfix, Objective-C dealloc still executes. Wouldn’t the original bug in dealloc happen again? That is why I call it the sorrow of dealloc.

Analysis and Solution

Now let’s analyze why JSPatch’s dealloc problem is so tricky.

Why Does weak Wrapping Crash?

The author’s initial approach was to wrap self as a weakObject and pass it to JS when dealloc was called. The main purpose was to avoid JS holding a strong reference to self, which would prevent dealloc from being called. However, this solution crashes:

Tracing runtime’s weak_register_no_lock, we find the clue:

weak_register_no_lock first checks whether the object is being deallocated. If it is, it aborts the program through _objc_fatal, causing the crash. The crash message we saw comes exactly from this _objc_fatal. This shows that when an Objective-C object’s dealloc function has already been triggered, weak references to that object are not allowed.

Why Does assignObject Avoid the Crash, and How Can We Avoid Calling Objective-C dealloc?

assign is just a pointer reference. It does not participate in Objective-C memory management, so it does not cause the weak-reference crash above. But improper access can easily cause dangling-pointer crashes, so it must be used carefully.

How can we avoid calling Objective-C dealloc? Before solving this, first understand how Objective-C object deallocation works. In ARC, calling [super dealloc] is not allowed. The compiler automatically inserts [super dealloc] during compilation.

Create a class called XXObject and trace the dealloc call flow:

It is not hard to see that the Objective-C dealloc function only handles the release logic we write. The real object cleanup work is completed by runtime. In objc_destructInstance, it:

  • Executes the C++ destructor if the class has one.
  • Removes and releases associated objects attached through runtime.
  • Clears the object’s SideTable weak table.

Since the Objective-C dealloc logic has already been replaced by the JS dealloc logic, the Objective-C dealloc logic should be skipped. Previously, because we did not understand the internals of Objective-C dealloc, we felt the compiler might be doing mysterious work inside it and had no way forward. But now we know that the core cleanup happens in objc_destructInstance. Even if Objective-C dealloc is not called, object cleanup is not absolutely affected. We can bypass this Objective-C dealloc obstacle in a certain way: after calling JS dealloc, skip the current class’s Objective-C dealloc and directly call the superclass’s dealloc. Although ARC prevents us from writing [super dealloc], we still have runtime.

What Happens If Both Parent and Child dealloc Are Hooked?

It still crashes, this time because of stack overflow:

As shown above, JPViewController JS dealloc keeps executing repeatedly.

Analyze the reason based on the previous modification:

When subclass JPViewController’s dealloc is called, we find the IMP of the superclass’s dealloc and call it through originalDealloc(assignSlf, NSSelectorFromString(@"dealloc"));.

Because the superclass JPBaseViewController’s dealloc has also been hooked, it eventually forwards into the same code again. But after Class instClass = object_getClass(assignSlf); executes, the class is still JPViewController, and its superclass is still JPBaseViewController. This forms an infinite loop and eventually causes stack overflow.

The first solution that comes to mind is to use a while loop and brute-force the dealloc inheritance chain. But if one dealloc method in the middle has been hooked as a JS block, then executing that JS block must also be handled. Clearly, this approach requires a lot of work and many edge cases.

Why?

    1. The Objective-C dealloc method itself has already been hooked into a JS block, so the Objective-C dealloc method is basically impossible to execute. Remember: do not call self.ORIGdealloc() inside the JS dealloc block, otherwise it is unnecessary and may crash.
    1. When the JS dealloc block is executing, the if (deallocFlag) block has not yet run. Therefore, self inside JS dealloc is still JPViewController. When if (deallocFlag) finally executes, it is already focused on final resource release through runtime and will no longer call custom methods. Therefore, it will not crash, and object_setClass is safe to use here.

Summary

The final solution is very simple: a small “skip” action plus changing the object’s own class. But for a long time, I had no idea how to solve this problem. Only after reading the runtime source code carefully did everything suddenly become clear.

Although JSPatch is no longer something we pay much attention to because of Apple’s policy, the core ideas inside it are still worth studying. And if other libraries, such as Aspects, use principles very close to JSPatch, could they also have similar problems?
