JSPatch VS Aspects

Preface

Many iOS open-source projects implement various kinds of magic by hooking the third stage of message forwarding, forwardInvocation. If a project integrates multiple libraries that do this, we may enjoy the convenience they provide, but we may also run into all kinds of traps caused by them.

iOS Message Forwarding

iOS message forwarding has been explained many times, so I will not repeat the basics. Here are the key points. Objective-C method invocation mainly follows this flow:

    1. First look in the class method cache. If found, jump to done.
    1. Search the class method cache again. If found, jump to done.
    1. Traverse the class method list. If found, add the method to the cache and jump to done.
    1. Walk through the superclass chain until NSObject, repeating steps 3 and 4 for each superclass.
    1. If the method is not found in the current class or any superclass, enter method resolution. If resolution succeeds, jump to retry.
    1. If method resolution is not implemented, runtime asks whether the receiver has another object that can handle this unknown selector through forwardingTargetForSelector:.
    1. If there is no fallback receiver, message redirection begins. Runtime wraps all details of the unknown message into an NSInvocation object and calls forwardInvocation:.

Hooking Through iOS Message Forwarding

Based on the message forwarding mechanism above, when an Objective-C object method is called, runtime searches upward along the inheritance chain until NSObject. If it still cannot find the method, the method does not exist, but an exception is not thrown immediately. Instead, the call goes through multiple forwarding stages, such as -resolveInstanceMethod:, -forwardingTargetForSelector:, -methodSignatureForSelector:, and -forwardInvocation:.

The final -forwardInvocation: receives an NSInvocation object. This object stores all information about the method call, including selector name, argument types, return value type, and most importantly all argument values.

If we want to implement a library that dynamically changes method implementations, we can hook forwardInvocation: define our own forwarding handler, redirect calls to target methods into that handler, and then dynamically control where those methods go next.

2. Aspects Hooking

Aspects supports not only class hooks, but also object hooks, offering finer granularity. For object-level hooks, Aspects does not directly swizzle the object’s forwardInvocation method. Instead, it dynamically creates a subclass of the current object, associates the object with that subclass, and replaces the subclass’s forwardInvocation. The idea is similar to KVO: the current object becomes an instance of a subclass, while external users can still treat it as the original object. All swizzling happens on the subclass, so the original class does not need to be changed. Object-level hooks in Aspects are not the topic today.

Why does it crash?

  • According to pointer 1, calling test enters forwarding. Since SEL(forwardInvocation) points to IMP(JPforwardInvocation), forwarding enters JPforwardInvocation. The JS block for test is found and executed.
  • The JS code calls self.ORIGtest(). Because of replacement order, SEL(ORIGtest) no longer points to IMP(test), but to IMP(_objc_msgForward), so it is forwarded again to IMP(JPforwardInvocation).
  • Now the JS block for _JPORIGtest cannot be found, so JSPatch falls back to its original forwarding path, SEL(ORIGforwardInvocation). But due to overwriting, SEL(ORIGforwardInvocation) points to IMP(__ASPECTS_ARE_BEING_CALLED__), so it enters __ASPECTS_ARE_BEING_CALLED__.
  • Inside __ASPECTS_ARE_BEING_CALLED__, the block for SEL(aspects__ORIGtest) cannot be found either, so it continues to Aspects’ original forwarding path, SEL(__aspects_forwardInvocation), which points to IMP(forwardInvocation).
  • In this example, IMP(forwardInvocation) is not implemented, so it crashes. Even if we implemented it, we would still not expect a selector like SEL(aspects__ORIGtest), so a crash would still be likely.

How can this be solved?

In theory, ORIGtest, as the original implementation of the function, should not enter forwarding. It should point directly to IMP(test). Once it enters JPforwardInvocation, it means the class’s test method has already been hooked by another library. We need to check whether the current ORIGtest has also been hooked. If not, follow the original flow. If it has been hooked, remove ORIG and forward again.

Why does it crash?

    1. According to pointer 6, sending test to an instance of MySubClass goes into forwarding. According to pointer 9, MySubClass’s SEL(forwardInvocation) points to IMP(JPforwardInvocation), so it enters JPforwardInvocation.
    1. The JS block for test is found and executes, printing MySubClass jspatch log. The JS block calls self.super().test(). JSPatch’s super-call mechanism works by finding the IMP implementation of the superclass method and adding a new method to the current class that points to the superclass’s IMP. Calling this new method is equivalent to calling super. So when self.super().test() is called, JSPatch adds SEL(SUPER_test) to MySubClass, pointing to the superclass MyClass’s IMP(test). Unfortunately, the superclass’s SEL(test) already points to IMP(_objc_msgForward), so SEL(_JPSUPER_test) also points to IMP(_objc_msgForward).
    1. According to pointer 9, forwarding enters JPforwardInvocation again. This time the JS block for SEL(_JPSUPER_test) cannot be found, so it follows the original forwarding path and enters JPExecuteORIGForwardInvocation.
    1. Since subclass MySubClass does not implement forwardInvocation, it enters the superclass MyClass forwarding path. According to pointer 4, it enters __ASPECTS_ARE_BEING_CALLED__. But inside that function, no block for SEL(aspects__SUPER_test) can be found, so it crashes directly.

How to solve it?

This problem is similar to the ORIG issue. In theory, a super call should not enter its own forwarding path; it should point directly to the superclass implementation. But because the superclass has already been hooked by Aspects, the call to self.super().test() accidentally enters the current forwarding path again, causing everything that follows.

Following the same idea, before falling back to original forwarding when the JS block is not found, check whether selectorName has the SUPER_ prefix and whether its IMP has already been hooked to _objc_msgForward. If so, remove the SUPER_ prefix and forward again.

    1. The subclass’s own SEL(__aspects_forwardInvocation) points to an unimplemented IMP(forwardInvocation), so it crashes directly.

How can this be solved?

The root cause is that the subclass cannot handle SEL(aspects__superTest), while the superclass forwardInvocation, which can really handle it, is not reached. In other words, the inheritance of forwardInvocation is broken by the hooks on the superclass and subclass. The solution is to let the inheritance hierarchy handle it.

How to Keep a Correct Hooking Posture

So far, we have analyzed several problems caused by JSPatch and Aspects both hooking message forwarding through forwardInvocation, and we have proposed solutions one by one. The core of the solution is to identify the forwarding state after multiple libraries have hooked it, and then analyze the method invocation flow from that state.

Although the previous fight involved only two libraries, the complexity is already quite high. If you have read this far, you can probably feel it too. And this is only a two-library conflict. What if there are more libraries?

Each library’s hook logic often considers only itself, assuming it is the only one using this kind of runtime magic in the project. But other libraries think the same way. Since hooks must have an order, logic overwriting or strange forwarding jumps are inevitable, which can lead to crashes and logic errors.

    1. Crashes are definitely what we least want, so they must be analyzed, solved, and avoided.
    1. Logic overwriting may not necessarily crash, but if several hook libraries are used on the same class, does that product logic or technical logic already have a problem?
    1. A fundamental reason multiple hook libraries fail together is that each library assumes SEL(forwardInvocation) points to the original IMP(forwardInvocation) before it hooks. It does not know that another library may have already changed SEL(forwardInvocation) to another implementation. The original forwarding implementation is then lost to the current library, causing incorrect original forwarding and crashes. If we implement a mechanism for getting the true original forwarding implementation without relying on the pre-hook state, this problem can be improved. Even so, logical overwriting of SEL(forwardInvocation) is probably unavoidable to some extent. If the integrated library is closed source, the situation becomes even more serious.

So when implementing this kind of library, or integrating one, be extra careful with the traps it may bring.

Summary

Forwarding is risky. Hook with care.
