Now analyze the core function, dispatch_once_f:

    1. As mentioned in the opening article, dispatch_atomic_cmpxchg is a macro whose prototype is __sync_bool_compare_and_swap((p), (o), (n)). It is a lock-free atomic operation based on CAS. The principle is: if p == o, set p to n and return true; otherwise, do nothing and return false.
    1. In a multithreaded environment, if thread A enters dispatch_once_f for the first time and *val == 0, it atomically changes the value to 1, executes the block passed into dispatch_once_f, calls dispatch_atomic_barrier, and finally changes *val to ~0.
    1. dispatch_atomic_barrier is a memory barrier. From the processor’s perspective, a memory barrier serializes read and write operations. From the software perspective, it solves sequential consistency problems. The compiler may reorder instructions, and the processor may execute instructions out of order. Inserting a memory barrier is equivalent to telling the compiler that instructions before and after the barrier cannot be reordered, and telling the processor that instructions after the barrier can only begin after instructions before it are complete. Therefore, dispatch_atomic_barrier guarantees that *val is modified only after the block finishes executing.
    1. While thread A is executing the block, if other threads also enter dispatch_once_f, the atomic check in the if branch must return false, so they enter the else branch and run the do-while loop. Inside the loop, _dispatch_hardware_pause is called. This helps improve performance and reduce CPU power usage. pause is similar to nop: it delays while spinning. The loop exits only after the first thread has finished executing the block and changed *val to ~0, followed by another dispatch_atomic_barrier. This means other threads cannot execute the block, which guarantees the uniqueness of the block execution in dispatch_once_f, and therefore the singleton is unique.

dispatch_once Deadlocks

After all that, does it mean singletons written with dispatch_once are completely worry-free?

Not really. Improper use of dispatch_once can cause deadlocks.

  • Deadlock pattern 1:
  1. Thread T1 calls singleton A. This is the first call in the application’s lifetime, so dispatch_once(&token, block()) is used to initialize the singleton.
  2. Some function inside block() calls dispatch_sync_safe, synchronously executing code on thread T2.
  3. A function currently running on T2 needs singleton A, so it calls dispatch_once again.
  4. Now T1 is waiting for the block to finish. The block is waiting for T2 to finish. T2 is waiting for T1’s dispatch_once to complete. They wait on each other, causing a deadlock.
  • Deadlock pattern 2:
  1. Thread T1 calls singleton A. This is the first call in the application’s lifetime, so dispatch_once(&token, block()) is used to initialize it.
  2. The block may call flow B, flow B calls flow C, and flow C may call singleton A again, triggering dispatch_once again.
  3. This again creates mutual waiting.

So when writing singletons, keep these points in mind:

  • Keep initialization as simple as possible.
  • Try to make initialization self-contained and reduce dependencies on other modules or classes.
  • Think carefully about whether a singleton is really needed. Do not create singletons casually, because once initialized they keep occupying resources and cannot be released, causing waste.
