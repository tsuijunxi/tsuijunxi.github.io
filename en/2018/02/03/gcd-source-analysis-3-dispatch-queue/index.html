Custom Queues

_dispatch_queue_init

Now look at the inline function _dispatch_queue_init:

From the previous code, global queues all have dq_width equal to UINT32_MAX, while _dispatch_queue_init sets dq_width to 1. This means a custom queue defaults to a serial queue.

Also, dq->do_targetq = _dispatch_get_root_queue(0, true) involves an important GCD queue/block model: the target queue. Blocks submitted to any queue are eventually placed on its target queue for execution. For a normal serial queue, the target queue is an overcommit-capable global queue, and the global queue is backed by a thread pool.

Other fields can mostly be understood from the previous sections. Here, focus on dq_serialnum:

Zero is skipped, 3 is unused, 1 is used by the main queue, 2 by the manager queue, and 4 to 9 by global queues. Custom queues start from 10. Each time a custom queue is created, _dispatch_queue_serial_numbers is updated atomically and then decremented by 1, which guarantees that every custom queue has a unique dq_serialnum.

Special Handling of dispatch_queue_attr_t

If an attr parameter is passed while creating a custom queue, it indicates overcommit support. An overcommit queue means that whenever a task is submitted, the system opens a new thread to handle it, avoiding overload on a single thread.

Also, if finalizer_func == _dispatch_call_block_and_release2, dq_finalizer_ctxt needs to be retained.

Common API Analysis

dispatch_async

dispatch_async mainly prepares its parameters and then calls dispatch_async_f.

    1. _dispatch_Block_copy creates a copy of the incoming block on the heap, or increases its reference count, ensuring that the block is not destroyed before execution.
    1. _dispatch_call_block_and_release, as the name suggests, calls the block and then releases it.

dispatch_async_f

Now analyze dispatch_async_f:

    1. First look at _dispatch_continuation_alloc_cacheonly. Its purpose is to fetch a dispatch_continuation_t structure from the thread’s TLS, or thread-local storage. Each thread has its own private storage, and that storage is not used by other threads.
    1. If the current thread’s TLS does not contain a dispatch_continuation_t, _dispatch_async_f_slow() is used.
    1. If dc is not empty, set its do_vtable to DISPATCH_OBJ_ASYNC_BIT, mainly for type distinction. Store the incoming block in dc_ctxt as context, set dc_func to _dispatch_call_block_and_release, and finally call _dispatch_queue_push to enqueue it.

DISPATCH_OBJ_ASYNC_BIT is a macro used to distinguish async, group, and barrier:

After obtaining a dispatch_continuation_t from the heap, it sets the same fields as above and then enters _dispatch_queue_push.

_dispatch_queue_push

_dispatch_queue_push is a macro. It actually calls _dispatch_queue_push_list.

_dispatch_queue_push_list

_dispatch_queue_push_list is an inline function, which suggests it is called very frequently. Inline functions are common in kernel-style code and are efficient, though they can increase binary size: a classic space-for-time tradeoff.

    1. If the queue is not empty, place dc at the tail and redirect dq->dq_items_tail. Since there are already tasks before it, inserting at the tail is enough.

Why is this a redirection? According to the definition of dispatch_atomic_xchg, it “sets *p to n and returns the previous value of *p”. Therefore, dispatch_atomic_xchg(&dq->dq_items_tail, tail) is equivalent to setting dq->dq_items_tail = tail, while prev is the old tail element and prev->do_next = head links the new node at the end.

    1. If the queue is empty, call _dispatch_queue_push_list_slow:

_dispatch_queue_push_list_slow sets dq->dq_items_head to dc, then calls _dispatch_wakeup to wake the queue. It calls _dispatch_wakeup because the queue is empty, no task is running, and the queue is sleeping.

_dispatch_wakeup

Now analyze how a queue is woken up. Here dou refers to a queue:

    1. If it is the main queue, call _dispatch_queue_wakeup_main directly.

The core logic that wakes the main thread is inside _dispatch_send_wakeup_main_thread, but unfortunately that part is not open source.

    1. If it is a global queue, execution enters _dispatch_queue_wakeup_global, the function pointed to by the global queue’s dx_probe. Here we truly encounter pthread:

There are two main paths:

    1. If dgq_kworkqueue exists in the queue context, call pthread_workqueue_additem_np. This function uses the workq_kernreturn system call to notify the workqueue that a new item should be executed. Based on this notification, the XNU kernel decides whether to create a thread according to system state. For an overcommit priority queue, workqueue always creates a thread, and that thread later executes _dispatch_worker_thread2.
    1. If dgq_kworkqueue does not exist, call pthread_create to start a thread directly. The thread entry is _dispatch_worker_thread, but that function still calls _dispatch_worker_thread2, so both paths eventually converge.

_dispatch_worker_thread

The first part mainly sets the signal mask of the new thread. Real task scheduling happens in _dispatch_worker_thread2.

After task scheduling ends, this thread waits on a semaphore. The semaphore it waits on is the same one used in dispatch_queue_wakeup_global. Why do this? To avoid creating new threads too frequently. If a newly created thread has finished all tasks, it does not immediately exit. Instead, it waits on a semaphore for about 65 seconds. If a new signal arrives within 65 seconds, meaning a new task has arrived, the thread continues executing that task instead of creating another thread. If no signal arrives after 65 seconds, the thread exits and is destroyed.

_dispatch_worker_thread2

The two paths mentioned earlier eventually call _dispatch_worker_thread2, so the core execution logic is here and deserves special attention:

This function schedules tasks. Two functions are important:

    1. _dispatch_queue_concurrent_drain_one, which takes one item from the queue.
    1. _dispatch_continuation_pop, which processes the item taken from the queue.

_dispatch_queue_concurrent_drain_one

mediator is used as both a lock and a signal. If the queue is empty, it returns NULL. If the current thread loses ownership of the queue during competition, it wakes the global queue and returns. Otherwise, it takes the head item, moves the queue head forward, and returns the old head.

_dispatch_continuation_pop

From this function, we can see that what is pushed into a queue is not only continuation tasks, but may also be another queue. If it is a queue, _dispatch_queue_invoke is executed directly. Otherwise, it executes dc->dc_func(dc->dc_ctxt).
