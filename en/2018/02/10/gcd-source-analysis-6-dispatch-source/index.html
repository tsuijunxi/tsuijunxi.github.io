Preface

Compared with other parts of GCD, dispatch_source is probably the least eye-catching one. It is a wrapper around kqueue, a common BSD kernel facility, and can monitor certain kinds of events. When those events occur, it automatically places a block onto a dispatch queue for execution. If you already know a little about I/O multiplexing, dispatch_source is much easier to understand.

kqueue

kqueue is one BSD implementation of I/O multiplexing. Its interface mainly consists of two system calls, kqueue() and kevent(), plus the struct kevent structure.

    1. kqueue() creates a kernel event queue and returns its file descriptor.
    1. kevent() registers or unregisters events with the kernel, and returns ready events or error events.
    1. struct kevent is the basic event structure operated on by kevent().

Inside one kqueue, {ident, filter} uniquely identifies an event:

    1. ident is the event ID. It is usually set to a file descriptor.
    1. filter can be understood as the event type. The kernel checks the state of the filter registered on ident, and notifies the application when that state changes. kqueue defines many filters:

For cases that need very high timing precision, we may consider CADisplayLink; in fact, GCD timers are also an option.

First, the handler is copied. Then dispatch_barrier_async_f is called. This method is extremely similar to dispatch_async_f from the queue article: it sets the block on a continuation and pushes it into the target queue. Also notice that dispatch_barrier_async_f treats ds directly as a queue. That is reasonable because their structure definitions are highly similar.

It sets the cancellation flag, wakes the source, performs cancellation, unregisters the source, and finally releases resources.

dispatch_source_get_xxx

dispatch_source_merge_data

dispatch_source_merge_data merges data into a dispatch source of type DISPATCH_SOURCE_TYPE_DATA_ADD or DISPATCH_SOURCE_TYPE_DATA_OR, and submits its event handler block to the target queue.

dispatch_resume

From the creation process above, a newly created source normally has do_suspend_cnt set to DISPATCH_OBJECT_SUSPEND_INTERVAL, meaning it starts in a suspended state and must be manually started with dispatch_resume.

The switch branch above should obviously go through DISPATCH_OBJECT_SUSPEND_INTERVAL, which calls _dispatch_wakeup.

_dispatch_wakeup was also analyzed in the queue article. It is mainly related to do_invoke. For a source, do_invoke points to _dispatch_source_invoke. This method executes all source actions. Each action is guaranteed to run on the proper queue. If the current queue does not match the action, the correct queue is returned, and the action later runs on that returned queue. This is the core focus of this article.

This function mentions the manager queue, _dispatch_mgr_q, many times. Some cases must switch to the manager queue, for example:

  • ds_is_installed is false.
  • ds_dkev is not empty.
  • ds_needs_rearm is true.

The manager queue is analyzed later.

_dispatch_kevent_merge

  • Find existing kevents, and merge any new flags if necessary.

The function searches for whether an identical dispatch kevent is already being observed. If it exists, new flags are merged. This also shows that a kevent is independent of a source; it does not belong exclusively to one source. If the event does not exist, the dk is inserted into the event queue. Finally, the source’s ds_list is inserted into the kevent source queue, and when flags are updated the kevent event is registered again.

Summary

This article is long and relatively complex, and source itself is also less familiar than other GCD APIs. The two most important ideas here are I/O multiplexing and the manager queue. Once you keep those two points in mind, the underlying principle of dispatch_source becomes much easier to understand.
