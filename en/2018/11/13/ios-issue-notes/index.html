Launch Images

Are You Really Reusing Cells?

In iOS development, cell reuse is completely normal. But for complex cells, the number of internal elements is often uncertain. Each reused cell may need a series of logic checks, a suitable height calculation, and a relayout of its subviews. That greatly reduces the benefit of reuse.

To avoid that trouble, some implementations remove all subviews after obtaining a reused cell, then recreate subviews according to the new model data. It is convenient, but it brings performance problems.

Take the comic-bookstore page in QQReader as an example. Every time the cell receives data, it used to do this:

Instrumentation showed that cellForRow accounted for as much as 17.6% of the time:

I then adjusted the comic-bookstore cell logic according to these principles:

  • Reuse the cell, and create each subview in the cell only once.
  • Create subviews lazily, only when they are actually needed.
  • When the reused cell has more subviews than the current data needs, hide the redundant ones.
  • For each network response, calculate each data model’s height only once, then cache and reuse it. After a refresh, discard all model data and cached heights.

So do not underestimate the performance cost of creating views.

How Can a C++ Container Store Objective-C Objects?

In everyday iOS development, the most commonly used containers are probably NSArray and NSDictionary. But in scenarios with stricter performance requirements, these containers can become insufficient. Many people choose Objective-C++ so they can use powerful C++ libraries such as STL.

The tricky part is that Objective-C object memory management is more troublesome than ordinary C++ object management. If an Objective-C object is placed directly into an STL container, the container will not manage it by default. We need to retain and release it manually.

Here I directly quote duboleon’s solution under MRC:

  • With retain, the original Objective-C object’s reference count is incremented when the handle is constructed and decremented when the handle is destroyed.
  • With copy, the Objective-C object must conform to NSCopying and implement copyWithZone:.
  • With assign, only assignment is performed.
  • By overloading operator*, *handle can be used to retrieve the Objective-C object stored inside the handle.

UIButton Highlight Delay in UIScrollView

During development, I noticed that a UIButton inside a UITableViewCell had a delayed highlight. The reason is:

When a finger touches the content of a UIScrollView, the following sequence occurs:

  1. The touch event is intercepted, and tracking becomes YES.
  2. An internal timer starts, with a default interval of 150 ms. It checks whether the finger moves within a very short time window.
  3. If movement is detected in that interval, UIScrollView starts scrolling by itself, tracking becomes NO, and even if there is an internal control under the touch that could respond, it will no longer receive the touch event.
  4. If no movement is detected in that interval, tracking remains YES; if there is an internal control under the finger that can respond to touch events, the event is passed to that control.

The Unruly UITableViewCell

Recently, while building a color tag, I thought using UILabel would be convenient. Unexpectedly, it caused trouble inside UITableViewCell. The reason is that UITableViewCell changes the background color of its subviews when highlighted:

But sometimes this is not the effect we want.

After looking through some references, I found one solution.

The main idea is to swizzle UITableViewCell’s setHighlighted:animated: method and UILabel’s setBackgroundColor: method. When the UITableViewCell becomes highlighted, update the label’s forbidSetBackgroundColor flag to control whether its background color can be changed.

This solution feels too heavy. Paying such a high cost for a small background-color issue is not really worth it. Every UITableViewCell calls setBackgroundColor: during initialization, and the solution also introduces an invasive property, firbidSetBackgroundColorWhenHighlighted, which external code must set to indicate whether this logic should run.

Most importantly, it does not solve the problem completely. Although it avoids UITableViewCell’s highlight logic, some custom controls in the project also have their own highlight logic and still cannot escape the same problem. So this is not a perfect solution.

The root cause is that we cannot control when a view’s setBackgroundColor: method is called.

How can we defuse this?

What if we implement a custom control and explicitly control who is allowed to call setBackgroundColor:?

Take QRCellLabel as an example.

  1. Define an internal class, QRCellInnerLabel, inherited from UILabel. Add a shouldSetBackgroundColor property to control whether setBackgroundColor: is allowed.
  1. Define a QRCellLabel class that mirrors common UILabel properties for convenient use. At compile time, forbid direct calls to setBackgroundColor: and expose a custom qr_setBackgroundColor: method.
  1. QRCellLabel contains two subviews: a UIImageView and a QRCellInnerLabel. The former is used for the background color, while the latter is used for text.

The implementation strategy is:

  • Implement setBackgroundColor: as an empty method. Even if outside code calls it, the control’s background color will not change.
  • In qr_setBackgroundColor:, turn on shouldSetBackgroundColor, set QRCellInnerLabel’s background color, then immediately turn shouldSetBackgroundColor off. This way the control’s background color can only be changed through the method it exposes.

With this approach, no matter which parent view contains the control, its background color cannot be changed without permission.

UIImageView Reuse

QQReader previously had an issue where book covers on the bookshelf would occasionally appear in the wrong place. I always thought it was caused by cell reuse. But after a long investigation, I found that before each cell reuse, the UIImageView’s image property was already being set to nil, so it felt like this should not happen. I even suspected the refresh mechanism for a while. I was naive.

Recently, I finally located the real problem.

Suppose a cell starts loading cover URL A. Before the network request returns, the cell is reused and starts loading cover URL B. But URL B returns earlier than URL A, or a local cover is set. Finally, URL A’s request returns. Because the old request was not unbound from the image view, it still sets the image, so the cell that should display cover B ends up displaying cover A. That causes the cover mix-up.

This also explains why simply setting UIImageView.image = nil before reuse is not enough.
