Preface

After JavaScript source code goes through lexical analysis and syntax analysis, it produces a syntax tree. The next task is to convert that syntax tree into bytecode, which is the subject of this article.

This whole process is essentially a step every programming language must go through: compilation. But unlike many languages such as C, C++, and Objective-C, after JavaScript compilation finishes, it does not generate object code or an executable file stored on disk. The generated bytecode may be interpreted line by line by the virtual machine immediately, or it may be cached and later converted into native code through JIT.

BytecodeGenerator

BytecodeGenerator means exactly what its name says: it generates bytecode. It exposes a class method named generate. Inside, it calls the constructor to create a temporary BytecodeGenerator, then calls its parameterless generate method. The return value indicates whether a parse error occurred, while the actual bytecode result is stored in the third parameter, CodeBlock.

Next, let’s look at several of its private constructors:

BytecodeGenerator needs the following parameters. Except for DebuggerMode, any one of them could easily take an entire article to explain, so I will keep this brief.

  • VM: the virtual machine.
  • Node: one of ProgramNode, FunctionNode, EvalNode, or ModuleProgramNode.
  • UnlinkedCodeBlock: corresponding to the node, one of UnlinkedProgramCodeBlock, UnlinkedFunctionCodeBlock, UnlinkedEvalCodeBlock, or UnlinkedModuleProgramCodeBlock.
  • DebuggerMode: whether it is in debug mode.
  • VariableEnvironment: the variable environment.

UnlinkedCodeBlock

No matter which of the above nodes calls emitBytecode, the flow eventually reaches emitStatementsBytecode. After all, whether it is ProgramNode, EvalNode, or FunctionNode, it is composed of basic statements.
