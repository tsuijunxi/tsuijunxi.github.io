Syntax Analysis Overview

In compiler theory, syntax analysis can generally be divided into top-down and bottom-up approaches:

  • Top-down analysis: builds the parse tree from the top, or root node, toward the bottom, or leaf nodes. Recursive descent parsing is the common form of top-down parsing. It may require backtracking and can be inefficient, so predictive analysis is introduced. By looking ahead a fixed number of symbols, k, in the input, it chooses the correct production. The most typical example is LL(1) grammar, which eliminates ambiguity, left recursion, and backtracking. Based on LL(1), one may further compute FIRST, FOLLOW, and SELECT sets, then introduce a predictive parsing table to choose productions.
  • Bottom-up analysis: builds the parse tree from the bottom, or leaf nodes, toward the top, or root node. The common framework for bottom-up syntax analysis is shift-reduce parsing. LR grammars are the largest class of grammars for which corresponding shift-reduce parsers can be constructed. Representative forms include LR(0), SLR, LR(1), and LALR.

The JavaScript syntax analysis discussed here uses recursive descent. It is suitable for handwritten parsers and is relatively simple. Recursive descent imposes some restrictions on the grammar, but it is still a mainstream parsing approach because it can be highly controlled by developers and has advantages in producing error messages.

Syntax Tree Nodes

Before diving into the details of the syntax tree, let’s first look at its nodes:

High-resolution version

The diagram contains most nodes in the syntax tree. The most important nodes are clearly ExpressionNode and StatementNode, and most nodes in the diagram inherit from one of them.

  • StatementNode: a basic statement node. Its child nodes mainly describe language structures:
    1. Sequential structures, such as ClassDeclNode and DeclarationStateMentNode.
    2. Conditional structures, such as IFElseNode and SwitchNode.
    3. Loop structures, such as WhileNode, ForNode, and DoWhileNode.
    4. Another major node is ScopeNode, which describes scope regions.
  • ExpressionNode: an expression node. Its child nodes mainly describe different expressions:
    1. ConstantNode, a constant node, from which string, boolean, integer, and floating-point nodes are derived.
    2. BinaryOpNode, a binary operator node, from which addition, subtraction, multiplication, division, modulo, left shift, right shift, and similar operator nodes are derived.
    3. There are also regular-expression nodes, this nodes, super nodes, and so on.

Node Memory Management

ParserArenaFreeable and ParserArenaDeletable

From the diagram, most Node classes eventually trace back to ParserArenaFreeable. This class overloads C++’s new operator to implement its own memory-management strategy instead of relying on the default new and delete object mechanism.

If you are familiar with C++, you will notice that this is very similar to placement new/delete. It repeatedly uses a larger dynamically allocated memory block to construct objects of different types, or arrays of those objects. For example, it can first allocate a sufficiently large character array, then construct objects or arrays on top of it as needed. It does not worry about allocation failure during object construction because it does not allocate memory at that point; it only calls the object’s constructor.

  • ParserArenaFreeable objects are freed when the arena is deleted.
  • Destructors are not called. Clients must not call delete on such objects.

Therefore, if a node inherits from ParserArenaFreeable, do not implement cleanup logic in its destructor. Even if you write one, it will not be called.

There is also ParserArenaDeletable, which is similar to ParserArenaFreeable, except that its destructor can be called. If a node needs its destructor to run and perform release logic, it can inherit from ParserArenaDeletable.

  • ParserArenaDeletable objects are deleted when the arena is deleted.
  • Destructors can be called. Clients must not call delete directly on such objects.

After all this, it may still feel confusing. Why does an ifStatement need to be so complex? Why so many stacks? Why so many loops?

  • First, what is the purpose of the final while (!exprStack.isEmpty()) loop?

As shown in the diagram, its purpose is to transform if ... else if ... else if ... else into a standard if ... else structure, making it easier for the syntax tree to process.

  • Second, why does if (!trailingElse) need special handling when there is no final else?

With the first point as context, this becomes easier to understand. It converts the non-standard if ... else if ... else if structure, which does not contain a final else, into a standard if ... else if ... else if ... else structure, so the loop in the first point can handle it uniformly.

SwitchNode

parseSwitchStatement

Most of the logic can be understood from the comments. The puzzling part is that case clauses are parsed twice:

The reason is that in switch syntax, the position of default is uncertain. It may appear at the beginning, at the end, in the middle, or may not exist at all. It effectively splits all case clauses in the switch into two halves. To avoid letting default interrupt a single case-parsing loop, JavaScriptCore performs two passes: one before default and one after it. The logic is clear and easy to understand.
