Preface

I originally thought two articles would be enough to finish the analysis of bytecode generation. In the end, the length grew too much, so I split the topic into three parts: upper, middle, and lower. This is the final article in the bytecode-generation series.

Note: if some explanations feel unclear, please also read the comments in the code.

ExpressionNode

Continuing from the middle part, this article analyzes bytecode-generation details for several ExpressionNode subclasses. Compared with StatementNode, ExpressionNode involves more detailed bytecode instructions.

ConstantNode

The bytecode generation for a constant node directly calls emitLoad and tries to load that constant.

Here emitLoad does not pass the third parameter, because the default value is SourceCodeRepresentation::Other.

emitLoad first calls addConstantValue to add the constant, then calls emitMove to move the return value into the destination register.

The implementation of emitMove is very straightforward: op_mov dst src.

Now let’s explain FirstConstantRegisterIndex:

Register numbers used in bytecode operations have different meanings according to their ranges:

  • 0x80000000-0xFFFFFFFF: negative indices from the CallFrame pointer are entries in the call frame. See JSStack.h.
  • 0x00000000-0x3FFFFFFF: forward indices from the CallFrame pointer are local variables and temporaries in the function call frame.
  • 0x40000000-0x7FFFFFFF: positive indices from 0x40000000 specify entries in the constant pool on the CodeBlock.

Clearly, this bytecode generation is closely related to CodeBlock, so it uses the third range.

ThisNode

The this keyword in JavaScript is rather strange. It means different things in different contexts. Do you still remember the first time you were dominated by this?

  • In the global environment, this always points to the global object, such as window, regardless of strict mode.
  • Inside a normal function, this differs between strict and non-strict mode. In non-strict mode, it points to the global object by default. In strict mode, it is undefined.
  • Inside an object method, this points to the object that calls the method.
  • Inside a constructor, this is bound to the newly created object.
  • An arrow function does not bind this; it captures the this value from its defining context.

There are two points to explain.

  • Because arrow functions do not bind this, some arrow functions need to load this and super, especially inside constructors.

In the example below, before calling eval in the constructor, this needs to be loaded. Although super represents the constructor of parent class A, it returns an instance of subclass B; the this inside super is therefore B. So super() is equivalent to A.prototype.constructor.call(this), and this must be loaded in advance.

  • Temporal Dead Zone: ES6 specifies that if a block contains let or const, then the variables declared by those commands form a closed scope from the beginning of that block. Using those variables before declaration throws an error. In short, before a variable declared with let is initialized, it is unavailable. This is called the temporal dead zone, or TDZ. Here, before using this, JavaScriptCore also needs to check whether the object represented by this is in a TDZ state.

SuperNode

Now let’s look at how bytecode is generated for the super keyword.

super can only be used inside a class. Calling it outside a class causes an error because JavaScript has no way to know which parent constructor it refers to. It is essentially syntactic sugar. JavaScript inheritance is still prototype-based, and super is fundamentally a form of constructor borrowing.

A subclass must call super inside its constructor; otherwise, creating an instance throws an error. This is because the subclass does not have its own this object at first. It inherits the parent class’s this object and then modifies it. Without calling super, the subclass cannot obtain this.

EqualNode

EqualNode is a subclass of BinaryOpNode, and their bytecode-generation ideas are basically the same.

The key method is emitEqualityOp, which is responsible for two kinds of equality checks:

  • Whether the values have the same type.
  • Whether the values are equal.

DotAccessorNode

In JavaScript, method and property access through dot syntax is represented by the dot operator.

The bytecode detail is worth noting: it includes op_get_by_id_with_this. Dot access is essentially loading a property or method name. Also, when loading for the first time, that property or method may not exist yet, so addConstant is called to add it.

ClassExprNode

Class-expression nodes in JavaScript are relatively complex.

The classic ES5 inheritance approach is combination inheritance: use the prototype chain to inherit methods and constructor borrowing to inherit properties.

ES6 is also based on this idea, but it wraps the behavior in a cleaner and more elegant API. It makes JavaScript increasingly powerful, adjusts several property references, standardizes inheritance operations, and separates inheritance implementation from instance construction.

Pay attention to the two lines below:

They implement JavaScript’s typical combination inheritance, where Sub inherits from Base:

In ES6, subclass inheritance of parent-class properties is implemented so that when constructing an instance, the subclass obtains its properties directly, without having to look them up on the prototype. ES6 static methods and static properties, which can only be accessed on the constructor, are also implemented through direct class inheritance. Ordinary reusable methods still live on the prototype chain; the principle and implementation are the same as ES5.
