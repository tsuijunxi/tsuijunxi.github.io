JSVirtualMachine

An instance of JSVirtualMachine is a complete and independent JavaScript execution environment. It provides the underlying resources needed for JavaScript execution.

This class mainly does two things:

  • Enables concurrent JavaScript execution.
  • Manages memory for bridged JavaScript and Objective-C objects.

Every JSContext belongs to a JSVirtualMachine. Each virtual machine can contain multiple contexts and allows values, namely JSValue objects, to be passed between those contexts.

However, each virtual machine is complete and independent. It has its own heap and garbage collector. The GC cannot handle objects in another virtual machine’s heap, so values created in one virtual machine cannot be passed to another virtual machine.

Even at this point, we still have not fully explained how JSVirtualMachine and JSManagedValue achieve conditional strong retention without creating retain cycles.

Here is my inference:

Objective-C uses ARC for memory management, while JavaScript uses GC. Since we are already looking at JavaScriptCore source code, the GC implementation must exist at this level. In any case, for a JavaScript object to be truly released, the corresponding C++ object’s destructor must eventually be involved; otherwise GC could not work. With that premise, the code above becomes useful. When we use a JSManagedValue object, JMV, to wrap a JSValue object, JV, the JMV does not strongly retain JV; it weakly references it. As long as JMV is still alive, we can find at least one JMV corresponding to JV in m_externalObjectGraph. During garbage collection, this tells the GC not to release JV, even if JV’s reference count may already be zero and it may have become isolated. As long as JV’s memory block has not been released, we can continue accessing it. If at some point no JMV corresponding to JV can be found in m_externalObjectGraph, the GC can reclaim JV’s memory. And throughout this whole process, no retain cycle is created.

Some clues for this can also be seen in scanExternalObjectGraph. If you are interested, take a look at that method.

JSContext

A JSContext object represents a JavaScript execution environment. In native code, we use JSContext to execute JavaScript code, access values defined or computed in JavaScript, and allow JavaScript to access native objects, methods, and functions. It is like a bridge between Objective-C and JavaScript.

JSValue

A JSValue instance is a reference to a JavaScript value. We use JSValue to convert basic data types, such as numbers and strings, between JavaScript and native code. We can also use it to create JavaScript objects that wrap native custom-class objects, or to create JavaScript functions implemented by native methods or blocks.

Every JSValue instance comes from a JSContext, which represents the JavaScript execution environment containing the value. Every JSValue strongly retains its JSContext. As long as any JSValue associated with a specific JSContext is retained, that JSContext stays alive. Other JSValue objects returned by instance methods of a JSValue belong to the same JSContext as the original JSValue.

Every JSValue is indirectly associated, through its JSContext, with a specific JSVirtualMachine that represents execution resources. A JSValue can only be passed to JSValue or JSContext instance methods managed by the same virtual machine. Passing a JSValue from one virtual machine into another virtual machine triggers an Objective-C exception.

JSManagedValue

Objective-C uses ARC, which cannot automatically solve retain cycles and requires manual handling by developers. JavaScript uses GC, where all references are strong references, but the garbage collector can resolve cyclic references. JavaScriptCore is the same: in most cases, we do not need to manually manage memory, but some cases need attention.

  • Do not hold a JSValue inside a native object exported to JavaScript. Every JSValue contains a JSContext, and this relationship can cause a retain cycle and memory leak.

Normally, we use weak for external references used inside a block to avoid retain cycles. But the memory of the JavaScript object corresponding to JSValue is managed and reclaimed by the virtual machine. This approach cannot accurately control the lifetime of the referenced JSValue inside the block. When the block needs to use it, the value may already have been reclaimed by the virtual machine.

Because the reference count of JSValue is zero, it is released too early and does not match our expectation.

Apple introduced conditional strong retention, or conditional retain, and the corresponding class is JSManagedValue.

A JSManagedValue object contains a JSValue. Its conditional-retain behavior allows it to manage memory automatically. The most basic use case is storing a JSValue inside a native object imported into JavaScript.

  • “Conditional retain” means that the managed JSValue is guaranteed to be retained if either of the following two conditions is satisfied: the JSValue can be reached through the JavaScript object graph, or the JSManagedValue can be reached through the native object graph. The relationship can be recorded in the virtual machine through addManagedReference:withOwner:. Conversely, if neither condition is satisfied, JSManagedValue sets its value to nil and releases the JSValue.

JSExport

The JSExport protocol provides a declarative way to export Objective-C instance classes and their instance methods, class methods, and properties to JavaScript code.

How JSExport Works

For every protocol implemented by a class, if the protocol inherits from JSExport, JavaScriptCore exports that protocol’s method and property list to JavaScript.

  • For every exported instance method, JavaScriptCore creates a corresponding method in prototype.
  • For every exported instance property, JavaScriptCore creates a corresponding accessor property in prototype.
  • For every exported class method, JavaScriptCore creates a corresponding JavaScript function on the constructor object.

JavaScript has always been a confusing language. It is dynamic and does not inherently have the concept of classes. Although ES6 introduced the class keyword, that syntax sugar still cannot change the fact that JavaScript is prototype-based.
