Preface

RunLoop is a concept that has already been explained many times. Many excellent developers have written about their own understanding of it, and I have read quite a few of those articles with real admiration, for example:

  • Runloop Knowledge Tree
  • Deep Understanding of RunLoop

Even so, I always felt that my understanding of RunLoop was still a little blurry. The veil had not been fully lifted, especially because a lot of what I knew came from hearing other people explain it.

A RunLoop is essentially a large event-driven loop. Event-driven loops exist in many languages. In pseudocode, it looks like this:

Sometimes I wonder: if I tried to implement a simple, homemade version of RunLoop based on my own learning and understanding, what should it look like?

  • Since a RunLoop is, well, a loop, the first thing should be an endless loop.
  • It should also have its own event queue. Whenever an event occurs, the event is pushed into the queue, and each loop iteration takes one event out and handles it.
  • When the queue is empty, the thread running the RunLoop should sleep. When a new event arrives, that thread should be woken up. With my limited knowledge, I can only think of I/O multiplexing as the mechanism that solves this.
  • A RunLoop should distinguish Timer, Observer, Source, and other concepts.
  • …

While collecting references, I unexpectedly found a project called LightWeightRunLoop-A-Reactor-Style-NSRunLoop. It felt exactly like finding what I had been looking for. After reading it carefully, I found that its overall idea matched my own mental model quite well. So in this article, I will use its source code to analyze how a lightweight RunLoop can be implemented. Many thanks to the author, wuyunfeng.

Overall Structure

LightWeightRunLoop implements several RunLoop-related APIs, such as PerformSelector, Timer, URLConnection, LWStream, and LWPort. The goal of this article is not to explain how to use these APIs, but to understand how they are implemented internally, and use that to deepen our understanding of RunLoop.

LWMessageQueue Initialization

Two important things happen here:

  • It defines a LWNativeRunLoop, which is related to the kernel mechanism mentioned earlier: I/O multiplexing. LWNativeRunLoop is the core of LWRunLoop, and it is the foundation that lets this loop actually run.
  • It observes changes to the RunMode. Once the mode changes, it calls LWNativeRunLoop to wake up the kernel.

Enqueuing Messages in LWMessageQueue

The enqueue method takes two parameters: the message itself and the time when the message should fire. The storage structure is a linked list. First it looks at the head of the list.

  1. If the head is empty, or if the new message should fire earlier than the current head, the new message becomes the head.
  2. Otherwise, it walks the linked list and finds the first message whose firing time is later than the new one, then inserts the new message before it.

Finally, if the current thread is blocked, it calls nativeWakeRunLoop to wake it up.

Dequeuing Messages from LWMessageQueue

First, it obtains the messages that need to be handled from nativeRunLoopFor.

  1. If there is no message, it marks the current thread as blocked.
  2. If the message matches the current thread’s RunMode, it checks its firing time. If the firing time is less than or equal to the current time, it removes the message from the queue and returns it. Otherwise, it simply sets nextWakeTimeoutMillis as the wake-up timeout.
  3. If the message does not match the current RunMode, it stores that message in a separate queue for messages that missed the current mode, so it can be used later when the RunMode changes.

The Magical nativeRunLoopFor

The key method nativeRunLoopFor appears many times above. Let’s focus on it:

For now, we only care about the _mReadPipeFd file descriptor. Once it matches, nativePollRunLoop is called:

In nativePollRunLoop, the data read into buffer is simply discarded. Some people may ask: why do something that looks unnecessary?

Think about it this way: if one end of a pipe has data to read, then data must have been written to the other end:

See it? The method name says exactly what it does.

Before a monitored file descriptor becomes ready, or before the timeout expires, kevent keeps the thread blocked, or asleep, so it no longer consumes CPU time. That means we do not care what data is actually sent or received through the pipe. What matters is that this write-and-read action directly wakes the RunLoop, allowing it to continue processing messages. With kevent handling blocking sleep, and with the pipe used here for wake-up, though other wake-up mechanisms are also possible, a thread’s RunLoop takes shape.
