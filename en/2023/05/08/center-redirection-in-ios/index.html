Center Redirection in iOS

Posted on 2023-05-08 | In OC
Words count in article: 87k | Reading time ≈ 5:17
中文 / English

Background

Center redirection, as the name suggests, means routing certain flows to one central point, performing some aspect-oriented work there, and then returning to the original downstream flow. In a sense, center redirection is very similar to Hook in iOS, but they are not the same thing: center redirection must have a center, while a Hook may not.

This article explains the idea through several examples.

How do you write iOS with JS syntax?

If you have used JSPatch, the following code should look familiar. It looks a lot like iOS, but it is actually JS syntax. The reason this writing style works is deeply related to center redirection.

Brute-force mapping

According to JS behavior, if we want UIView.alloc() to work, the only possible way is to add an alloc method to the UIView object. Otherwise the call cannot succeed. In JS, calling an undefined property or variable immediately throws an exception.

So to make the call succeed, the class name is passed into OC; OC uses runtime APIs to find all methods of that class and returns them to JS; then the JS class object generates a function for every method name. Each generated function simply takes the method name and asks OC to call the corresponding method. The generated UIView object roughly looks like this:

This not only requires enumerating all methods on the current class, but also walking up the superclass chain all the way to the root. Every method in the inheritance chain has to be added to the JS object. A single class can have hundreds of methods. Adding all of them to every JS object causes serious memory growth and is not usable in practice.

__c redirection

The final JSPatch solution is: when a nonexistent method is called, forward it to a specified function. Before OC executes JS, a regex rewrites all method calls into calls to the __c() function, achieving a message-forwarding mechanism similar to OC/Lua/Ruby.

__c is added to the Object prototype, so all objects can call it. It then behaves differently depending on the current object type:

With this design, we no longer need to enumerate object methods in OC, nor store all methods on the JS object. Forwarding is enough to invoke any method. __c seems to provide a meta-function capability: the original function becomes a parameter to this meta-function, which is exactly the charm of center redirection.

Login-check center redirection

Most apps have login functionality. Many actions need to check whether the user is logged in before they run. If the user is logged in, the action can continue; otherwise the app must jump to login first. Business code often ends up looking like this:

This style has two problems:

  1. The thing the user wanted to do is interrupted. After login, the app will not automatically continue that action, so the user has to trigger it again. This is especially serious in paid flows.
  2. Login checks are scattered everywhere, making the code bloated. Once the API or login strategy changes, every call site has to be modified, which is hard to maintain.

How do we solve this? Let’s try center redirection: hand the complex decision logic to a proxy, redirect all places that need login checks to that proxy, and use NSProxy, which is naturally designed for forwarding on iOS.

Call flow

The original login-check flow can now be written very simply:

  1. loginProxy records the current target, which is self here.
  2. Since loginProxy does not implement the target method doSomethingNeedLogin, forwarding goes through forwardInvocation.
  3. Inside forwardInvocation, the proxy checks login state. If already logged in, it directly invokes the invocation.
  4. Otherwise, it uses AccountManager to add the target to the one-time observer collection, then presents the login flow.
    • If login succeeds, AccountManager triggers doSomethingNeedLogin through [invocation invokeWithTarget:target], then removes target from the one-time observer collection.
    • If login fails, target is removed directly and doSomethingNeedLogin is not triggered.

From this perspective, login center redirection solves both problems mentioned earlier:

  1. The original action is not interrupted; what needed to happen before login continues after login returns.
  2. Login decision logic is centralized in the proxy, while business-side calls become simpler.

How do we center-redirect any Block?

The first example achieved center redirection through script preprocessing. The second example used the natural forwarding capability of the OC language. Is there a more thorough, lower-level form of center redirection that ignores language features?

We know that all OC methods eventually call into the objc_msgSend family, so if we want to redirect OC methods, we only need to hook objc_msgSend. But how do we redirect any single Block?

  1. Although a Block is also essentially an Objective-C object, it does not go through message forwarding. It is called directly, much like a C function.
  2. Different Blocks have different signatures. The number of parameters and return type are uncertain. Redirecting arbitrary Blocks is therefore very difficult to solve purely at the Objective-C language level.

After some research, I found that the center-redirection assembly framework TrampolineHook can intercept a specified function and receive a callback notification when the function is invoked. It is a center-redirection framework where you do not need to care about the underlying architecture’s calling convention, context saving and restoring, or the strange crashes traditional Swizzle solutions can introduce in large projects.

Can that mechanism be used for Block redirection? Research shows that it can. I decided to use its underlying principle to implement a Block redirection framework named TrampolineBlockHook, supporting both arm64 and x86_64.

vm_remap

Principle

iOS restricts us from creating writable and executable memory directly, but vm_remap can indirectly bypass this limitation.

On Darwin, vm_remap() provides support for mapping an existing code page at new address, while retaining the existing page protections; using vm_remap(), we can create multiple copies of existing, executable code, placed at arbitrary addresses.

vm_remap lets a memory page inherit the properties of the page being mapped. If the mapped page is executable, the newly created page naturally has executable permission too. With vm_remap, we can create multiple copies of executable code and place them at arbitrary addresses.

As shown in the figure from Implementing imp_implementationWithBlock(), we can write an executable Trampoline Page beforehand and create runtime copies through vm_remap: Trampoline Page Copy #1 and Trampoline Page Copy #2, which are used to execute code.

However, this only solves half the problem. Each Trampoline Page may contain multiple Trampoline Entrys. Every redirected Block has one corresponding Trampoline Entry. But those entries need associated information, such as the original Block address and the addresses of the before/after stubs. That information must be configured in the corresponding Trampoline Data page.

If the Trampoline Data page is mapped next to the Trampoline Page, we can use PC-relative addressing to load the needed data from the adjacent page. As shown below, if a Trampoline Entry in Trampoline Page Copy #1 needs some information, it can load it from the corresponding position in Trampoline Data #1.

Code practice

Here we allocate two continuous pages through vm_allocate, release the second page through vm_deallocate, and finally use vm_remap to map trampoline_page into the second page. This gives us the two pages we need: the first page is empty and stores data such as the Block address and stub addresses like pre and post; the second page maps all dynamically executable addresses. In the diagram, the first page is the trampoline data page, and the second page is the trampoline text page.

Careful readers may notice a chunk of code named tramp dispatch before the first tramp entry1. Its size determines the offset of tramp entry1. There are two ways to calculate this size: compute it manually, or use a tool such as Hopper.

Block structure representation

To redirect arbitrary Blocks without caring about parameters or return types, we need a structure to describe a Block. We can use Block_layout from https://github.com/apple-oss-distributions/libclosure/blob/main/Block_private.h.

Flow-jump logic

  1. Take the address A of the Block we want to replace and save it.
  2. Redirect this Block to a dynamically allocated executable address B.
  3. When this Block runs, it jumps to executable address B.
  4. After some operations, B can retrieve the previously saved address A.
  5. Before jumping back to address A, it jumps to the pre stub to do some work.
  6. It jumps to address A and executes the original logic.
  7. After the original logic finishes, it jumps to the post stub to do more work.

In the redirected jump flow, we need the pre stub and post stub information for the Block. Those addresses are configured in the data page, so we need to fill them in during redirection.

The red area in the original diagram represents one tramp data block. It contains five slots, storing ReplacedBlock, tramp, ReplacedBlock->invoke, pre, and post in order.

We also need to point the original Block’s invoke pointer to the tramp entry in the code area, so execution jumps there when the Block runs. To support unhooking, we need to save the original Block implementation. The layout->descriptor->reserved field is a convenient place to store it.

arm64 assembly implementation

The most important part is how these jumps are handled in assembly.

Registers

A quick review of arm64 registers:

Assembly code

On arm64, one page is 0x4000, or 16 KB, so .align 14 is used. On arm64, every instruction is 4 bytes regardless of length.

Now let’s explain the flow line by line:

  1. Since the Block is redirected to a tramp entry, calling the Block jumps to the entry. Assuming this is the first redirected Block, that entry is inside a .rept block repeated 404 times. Why 404? Page size is 16KB = 16384B. Subtract offset 224B, and each tramp entry is 40B, so (16384 - 224) / 40 = 404. One page can hold 404 redirected Blocks.

  2. The tramp entry expands to the following 40 bytes. At this point, lr stores the address after the Block; after the assembly code finishes, we need to jump back there, so we save it into x13. Then we jump to _block_tramp_dispatch. Why add 8 nops? Because each tramp data block is 40 bytes. To make each tramp data correspond exactly to each tramp entry by size and offset, the entry must be padded to 40 bytes. Each instruction is 4 bytes, so we need 10 instructions total.

  1. Because execution jumped from the entry, lr holds the address of the instruction after the branch. lr - 8 gives the start address of the entry, and subtracting one page size #0x4000 gives the corresponding tramp data address.
  1. Store the computed tramp data address on the stack.
  1. x13 currently stores the address after the Block, so store it on the stack as well.
  1. x12 stores tramp data. Offset 24 bytes from that address to get the pre stub. If it is null, jump directly to the block label. Why 24 bytes? During redirection, pre is stored at config[3]; config[0] through config[2] each take 8 bytes, so the offset is 24 bytes.
  1. x13 now holds the pre address, and blr can call it directly. When assembly calls another function, caller-save registers need to be saved and restored around the call.
  1. x12 stores tramp data. Offset 16 bytes gives the original Block implementation address. Load it into x13 and jump. Notice that caller-save registers are not saved and restored here. That is because we need to preserve the same execution context as before redirection. If the original Block returns a value, we want the redirected version to return the same value.
  1. Reload the tramp data address from the stack into x12, then offset 32 bytes to get the post address. The subsequent call is similar to pre. We reload tramp data because the previous block call did not preserve caller-save registers and may have destroyed x12.
  1. Load the address after the Block from the stack into x13, then jump to it.

Hopper diagram

Look carefully: in the left diagram, _block_tramp_dispatch is at 0x0000000000008000, which is the start of a page. In the right diagram, the first tramp entry is at 0x00000000000080e0, so the offset is 0xE0, exactly the 224 mentioned earlier.

Stack alignment pitfall

During debugging, x86_64 often crashed at SSE instructions such as movaps, which looked quite strange.

After investigation, the root cause was stack byte alignment. The document https://jyywiki.cn/pages/OS/manuals/sysv-abi.pdf says:

The end of the input argument area shall be aligned on a 16 (32 or 64, if __m256 or __m512 is passed on stack) byte boundary. In other words, the value (%rsp + 8) is always a multiple of 16 (32 or 64) when control is transferred to the function entry point. The stack pointer, %rsp, always points to the end of the latest allocated stack frame.

The System V AMD64 calling convention requires the stack to be aligned to 16 bytes. In other words, before the call instruction runs, %rsp must be a multiple of 16 (in hexadecimal, the last digit is 0). This alignment exists because modern x86_64 machines introduced SSE and AVX instructions. These instructions support SIMD and greatly improve processing speed, but they require data to be loaded from addresses that are integer multiples of 16.

At the crash point, printing the registers showed that the rbp value involved in the movaps instruction was 0x7ff7bac48f98, which was not 16-byte aligned. Even with offset -0x30, it was still not aligned. Further investigation showed that when saving caller-save registers, an odd number of registers had been pushed, causing the stack address to lose 16-byte alignment.

The fix is simple: push one more register by repeating line 10.

Why not save and restore xmm0~xmm7?

Careful readers may notice that the x86_64 assembly does not save floating-point registers. The current situation is that Xcode reports unsupported syntax, and I have not yet found a good solution.

Thoughts

The TrampolineHook center-redirection mechanism can be used for many things:

  1. Apple’s own imp_implementationWithBlock is implemented based on this technique.
  2. Apple’s famous MainThreadChecker also uses a similar technique.

The TrampolineBlockHook implemented in this article effectively inserts two function stubs around a Block: pre and post. Around these two stubs, many applications are possible. I plan to explore these directions later:

  1. measuring Block execution time,
  2. adding logs to Blocks,
  3. analytics and event tracking.

At the same time, TrampolineBlockHook still has problems, such as multithreading issues and the lack of validation in large projects. These need continuous polishing.

Summary

The center-redirection examples in this article use different technical mechanisms, but the idea is the same. The key lies in how the flow transfer is implemented. This article was written while practicing TrampolineBlockHook, partly as a rough note. When supporting the x86_64 architecture, I indeed hit serious crash issues and took quite a few detours, so this document also serves as a record.
