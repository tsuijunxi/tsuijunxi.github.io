Hooking Objective-C Blocks with TrampolineHook on iOS

Posted on 2023-05-08 | In OC
Words count in article: 2.3k | Reading time ≈ 8 mins.
中文 / English

Background

Instrumentation often needs a single interception point: execution is redirected through shared logic, some work is performed before or after the original call, and control then returns to its normal path. This resembles a conventional hook, but the emphasis here is on routing many call sites through the same trampoline.

Hooking an Objective-C block

Most Objective-C method dispatch eventually passes through one of the objc_msgSend variants, so method interception can be framed as hooking those entry points. Blocks are different: how can we intercept one arbitrary block invocation?

  1. Although a block is an Objective-C object, invoking it does not go through message forwarding. Its function pointer is called directly, much like a C function.
  2. Blocks can have different signatures, parameter counts, and return types. A general-purpose interception mechanism is therefore difficult to implement purely in Objective-C.

TrampolineHook provides a useful model. It redirects a function through an assembly trampoline and invokes callbacks when that function runs. Callers do not have to manage architecture-specific calling conventions or save and restore the execution context themselves. This also avoids some of the fragility that method-swizzling-based instrumentation can introduce in large codebases.

The same mechanism can be applied to blocks. Based on that idea, I built TrampolineBlockHook, a block interception framework that supports both arm64 and x86_64.

vm_remap

Principle

iOS does not generally allow an application to allocate memory that is both writable and executable. vm_remap offers a different route: prepare executable code in advance, then map copies of that code into the required virtual address range.

On Darwin, vm_remap() provides support for mapping an existing code page at new address, while retaining the existing page protections; using vm_remap(), we can create multiple copies of existing, executable code, placed at arbitrary addresses.

The remapped page retains the protection attributes of the source mapping. If the source page is executable, its mapped copies are executable as well. This lets us create multiple instances of a prebuilt trampoline page at addresses selected at runtime.

As illustrated in Implementing imp_implementationWithBlock(), we can build an executable Trampoline Page ahead of time and use vm_remap to create runtime copies such as Trampoline Page Copy #1 and Trampoline Page Copy #2.

That solves only half of the problem. A Trampoline Page contains multiple Trampoline Entry slots, one for each hooked block. Every entry also needs metadata: the original block address and the addresses of its before and after stubs. We store that metadata in a corresponding Trampoline Data page.

If the Trampoline Data page is mapped next to the Trampoline Page, we can use PC-relative addressing to load the needed data from the adjacent page. As shown below, if a Trampoline Entry in Trampoline Page Copy #1 needs some information, it can load it from the corresponding position in Trampoline Data #1.

Mapping the code and data pages

We first allocate two contiguous virtual memory pages with vm_allocate, release the second page with vm_deallocate, and then map trampoline_page into that address using vm_remap. The first page remains writable and stores metadata such as the block address and the pre and post stub addresses. The second page contains the executable trampoline entries. In the diagram, these are the trampoline data page and the trampoline text page, respectively.

The generated page begins with tramp dispatch, followed by the first tramp entry. Because the dispatch routine determines the entry’s offset within the page, we need its exact size. We can calculate that size manually or inspect the assembled output in a tool such as Hopper.

Representing a block

To intercept blocks without knowing their parameters or return types, we need access to their runtime representation. Apple defines the relevant Block_layout structure in Block_private.h.

Control-flow redirection

  1. Save the original block implementation address as A.
  2. Point the block’s invoke function at a dynamically mapped trampoline entry, B.
  3. When the block is invoked, execution branches to B.
  4. The trampoline retrieves the metadata associated with that entry, including the saved address A.
  5. If a pre stub is present, call it before the original implementation.
  6. Call the original implementation at A with the original execution context.
  7. When it returns, call the post stub and then resume the caller’s control flow.

The trampoline needs the block’s pre and post stub addresses while redirecting control flow. We therefore write those addresses into the data page when installing the hook.

The red area in the diagram represents one tramp data record. Its five slots store ReplacedBlock, tramp, ReplacedBlock->invoke, pre, and post, in that order.

We then point the block’s invoke function at the corresponding tramp entry, causing future invocations to enter the trampoline. Removing the hook requires the original implementation address, which this implementation stores in layout->descriptor->reserved.

arm64 assembly implementation

The critical part of the implementation is preserving the calling context while assembly redirects control flow through the trampoline.

Registers

The following register roles are relevant to the trampoline:

Assembly code

On arm64, one page is 0x4000, or 16 KB, so .align 14 is used. On arm64, every instruction is 4 bytes regardless of length.

The dispatch sequence works as follows:

  1. Because the block’s invoke function points at a tramp entry, calling the block branches directly to that entry. The entries are generated by a .rept block repeated 404 times. A page contains 16 KB = 16384 B; after subtracting the 224 B dispatch area, the remaining space holds (16384 - 224) / 40 = 404 entries of 40 B each.

  2. Each tramp entry occupies 40 bytes. At entry, lr contains the return address following the block call, so we preserve it in x13 before branching to _block_tramp_dispatch. The eight nop instructions pad the entry to 40 bytes, matching the size and offset of its tramp data record. Since every arm64 instruction is 4 bytes, each entry contains ten instructions in total.

  1. Because execution jumped from the entry, lr holds the address of the instruction after the branch. lr - 8 gives the start address of the entry, and subtracting one page size #0x4000 gives the corresponding tramp data address.
  1. Store the computed tramp data address on the stack.
  1. x13 currently stores the address after the Block, so store it on the stack as well.
  1. x12 stores tramp data. Offset 24 bytes from that address to get the pre stub. If it is null, jump directly to the block label. Why 24 bytes? During redirection, pre is stored at config[3]; config[0] through config[2] each take 8 bytes, so the offset is 24 bytes.
  1. x13 now holds the pre address, which blr calls directly. Because this is a nested function call, caller-saved registers must be preserved around it.
  1. The original block implementation is stored 16 bytes into the tramp data record. Load it into x13 and branch to it. Caller-saved registers are deliberately left untouched here so that the original block receives the same execution context it would have received without the hook. Its return value must likewise pass through unchanged.
  1. Reload the tramp data address from the stack into x12, then offset 32 bytes to get the post address. The subsequent call is similar to pre. We reload tramp data because the previous block call did not preserve caller-save registers and may have destroyed x12.
  1. Load the address after the Block from the stack into x13, then jump to it.

Hopper diagram

In the left diagram, _block_tramp_dispatch begins at the page boundary 0x0000000000008000. In the right diagram, the first tramp entry begins at 0x00000000000080e0. The resulting 0xE0 offset is the 224-byte dispatch area described above.

Stack alignment pitfall

During debugging, the x86_64 implementation repeatedly crashed on SSE instructions such as movaps.

The root cause was stack alignment. The System V AMD64 ABI specifies:

The end of the input argument area shall be aligned on a 16 (32 or 64, if __m256 or __m512 is passed on stack) byte boundary. In other words, the value (%rsp + 8) is always a multiple of 16 (32 or 64) when control is transferred to the function entry point. The stack pointer, %rsp, always points to the end of the latest allocated stack frame.

The System V AMD64 calling convention requires 16-byte stack alignment at a function-call boundary. Immediately before call, %rsp must be a multiple of 16. Some SIMD instructions, including aligned moves such as movaps, rely on correctly aligned memory operands.

At the crash site, the rbp value used by movaps was 0x7ff7bac48f98, which was not 16-byte aligned; applying the -0x30 offset did not restore alignment. The trampoline had pushed an odd number of caller-saved registers, shifting the stack away from the required boundary.

The fix is to push one additional register, as shown by the repeated instruction on line 10.

Why not save and restore xmm0-xmm7?

The x86_64 implementation does not currently preserve the floating-point registers. Xcode’s assembler rejected the syntax I tried, and I have not yet found a satisfactory solution. This remains a known limitation.

Thoughts

Trampoline-based interception appears in several runtime techniques:

  1. Apple’s own imp_implementationWithBlock is implemented based on this technique.
  2. Apple’s famous MainThreadChecker also uses a similar technique.

TrampolineBlockHook effectively inserts two function stubs around a block: pre and post. Those interception points enable several useful forms of instrumentation that I plan to explore:

  1. measuring block execution time,
  2. adding logs to blocks,
  3. analytics and event tracking.

TrampolineBlockHook still needs more work, particularly around thread safety and validation in large production codebases.

Summary

Although the examples in this article use different low-level mechanisms, they share the same core idea: route control flow through a trampoline while preserving the original calling context. Building TrampolineBlockHook made the ABI details concrete, especially on x86_64, where stack alignment caused failures that were initially difficult to diagnose. This article records both the resulting design and the debugging path that led to it.
