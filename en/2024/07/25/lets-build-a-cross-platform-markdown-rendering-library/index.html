Let's Build a Cross-Platform Markdown Rendering Library for iOS and Android

Posted on 2024-07-25 | In C++ / OC / Java
Words count in article: 5.2k | Reading time ≈ 19 mins.
中文 / English

Background

As ChatGPT-style products became common, many apps started integrating AI responses into chat interfaces. Those responses are usually returned as Markdown, so mobile clients need reliable Markdown rendering support. A quick survey showed three practical constraints:

  1. Many existing solutions are based on WebView, which can be expensive on mobile.
  2. On iOS, CocoaMarkdown is one of the few native rendering libraries, but its feature coverage and extensibility are limited.
  3. On Android, Markwon has a solid architecture, but it is Android-only.

That led to a native cross-platform renderer with a shared C++ core and thin platform adapters for iOS and Android. In this article, uppercase Markdown refers to the SDK, while lowercase markdown refers to the syntax.

Library overview

Markdown is an embeddable native rendering library for iOS and Android. It supports standard Markdown syntax together with a selected set of HTML elements. The current implementation targets those two platforms, with no additional adapters planned for now.

Implementation

Cross-platform foundation

Rendering eventually touches platform UI APIs, while the reusable parts of the problem, parsing and layout, are a better fit for portable C++. The design works by placing abstract drawing interfaces between those two worlds.

The C++ core lays out and paints content against abstract canvases, brushes, fonts, and views. Each platform adapter binds those interfaces to its native graphics stack only when measurement or drawing is required.

The advantages are:

  1. Both platforms can produce almost identical rendering results.
  2. Both platforms only need to develop and maintain one copy of the core logic.
  3. The portable core leaves room for additional platform adapters.

Of course, it also has drawbacks:

  1. The implementation requires solid C/C++ experience, and the learning curve is steeper than it is for most platform-native UI frameworks.
  2. The abstraction boundary hides some conveniences that native UI frameworks normally provide out of the box.

Architecture

The engine is divided into a platform-independent core and a thin platform layer:

  1. The blue area is the C++ core, responsible for parsing Markdown and producing layout and drawing operations.

    1. The third-party library md4c performs the actual markdown parsing.
    2. NodeTree, AtomTree, and BoxTree form the engine’s three-stage representation.
    3. Graphics2D and its supporting interfaces provide the platform-neutral drawing surface.
    4. BoxBreaker contains the line-breaking and layout rules.

  2. The orange area contains the iOS and Android adapters.

    1. The iOS adapter is implemented in Objective-C++.
    2. The Android adapter uses Kotlin and JNI.

A future Flutter adapter could call the C++ core directly through Dart FFI rather than routing rendering through iOS or Android platform channels.

Building the Node tree

Why md4c?

There is no reason to write another Markdown parser from scratch. I chose md4c for four practical reasons:

  1. It conforms to CommonMark 0.30.
  2. It parses quickly.
  3. It is simple to use.
  4. It is portable.

Qt also uses md4c for Markdown parsing.

How to build the node tree

A stack turns md4c’s callback stream into a tree:

  1. enterBlock or enterSpan starts a node and pushes it onto the stack.
    1. The first node becomes mRootNode and never changes.
    2. mCurrentNode points to the stack top. A newly parsed node is attached to it, then becomes the new current node.

Using an unordered list as an example:

  1. leaveBlock or leaveSpan completes the current node. The parser pops it, restores mCurrentNode to its parent, and verifies that the closing callback matches the node being removed.
  1. foundText creates a leaf node and attaches it directly to the node at the top of the stack.

When md4c finishes, mRootNode owns the complete syntax tree.

How to handle HTML tags

Markdown may also contain inline HTML:

  1. md4c reports each HTML fragment as text rather than exposing its structure. A second parser must distinguish opening, closing, and self-closing elements such as <img/> and <br> and update the node stack accordingly.
  2. That parser must also extract element attributes.

HtmlTagParser handles that second parsing pass.

Building the Atom tree

After recursive descent produces the syntax tree, the engine converts it into an Atom tree. Most Node types map to an Atom, although the relationship is not strictly one-to-one.

Atom assembly rules

Atoms preserve the hierarchy of the syntax tree. A node usually produces either one Atom or a RowAtom containing several children, and those children may themselves contain nested atoms.

Layout

The previous stages produce an n-ary Box tree in the C++ core. Before those boxes can be painted onto the abstract canvas, the layout engine must assign each one a final position.

Streaming Box splitting

Markdown content follows a flow layout, but every line has a finite width. The first layout problem is therefore deciding where the Box tree can be split to wrap onto the next line.

  3. The orange-red node is the second child, and it has three child nodes: yellow, sky blue, and purple.
  4. The blue node is the third child.

Pre-layout inside block elements

Block elements such as tables, lists, and quotes occupy a full line in the outer flow, but their contents may still wrap internally. They therefore perform an internal layout pass before they enter the outer line-breaking algorithm.

  1. Quote

In the quote example, the gray rule and the gap beside it consume part of the available width. The quote lays out its text against the remaining width, then sizes the rule to the resulting text height.

  1. Table

Table layout is more complex:

  1. Determine the natural width of each column and compare their sum with the available table width:

    1. Calculate the maximum width of each column.
    2. Sum all column widths.
      1. If the columns already fit, keep their natural widths.
      2. Otherwise, shrink them proportionally to fit the available width.
    3. Reflow each cell against its final column width.

  2. Apply the left, center, or right alignment parsed from the Markdown table definition.

Inline alignment

Inline content supports left, right, center, and justified alignment:

  1. For left alignment, calculate the right-side blank space and fill it with a StrutBox.
  2. For right alignment, calculate the left-side blank space and fill it with a StrutBox.
  3. For center alignment, calculate blank space on both sides and fill it with StrutBoxes.
  4. For justified alignment, distribute the remaining width between neighboring boxes.

Layout rules: details matter

Text layout also needs language-aware break rules. Here those rules operate on a nested Box tree rather than a flat character stream, so the engine must preserve semantic groups while searching for break points.

  1. Chinese characters are all potential line-break points.
  2. Punctuation that must avoid line start or line end is not a line-break point.
  3. Consecutive em dashes are not line-break points.
  4. Spaces are line-break points.
  5. English words are not line-break points.
  6. Some English punctuation marks are not line-break points.
Keeping punctuation groups together

The following sequences are treated as indivisible units during line breaking:

  1. Em dashes: ––
  2. Ellipses: …... and ······
  3. Straight double quotes: "xxx", where xxx is one English word.
  4. Abbreviations such as I'm and You're.

MDTextNode groups these sequences before layout so the line breaker sees each one as a single unit.

Line-start and line-end punctuation rules

To keep reading smooth and consistent, most punctuation marks have positional restrictions. Depending on their type, a punctuation mark may be forbidden at the start or end of a line:

  1. Pause marks, commas, periods, colons, semicolons, exclamation marks, question marks, closing quotes, closing brackets, closing book-title marks, hyphens, middle dots, and separators should not appear at the beginning of a line.
  2. Opening quotes, opening brackets, and opening book-title marks should not appear at the end of a line.

Push-out vs prefer-push-in punctuation handling

Both figures are from: https://www.zcool.com.cn/article/ZMTE5NjYwOA==.html#kuak

  1. “Push-out” handling is what most layout systems do. For punctuation that cannot appear at the start of a line, if it is placed at line start, the system pulls one character from the previous line into the current line. This enlarges character spacing on the previous line and interrupts the reading rhythm, as shown on the left.
  2. “Prefer-push-in” handling compresses the punctuation width inside the current line to make room for the comma that otherwise would not fit. This keeps character spacing stable. Only when the punctuation on the current line cannot be compressed enough does it fall back to push-out behavior, as shown on the right.
Leading-space handling

Sometimes whitespace appears at the beginning of a line. In that case, leading whitespace should be removed.

Punctuation width adjustment
Consecutive punctuation

Regardless of the overall text style, when annotation punctuation is adjacent to other punctuation, or when annotation punctuation repeats, spacing should be adjusted to make text more compact and readable. In principle, if two adjacent punctuation marks occupy two character widths, they should be reduced to 1.5 character widths. On that basis, a style may further compress them to one character width. The compression direction should make opening and closing annotation marks stay close to the content they annotate.

The detailed compression rules are:

  1. If a closing annotation mark is followed by an opening annotation mark, another closing annotation mark, a pause mark, comma, period, colon, or semicolon, squeeze it.
  2. If an opening annotation mark is followed by another opening annotation mark, squeeze it.
  3. If a pause mark, comma, or period is followed by an opening or closing annotation mark, squeeze it.
  4. If a semicolon or colon is followed by an opening annotation mark, squeeze it.
Line-start and line-end punctuation compression

When punctuation appears at the start or end of a line, the following spacing rules make the text more compact and readable:

  1. If an opening annotation mark appears at the start of a line, half a Han-character width can be removed from its leading side.
  2. If punctuation that originally occupies one character width appears at the end of a line, half a Han-character width can be removed from its trailing side.

RTL support

Right-to-left languages such as Arabic and Hebrew reverse the direction of both reading and many UI layouts. Since iOS 9, UIKit has supported this through semantic content attributes and direction-aware leading and trailing anchors.

Mirroring an entire window is not sufficient because text glyphs themselves must remain readable. UIKit therefore treats controls such as UILabel and UITextView as non-flippable and applies bidirectional text rules inside them.

The custom renderer must provide the equivalent behavior itself:

  1. Resolve bidirectional text within each paragraph instead of mirroring glyphs.
  2. Mirror the structure and alignment of block elements such as quotes, tables, and lists.

In the diagrams, the left side shows the Markdown engine without processing, while the right side shows the correct display after processing.

Usage
Text

For each paragraph, the engine uses the first character to determine the layout direction. For example, "مرحبا 你好" starts with Arabic, so RTL rules are used. Similarly, "你好 مرحبا" starts with Chinese, so LTR rules are used.

  1. If LTR rules are used, scan each line for RTL ranges and reverse the RTL text inside those ranges.
  2. If RTL rules are used:
    1. Scan each line for RTL ranges and reverse the RTL text inside them.
    2. Scan each line for LTR ranges, and move trailing punctuation and spaces in each LTR range to the beginning of that range.
    3. Use the scanned ranges as units and perform cyclic shifting.
Quote
  1. The gray vertical line should be laid out on the right.
  2. The text inside should be right-aligned as a whole.
List

For lists:

  1. The bullet should be laid out on the right.
  2. The text should be right-aligned as a whole.
Table

For tables:

  1. RTL tables should first be aligned to the right as a whole.
  2. Table columns should also be ordered from right to left. For example, the first numeric column in LTR becomes the third column in RTL.
  3. Alignment rules must also be adapted. Left alignment in LTR becomes right alignment in RTL.

Event interaction

Tap events

Links and other interactive elements need hit testing even though most rendered content has no native control behind it. The engine handles this by storing event metadata on boxes and searching the tree recursively for the box at a touch coordinate.

Binding event information

Interactive nodes carry an AreaInfo object containing the event type and payload. MDHrefNode, for example, attaches that metadata to its atoms, which propagate it to the generated boxes.

Finding event information by coordinate

When a touch arrives, Icon finds the smallest indivisible box containing that point. If the box carries AreaInfo, the renderer forwards the event payload to its delegate.

Region selection

A native rich-text view also needs text selection. Because this renderer owns its layout tree, it cannot delegate selection to UILabel or UITextView; it must map the user’s gesture back to boxes and draw the selected range itself.

Long press to determine start and end points

A long press starts selection. As the gesture changes, the view tracks the anchor and extent; when the gesture ends, those points define the initial selected range.

Modifying start and end points

Afterward, the user can drag either handle to adjust the range.

Determining the region from start and end points

The raw gesture points do not yet define a reliable selection rectangle.

If the start point is sp and the end point is ep, the orange area is the rectangle between them, while the light-green cells represent text boxes. A purely geometric containment test excludes some boxes that users would expect to be selected, so the raw coordinates need to be adjusted before hit testing.

Instead, the engine snaps each endpoint to the box it hits:

  1. Set the top-left coordinate of the start box as the new start point.
  2. Set the bottom-right coordinate of the end box as the new end point.

Multi-line selection needs one more step. Rather than classify every box by line, the engine constructs one enclosing rectangle and subtracts the two corner regions that lie outside the logical range:

  1. S1 is the rectangle spanning the adjusted start and end boxes.
  2. S2 and S3 are the unused corner regions introduced by that rectangle.
  3. A box is selected when it falls inside S1 but outside both S2 and S3.

The same test works for both single-line and multi-line ranges.

Calculating contained elements from a region

After determining the region, the engine walks the n-ary Box tree in preorder and finds the boxes inside it. Their coordinates can then be converted and drawn directly.

Platform-independent interfaces

The renderer isolates platform graphics APIs behind a small set of C++ interfaces. The most important ones are shown below.

Graphics2D

Graphics2D defines the platform-neutral 2D drawing surface:

  1. Draw strings, lines, rectangles, views, and so on.
  2. Apply transformations such as translation, scaling, and rotation.
  3. Set fonts, colors, strokes, and so on.

TextLayout

TextLayout abstracts native text measurement and drawing.

Others

Supporting interfaces include Point2D, Line2D, Rectangle2D, Path, and View.

Platform adaptation

iOS

Objective-C++ integration

The iOS adapter uses Objective-C++, enabled by the .mm file extension, so the same translation unit can call both Objective-C and C++ APIs. The languages remain separate, however: Objective-C syntax cannot invoke arbitrary C++ objects, Objective-C classes do not gain C++ constructors or destructors, and the two class hierarchies cannot inherit from one another.

For a closer look at ownership across that boundary, see Understanding OC/C++ Closures.

Each platform-neutral interface has an Objective-C++ implementation that forwards to the corresponding Apple framework.

Graphics2D_iOS

TextLayout_iOS

TextLayout_iOS uses native text measurement APIs to calculate text bounds and returns a platform-adapted Rectangle2D_iOS.

Binding the renderer

MarkdownView owns both the parsed _icon and the iOS _graphics adapter. During drawRect:, it attaches the current CGContext to _graphics and passes that abstract renderer to paintIcon. C++ virtual dispatch then routes each drawing operation to the iOS implementation.

Android

Layered implementation

The Android adapter crosses the JNI boundary and is therefore split into three layers:

  1. The Kotlin API layer.
  2. The JNI communication layer.
  3. The C/C++ implementation layer.

Each abstract interface has both a C++ adapter (xxx_Android) and a Kotlin counterpart. The C++ side preserves the shared renderer contract, while the Kotlin side calls Android framework APIs; JNI connects the two.

Graphics2D_Android

The call flow is: draw -> markRecord -> JNI -> record -> play -> drawText.

TextLayout_Android

TextLayout_Android calls into the Kotlin side through JNI, uses Android text measurement APIs, and returns the result to the C++ layer.

Binding the renderer

MarkdownView binds the current Android Canvas to Graphics2D, applies display-density scaling, and calls icon.paintIcon.

Customization

Different host apps may need to interpret or present particular nodes in their own way, while the SDK still needs sensible default behavior. The customization layer must support both without coupling the shared engine to one product’s UI.

To achieve this, the host app can provide a native view implementation for a node and inject it into the engine. That view participates in the Markdown layout pass and is later composed with the canvas output.

iOS

Abstract View interface

The first step is to define the View interface. getWidth, getHeight, and getDepth are used for layout, while setX, setY, and getNativeView are used for rendering. All pure virtual methods listed here are necessary.

Define View_iOS

The second step is to implement the View interface. On iOS, View_iOS calls invokeRenderBlockIfNeeded from setX, setY, and getNativeView. This keeps layout and rendering separate: background parsing computes dimensions without touching UIKit, and the native view is created lazily when rendering begins.

Define MDCustomNode_iOS

Following the tree model described earlier, MDCustomNode_iOS is a custom Node. Its getAtom method invokes layoutBlock and creates an MDCustomAtom_iOS. One detail requires care: custom layout needs the node’s content, but that content is assembled from child nodes that are not available when the node is first created. The current implementation therefore extracts content only after the full node tree has been built, and currently supports plain-text children only.

Define MDCustomAtom_iOS

MDCustomAtom_iOS wraps the layout result and creates a View_iOS object with width, height, depth, render block, and attributes.

Layout custom views

During layout, MDCustomAtom creates an MDCustomViewBox, converts the native view size into engine coordinates according to the current environment font size, and returns it as a normal Box.

Draw custom views

When the box is drawn, it sets the native view position and delegates drawing to Graphics2D. Through C++ polymorphism, g2->draw calls the iOS implementation, which adds the native view to its parent view (MarkdownView) through addSubview.

Cell reuse may leave a native view attached to an old parent. Before MarkdownView.drawRect adds it again, the renderer calls [nativeView removeFromSuperview].

Register custom implementation

Suppose the host app wants to render the sup tag as an input field. It can provide layout and rendering callbacks through MarkdownParam.

Android

Abstract View interface

Android implements the same platform-neutral View contract used by iOS.

Define View_Android

View_Android wraps the Kotlin view in mView. Unlike iOS, Android creates that native view before layout and passes it into the wrapper; reproducing the iOS lazy-creation path across JNI would add more complexity and calls than it saves.

Define MDCustomNode_Android

Android uses an MDCustomViewGenerator named mGenerator to measure and create custom views across the JNI boundary.

The generator exposes separate methods for measurement and view creation:

Because the C++ object cannot instantiate an Android View, Kotlin provides the corresponding ICustomViewGenerator implementation. JNI forwards measurement and creation requests between the two generators.

MDCustomViewGenerator and CustomViewGeneratorManager communicate through the same JNI bridge used elsewhere in the adapter.

Define MDCustomAtom_Android

MDCustomAtom_Android wraps the generated Android custom view into View_Android.

Layout custom views

Custom Android views enter the same Box-based layout pipeline as their iOS counterparts.

Draw custom views

Through virtual dispatch, g2->draw reaches the Android adapter, obtains the native view, detaches it from any previous parent, and adds it to the renderer’s root view.

Register custom implementation

Suppose the host app wants to render the sup tag as an input field. It can implement ICustomViewGenerator, return the layout dimensions, create an Android view, and register the generator through MarkdownIconBuilder.

Conclusion

This article used Markdown to explore a broader problem: how to share parsing, layout, and drawing logic across native platforms without giving up platform-specific UI. The three-tree model, virtual graphics layer, and thin adapters are not limited to Markdown; the same architecture can support other structured-content renderers as well.
