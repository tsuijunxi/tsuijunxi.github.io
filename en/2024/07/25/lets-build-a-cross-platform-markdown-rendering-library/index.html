Let's build a cross-platform markdown rendering library

Posted on 2024-07-25 | In C++ / OC / Java
Words count in article: 124k | Reading time ≈ 7:32
中文 / English

Background

When ChatGPT became wildly popular, many apps began to integrate it in the form of a chatbot. TikTok was no exception. Since ChatGPT responses are usually returned as markdown, mobile clients need markdown rendering support. After some research, I found that:

  1. Many solutions are based on WebView, which can be costly on mobile.
  2. On iOS, CocoaMarkdown is one of the few native rendering libraries, but it is not feature-complete enough and is not easy to extend.
  3. On Android, Markwon has a solid architecture, but it is Android-only.

So I decided to build a cross-platform rendering engine suitable for both mobile platforms and named it Markdown. This article explains how to implement a cross-platform markdown rendering library. If you are interested in cross-platform technology, come along for the ride.

To avoid confusion, lowercase markdown refers to the syntax, while uppercase Markdown refers to the SDK.

Introduction

Basic information

Markdown is positioned as a dynamic, cross-platform, embeddable markdown rendering library. It can be embedded into apps on different platforms. Its main purpose is to display markdown syntax text and some html tags embedded in markdown. So far, Markdown has been adapted for iOS and Android; support for other platforms is not yet planned.

Implementation

Cross-platform foundation

First, let’s talk about the foundation of cross-platform rendering. Markdown is a rendering-heavy SDK, so it inevitably needs to interact with UI. C/C++ is not naturally good at UI work; it is better at logical, non-UI tasks. So why is it still possible to implement this in C/C++?

The key is that the C/C++ layer abstracts a series of interfaces. Layout and rendering can then be detached from concrete platform dependencies. The C/C++ layer can complete layout and rendering against a virtual canvas and virtual brushes, while each platform only needs to adapt and bind those interfaces before real layout and drawing happen.

The advantages are:

  1. Both platforms can produce almost identical rendering results.
  2. Both platforms only need to develop and maintain one copy of the core logic.
  3. C/C++ is widely portable and can be extended to other platforms relatively easily.

Of course, it also has drawbacks:

  1. You need to be familiar with C/C++, which is, as everyone knows, not the friendliest language.
  2. Many things must be decoupled from the concrete platform, meaning some platform conveniences are no longer available out of the box.

Architecture

The Markdown engine is mainly composed of a platform-independent layer and a platform-specific layer:

  1. The blue area is the platform-independent layer. It is implemented in C/C++ and is the core of Markdown, responsible for parsing, layout, and rendering of markdown text.

    1. The third-party library md4c performs the actual markdown parsing.
    2. NodeTree, AtomTree, and BoxTree form the important three-tree model.
    3. Graphic2D and its dependent abstract interfaces are also important: together they represent a virtual UI world.
    4. BoxBreaker represents the layout logic, where many tricky details live.

  2. The orange area is the platform-specific layer. Currently, iOS and Android have been adapted.

    1. The iOS platform is implemented with objc.
    2. The Android platform is implemented with Kotlin.

If other platforms are needed in the future, such as Flutter, they can be planned and adapted. Flutter adaptation here does not mean communicating with iOS/Android through traditional Channels; instead, it means using FFI so Dart can communicate directly with C++.

Building the Node tree

Why md4c?

Many open-source projects can parse markdown, so there is no need to reinvent the wheel. After research, I chose md4c as the syntax parser. It has several advantages:

  1. It conforms to CommonMark 0.30.
  2. It parses quickly.
  3. It is simple to use.
  4. It is portable.

The well-known cross-platform UI framework Qt also uses this library to support markdown parsing.

How to build the node tree

The syntax tree is built by following stack push and pop rules:

  1. When enterBlock or enterSpan is called, it means a node starts, so we push a node onto the stack.
    1. The root node mRootNode is the first parsed node and is only updated once.
    2. mCurrentNode is the current top of the stack. Whenever a new node A is parsed, mCurrentNode adds A as a child, and A becomes the new mCurrentNode.

Using an unordered list as an example:

  1. When leaveBlock or leaveSpan is called, it means the node has ended, so we pop the stack. After popping, mCurrentNode must be updated. To keep push and pop behavior consistent, the implementation also performs balance checks.
  1. When foundText is called, it means a leaf node has been parsed. The current stack-top node can add it directly as a child.

This process continues recursively until parsing completes. Finally, the full node tree can be obtained through mRootNode.

How to handle HTML tags

Sometimes html tags are embedded in markdown:

  1. md4c parses them as leaf nodes and does not parse tag parameters. Therefore, tags must be parsed separately, and we need to decide whether to push or pop according to whether a tag is a start tag or an end tag. HTML also has self-closing tags, such as <img/> and <br>, which require extra checks.
  2. md4c does not parse tag attributes either, so attributes also need to be handled separately.

Layout

The previous steps produce a multi-way Box tree. The parsed Boxes all live in the C++ layer, and the C++ layer already has a virtual canvas and virtual brushes. Before drawing, however, layout is needed to determine the final position of each element.

Streaming Box splitting

Normally, markdown elements are laid out in a flow. But the canvas width is limited, so the first problem is how to wrap and split the Box tree according to a given canvas width.

Assume the figure is the Box tree:

  1. The white node is root.
  2. The light-blue node is the first child.
  3. The orange-red node is the second child, and it has three child nodes: yellow, sky blue, and purple.
  4. The blue node is the third child.

Suppose we are laying out the first line. Based on the screen width, the orange-red node must be split. Since it has children, we recurse into it. The yellow node can belong to the current line, while the purple node definitely cannot. The tricky one is the sky-blue node: it is a node with no children, so we need to decide whether it can be split.

Notice that after splitting, the orange-red node disappears. That is because it is a parent/container node and does not occupy real space by itself; its size is fully determined by its children. The more complex case is when the sky-blue node also has children. Then the recursion must continue, so laying out each line may involve deep recursive descent until the line is filled.

Pre-layout inside block elements

Some markdown block elements, such as tables, lists, and quotes, occupy the full width externally and behave as one block. After splitting, they still occupy a full line. But their internal children may also wrap, so these block elements need to lay out their internal children in advance.

  1. Quote

As shown above, take "Quote" as an example. There is a gray vertical line on the far left with the same height as the text. During layout, the line and the whitespace after it must be reserved, so the reserved width is subtracted from the available context width.

  1. Table

Table layout is more complex:

  1. First, determine the width of each column, which determines the whole table width. Sometimes the table is narrower than the given width, while sometimes it exceeds the given width. The column width is determined as follows:

    1. Calculate the maximum width of each column.
    2. Sum all column widths.
      1. If the sum does not exceed the given width, do nothing.
      2. Otherwise, calculate the percentage ratio of each column and multiply it by the given width to obtain the final width of each column.
    3. The content in each table cell must be split according to the current column width.

  2. Each column also has its own alignment rule: left, center, or right. These rules are parsed from markdown syntax.

Inline alignment

For alignment, the content may be left-aligned, right-aligned, centered, or justified. The strategies are:

  1. For left alignment, calculate the right-side blank space and fill it with a StrutBox.
  2. For right alignment, calculate the left-side blank space and fill it with a StrutBox.
  3. For center alignment, calculate blank space on both sides and fill it with StrutBoxes.
  4. For justified alignment, calculate the gap between every two characters and fill with StrutBoxes.

Layout rules: details matter

Like a reading engine, the Markdown engine has many default text layout rules. Unlike ordinary streaming text, however, Markdown text layout always operates on a multi-way Box tree. Enforcing these rules costs more.

  1. Chinese characters are all potential line-break points.
  2. Punctuation that must avoid line start or line end is not a line-break point.
  3. Consecutive em dashes are not line-break points.
  4. Spaces are line-break points.
  5. English words are not line-break points.
  6. Some English punctuation marks are not line-break points.

Prohibition against separating symbols

The following punctuation should be treated as a single unit between lines and must not be split into two lines just to fit wrapping:

  1. Em dashes: ––
  2. Ellipses: …... and ······
  3. Straight double quotes: "xxx", where xxx is one English word.
  4. Abbreviations such as I'm and You're.

The solution is to bind these units early when MDTextNode splits text, so they are treated as one unit during layout.

Line-start and line-end punctuation rules

To keep reading smooth and consistent, most punctuation marks have positional restrictions. Depending on their type, a punctuation mark may be forbidden at the start or end of a line:

  1. Pause marks, commas, periods, colons, semicolons, exclamation marks, question marks, closing quotes, closing brackets, closing book-title marks, hyphens, middle dots, and separators should not appear at the beginning of a line.
  2. Opening quotes, opening brackets, and opening book-title marks should not appear at the end of a line.

Push-out vs prefer-push-in punctuation handling

Both figures are from: https://www.zcool.com.cn/article/ZMTE5NjYwOA==.html#kuak

  1. “Push-out” handling is what most layout systems do. For punctuation that cannot appear at the start of a line, if it is placed at line start, the system pulls one character from the previous line into the current line. This enlarges character spacing on the previous line and interrupts the reading rhythm, as shown on the left.
  2. “Prefer-push-in” handling compresses the punctuation width inside the current line to make room for the comma that otherwise would not fit. This keeps character spacing stable. Only when the punctuation on the current line cannot be compressed enough does it fall back to push-out behavior, as shown on the right.

Leading-space handling

Sometimes whitespace appears at the beginning of a line. In that case, leading whitespace should be removed.

Punctuation width adjustment

Consecutive punctuation

Regardless of the overall text style, when annotation punctuation is adjacent to other punctuation, or when annotation punctuation repeats, spacing should be adjusted to make text more compact and readable. In principle, if two adjacent punctuation marks occupy two character widths, they should be reduced to 1.5 character widths. On that basis, a style may further compress them to one character width. The compression direction should make opening and closing annotation marks stay close to the content they annotate.

The detailed compression rules are:

  1. If a closing annotation mark is followed by an opening annotation mark, another closing annotation mark, a pause mark, comma, period, colon, or semicolon, squeeze it.
  2. If an opening annotation mark is followed by another opening annotation mark, squeeze it.
  3. If a pause mark, comma, or period is followed by an opening or closing annotation mark, squeeze it.
  4. If a semicolon or colon is followed by an opening annotation mark, squeeze it.
Line-start and line-end punctuation compression

When punctuation appears at the start or end of a line, the following spacing rules make the text more compact and readable:

  1. If an opening annotation mark appears at the start of a line, half a Han-character width can be removed from its leading side.
  2. If punctuation that originally occupies one character width appears at the end of a line, half a Han-character width can be removed from its trailing side.

RTL support

RTL stands for right-to-left. It means the writing and reading direction goes from right to left. Common RTL languages include Arabic and Hebrew. Since iOS 9.0, Apple has provided system-level support for RTL UI, mainly through leading and trailing UILayoutGuides that replace left and right in scenarios that need flipping, and through UIView semantic attributes. In an RTL environment, leading means right and trailing means left; in a normal LTR environment, the opposite is true.

Some solutions adapt RTL by mirroring the whole window. But some elements must not be flipped, such as text elements, because text must always face the viewer. Therefore components such as UILabel, UITextView, and YYLabel are, by default, non-flippable elements.

So how should a custom Markdown engine handle RTL?

  1. Markdown contains many text elements, which cannot be flipped, so the engine must handle RTL logic for text itself.
  2. Markdown also contains many other elements, such as quotes, tables, and lists, which must follow RTL rules too.

Usage

Text

For each paragraph, the engine uses the first character to determine the layout direction. For example, "مرحبا 你好" starts with Arabic, so RTL rules are used. Similarly, "你好 مرحبا" starts with Chinese, so LTR rules are used.

  1. If LTR rules are used, scan each line for RTL ranges and reverse the RTL text inside those ranges.
  2. If RTL rules are used:
    1. Scan each line for RTL ranges and reverse the RTL text inside them.
    2. Scan each line for LTR ranges, and move trailing punctuation and spaces in each LTR range to the beginning of that range.
    3. Use the scanned ranges as units and perform cyclic shifting.

Quote

  1. The gray vertical line should be laid out on the right.
  2. The text inside should be right-aligned as a whole.

List

For lists:

  1. The bullet should be laid out on the right.
  2. The text should be right-aligned as a whole.

Table

For tables:

  1. RTL tables should first be aligned to the right as a whole.
  2. Table columns should also be ordered from right to left. For example, the first numeric column in LTR becomes the third column in RTL.
  3. Alignment rules must also be adapted. Left alignment in LTR becomes right alignment in RTL.

Binding event information

When an element needs events, event type and parameters can be bound to the corresponding Box area. For example, create AreaInfo and attach it to the Atoms generated by MDHrefNode; then the Atom passes AreaInfo to the generated Boxes.

When a touch event occurs, the coordinate is passed to Icon. Icon finds the indivisible Box that contains the coordinate and then checks whether the box has bound AreaInfo. If AreaInfo exists, the necessary event information can be thrown to the delegate.

Region selection

As a rich text rendering component, the view naturally needs to interact with users. The most common interaction is region selection. Because this is a custom component, this feature must also be implemented manually. The principle is simple: given a region, if an element falls within it, color it; otherwise, leave it unchanged. The idea is simple, but the implementation is not.

Long press to determine start and end points

Region selection is usually triggered by long press. During the long-press process, the selection state changes. When the gesture ends and is not cancelled, the start and end points can be obtained.

Modifying start and end points

After a region is selected, touch events can still drag the start or end anchor to modify the selected region.

Determining the region from start and end points

Once the start and end points are known, simply using two points to define a region can produce errors.

If the start point is sp and the end point is ep, the orange area is the region between those two coordinate points, while the light-green cells are text boxes. Obviously, if we calculate purely by coordinates, some text boxes are not contained in the region and therefore cannot be selected. But from the user experience perspective, we expect them to be selected. So hard coordinate calculation has clear flaws.

A better approach is: if a point hits a certain box, that box should be considered selected. In this case, the start and end points can be recalibrated:

  1. Set the top-left coordinate of the start box as the new start point.
  2. Set the bottom-right coordinate of the end box as the new end point.

For multiple lines, there is another problem. If the region is artificially split by lines, calculation errors may occur, because some text that should be selected may occupy multiple lines and become hard to classify. Therefore, the final solution is a completion strategy:

  1. Complete the selected area by its top-left and bottom-right corners; this whole area is S1.
  2. Treat the completed extra areas as S2 and S3.
  3. A box is selected if: S1 contains the box && S2 and S3 do not contain it.

This strategy works for both single-line and multi-line selection, and is easy to understand and calculate.

Calculating contained elements from a region

After the region is determined, traverse the Box tree and match boxes. Here, preorder traversal of a multi-way tree is used. After the boxes inside the selected region are found, their coordinates can be converted and drawn directly.

Platform adaptation

iOS

Objective-C/C++ mixed compilation

The iOS platform adaptation is implemented through OC/C++ mixed compilation. As long as the file is named with the .mm extension, OC and C++ APIs can be used in the same file. There are several things to understand about OC/C++: objc++ does not add C++ capabilities to OC classes, nor does it add OC capabilities to C++ classes. For example, you cannot call a C++ object with OC syntax, add constructors or destructors to an OC object, or interchange this and self. The class hierarchies are independent: C++ classes cannot inherit from OC classes, and OC classes cannot inherit from C++ classes.

For more details about OC/C++ mixed compilation, you can refer to my previous WeChat article: Understanding OC/C++ Closures.

Each interface corresponds to an implementation class. Mixed compilation allows OC and C++ to be written together in .mm, which is very direct.

Graphics2D_iOS

Take drawing a string as an example. The implementation looks familiar if you have worked on reading engines.

TextLayout_iOS

TextLayout_iOS uses native text measurement APIs to calculate text bounds and returns a platform-adapted Rectangle2D_iOS.

How to bind?

MarkdownView owns _icon, and _icon.paintIcon needs a Graphics2D parameter. At the same time, MarkdownView holds a _graphics object. Thanks to C++ polymorphism, passing _graphics to paintIcon completes the binding.

Android

Layered implementation

Android adaptation uses JNI to enable communication between Kotlin and C/C++, so it is designed as three layers:

  1. The Kotlin API layer.
  2. The JNI communication layer.
  3. The C/C++ implementation layer.

Unlike iOS, each interface here corresponds to both a C++ implementation class (xxx_Android) and a Kotlin implementation class. This is because Android cannot mix the two languages in the same way. Neither the C++ implementation nor the Kotlin implementation can complete the adaptation alone; they must cooperate through JNI.

Graphics2D_Android

The call flow is: draw -> markRecord -> JNI -> record -> play -> drawText.

TextLayout_Android

TextLayout_Android calls into the Kotlin side through JNI, uses Android text measurement APIs, and returns the result to the C++ layer.

How to bind?

MarkdownView receives the Android Canvas, binds it to Graphics2D, applies density scaling, and finally calls icon.paintIcon.

Customization

Sometimes the business side may interpret and present certain nodes differently. As an SDK, Markdown still needs to follow standard rendering behavior when serving multiple business integrations. So how can this conflict be reduced?

The solution is to provide a way for the business side to supply the implementation UI of a node and inject that implementation into the engine. The injected UI participates in the Markdown layout process and is eventually drawn by the engine onto the canvas.

iOS

Abstract View interface

The first step is to define the View interface. getWidth, getHeight, and getDepth are used for layout, while setX, setY, and getNativeView are used for rendering. All pure virtual methods listed here are necessary.

Define View_iOS

The second step is to implement the View interface. On iOS, View_iOS is defined and the implementation is simple. The only point worth mentioning is that invokeRenderBlockIfNeeded is called in setX, setY, and getNativeView. This allows layout and rendering to happen on different threads. The engine does not want to operate on UI while parsing on a background thread. In fact, no real view is generated during layout.

Define MDCustomNode_iOS

Following the tree model described earlier, MDCustomNode_iOS is defined as a customized Node. Its layout logic is executed inside getAtom through layoutBlock. Then an MDCustomAtom_iOS object is created. Everything looks fine, but there is an easily overlooked issue: content. Custom layout needs concrete content, and content depends on child nodes. When a node is first created, it does not know its children yet. Only after the whole node tree is built can content be extracted from children. The current handling is relatively rough and only supports the simplest text cases.

Define MDCustomAtom_iOS

MDCustomAtom_iOS wraps the layout result and creates a View_iOS object with width, height, depth, render block, and attributes.

Layout custom views

During layout, MDCustomAtom creates an MDCustomViewBox, converts the native view size into engine coordinates according to the current environment font size, and returns it as a normal Box.

Draw custom views

When the box is drawn, it sets the native view position and delegates drawing to Graphics2D. Through C++ polymorphism, g2->draw calls the iOS implementation, which adds the native view to its parent view (MarkdownView) through addSubview.

Because of cell reuse, this implementation can cause problems, so every time MarkdownView.drawRect is called, [nativeView removeFromSuperview] must first remove the native view from its old parent.

Register custom implementation

Suppose the business side wants to treat the sup tag as an input box. It can provide layout and render callbacks and assign them to MarkdownParam.

Android

Abstract View interface

Same as iOS.

Define View_Android

The second step is to implement View. On Android, View_Android holds the real Kotlin view mView. Unlike the lazy-created view on iOS, mView is created outside and passed in ahead of time. The reason is that achieving the same lazy-loading behavior on Android would be much more expensive, so this is a compromise.

Define MDCustomNode_Android

Unlike iOS, which can create views directly through a block, Android first defines an MDCustomViewGenerator object named mGenerator. It is responsible for layout and rendering of custom views.

Since MDCustomViewGenerator lives in the C++ layer and cannot create a real view by itself, the Android layer must also create a real view generator. The real generator implements the required interface methods. The C++ layer and Kotlin layer then communicate through JNI.

Define MDCustomAtom_Android

MDCustomAtom_Android wraps the generated Android custom view into View_Android.

Layout custom views

Same as iOS.

Draw custom views

Through C++ polymorphism, g2->draw eventually calls the Android-side logic, obtains the native view, removes it from the old parent if needed, and adds it to the root view.

Register custom implementation

Suppose the business side wants to treat the sup tag as an input box. It can implement ICustomViewGenerator, return layout dimensions, create an Android view, and register the generator through MarkdownIconBuilder.
