Reading LaTeX with TTS

Posted on 2024-02-02 | In LaTeX TTS
Words count in article: 103k | Reading time ≈ 6:15
中文 / English

Background

The product recently needed to read LaTeX formulas aloud, but the current TTS engine does not understand LaTeX syntax. If we feed raw LaTeX directly into TTS, there will be many pronunciation errors.

After research, there are already some existing solutions:

  • MathJax Speech Converter
  • TeX2Speech

These open-source solutions do not support Chinese well, and their rule systems differ a lot from Chinese speech patterns. They are also non-native solutions, so performance is poor. We therefore decided to add a translation layer before feeding LaTeX into TTS: parse the LaTeX syntax, build a syntax tree, convert the original LaTeX into natural-language text that TTS can read, and then send that text to TTS.

Since the LaTeX rendering engine already parses the syntax and builds the tree, the main job is to walk that existing tree and assemble text according to rules. Because LaTeX has many commands and symbols, the workload is large. This article explains the implementation with both math and chemistry examples, and also covers the tricky parts we hit in practice.

All LaTeX reading logic in this article is for Chinese only.

How it works

Architecture

If you know LaTeX, you probably know that the raw LaTeX text is parsed into an Atom tree, then that Atom tree recursively generates a Box tree, and Box objects are finally rendered through a platform-independent Graphics2D interface.

Since TTS does not involve rendering, we only need to assemble speech text on the Atom tree nodes. During that generation process, we may need to build rules and data tables. The whole speech-text generation pipeline is platform-independent, so this logic can be shared across platforms.

Syntax tree nodes

Because Atom nodes can be nested recursively, the speech assembly process is also recursive. That means every Atom subclass needs to implement the same interface.

Math rules

Unicode

LaTeX contains many Unicode symbols used to express mathematical notation. Many of them cannot be recognized by the TTS engine, so we maintain a dedicated hash table to translate Unicode values into spoken text.

Special symbols

LaTeX also has many dedicated mathematical symbol expressions. The TTS engine either cannot recognize them or pronounces them inaccurately, so we maintain another hash table to translate those dedicated symbols.

When parsing root, the parser does not know that an of command will appear later. According to the parsing rules, it generates two commands: CommandRoot and CommandOf, each with its own arguments. But since this is a combined command, the two commands must work together to render correctly. Therefore, during initialization, CommandOf tentatively checks the previous command. If it is CommandRoot, it steals the argument from CommandRoot and ignores CommandRoot. Finally, CommandOf uses all collected arguments to generate the correct NthRootAtom.

With this design, its TTS text can also be assembled conveniently.

Parameter stealing

Consider this LaTeX text:

Its final rendering is $37^\circ\rm{C}$, while the speech text should be “37摄氏度”.

For rendering, this is simple: draw three adjacent nodes in sequence. But inferring the TTS text is troublesome because the related nodes do not live in the same subtree. During LaTeX parsing, a “command stack” is generated. Normally, commands just pop from the stack in order. But here commands have semantic relationships, so special handling is needed.

When CommandRm closes, it performs several checks:

  1. Pop the top CommandRm and check whether its content is C.
  2. Check whether the current stack top is SubSupCom, with empty sub and sup equal to °.
  3. If both conditions hold, steal the sup from SubSupCom, combine it with the current content C, generate a new SubSupCom, place it in a ContainerAtom, and name it “摄氏度”.
  4. If either condition fails, use the normal pop logic.

Ambiguous readings

Negative or minus?

Some symbols have different readings in different scenarios, so we need rules.

For -, in -b it should be read as “negative”; in (-b) it should also be “negative”; while in a-b it should be read as “minus”. The rule is:

  1. If the previous symbol is empty, read “negative”.
  2. If the previous symbol is a SymbolAtom:
    1. if its content is ( or [, read “negative”;
    2. otherwise read “minus”.
  3. In all other cases, read “minus”.

Similar symbols include:

  1. ±, which has ambiguous readings between plus-minus and positive-negative.
  2. +, which can mean positive or plus.

Dot, multiplication, or dot product?

For ·, sometimes it should be read as “dot”, sometimes as “multiplied by”, and sometimes as “dot product”. The rule is:

  1. If the previous or next symbol is empty, read “dot”.
  2. If both previous and next symbols are vectors, read “dot product”.
  3. Otherwise, read “multiplied by”.

In practice, · can also be combined to form different readings, such as ellipsis or remainder.

Invisible symbols

Sometimes a symbol is missing visually, but the TTS text must still include it.

Take multiplication as an example. For (a+b)(c+d) or 2(a+b), the speech needs to add “multiplied by” between the two parts. The rule is:

  1. If the current symbol is a FencedAtom in the form (xxx):
    1. if the previous symbol is CharAtom, add “multiplied by”;
    2. if the previous symbol is also a FencedAtom in the form (xxx), add “multiplied by”;
    3. otherwise do nothing.
  2. Otherwise do nothing.

Improper fractions

Some structures are logically a whole, but can be rendered independently. For example, the mixed number $3\cfrac{1}{2}$ has LaTeX text 3\frac{1}{2}. The rendering engine parses it into two Atoms: one CharAtom for 3, and one FracAtom for 1/2. For rendering, they can simply be drawn one after another.

But for TTS, they are semantically related. Therefore, when the current Atom is a FracAtom, the engine needs to combine it with the previous Atom and determine whether they may form a mixed number.

Mispronunciation

During testing, some pronunciations were inaccurate. In those cases, we can use the TTS engine’s SSML support to correct pronunciation.

Chemistry rules

Flattening a subtree locally

The TTS reading of chemistry is completely different from math. Chemistry involves recognition of chemical names, chemical equations, ions, and similar concepts, so the existing tree traversal rules are basically not reusable. This means that to support chemical TTS, a completely different framework from the math one is needed.

Most chemical structures are relatively flat, and most molecular formulas do not have very deep hierarchy. They mainly use ScriptsAtom to express subscripts in chemical formulas. Therefore we can locally flatten the tree structure. In other words, when reading ScriptsAtom, do not traverse its child nodes; instead, flatten it into one layer according to a rule.

The rule is: ScriptsAtom has three elements: base, subscript, and superscript. Convert each element to string, prefix subscripts with _, prefix superscripts with ^, and concatenate them.

Recognizing chemical formulas

After flattening, the TTS traversal result for the formula above is H_2, S, O_4. How do we turn these scattered texts into a chemical formula name? Dictionary mapping is one option, but there are several problems:

  1. During traversal, how do we determine that H_2SO_4 is a group?
  2. How do we know whether H_2SO_4 has a corresponding chemical name?
  3. If it has no name, how do we fall back? After all, H_2S also has a name, “硫化氢”.

This problem is very similar to search engines. When you type some characters, search engines can show a list of associated suggestions.

Therefore, we can borrow the search-engine idea and introduce a Trie tree to solve recognition of chemical formula names.

The figure shows a constructed Trie tree of chemical formula names. Every node stores a name, if any, representing the chemical formula on the path from the root to the current node. The search process uses a greedy algorithm:

  1. Input H_2 and reach the red node. Since it has a name, record “氢气”.
  2. Continue input S and reach the green node. It also has a name, so overwrite the name as “硫化氢”.
  3. Continue input O_4 and reach the blue node. It also has a name, so overwrite the name as “硫酸”.

  1. Separate characters with #.
  2. Keep consecutive digits together.
  3. For ScriptsAtom, prefix subscripts with _, prefix superscripts with ^, and keep the whole part as one unit.

Hydrates

In chemistry, many substances crystallize from aqueous solution and combine with a certain number of water molecules. These water molecules are called waters of crystallization. Their reading is usually “x hydrate y”, where x is the number of water molecules and y is the compound name before ·.

  • CuSO4·5H2O: 五水合硫酸铜
  • Na2CO3·10H2O: 十水合碳酸钠

If all hydrates are stored in the table, there are two problems:

  1. They cannot be fully enumerated, so omissions are inevitable.
  2. There is a lot of waste.

If we can extract the number of water molecules in the hydrate, both problems can be solved. We only need to look up the name before · in the data table, and the final chemical name can be determined.

The idea is: during Trie traversal, if the · symbol is encountered, check whether the following substance is number + H2O or just H2O. If so, stop the loop and combine the previously found chemical symbol name y into the final name: x hydrate y.

There are also cases where this rule does not fit naturally. For example, NH3·H2O would become “一水合氨气” under the rule above, which sounds awkward. The correct name is “一水合氨”. For this kind of case, we can add a whitelist: when encountering ·, look up the full form in the table first, and only fall back to the rule if the lookup fails.

Summary

Rome was not built in a day. The ability to generate TTS text for LaTeX cannot be completed overnight either; it still needs long-term human effort and continuous polishing.
