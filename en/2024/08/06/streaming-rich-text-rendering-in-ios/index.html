Streaming Rich Text Rendering in iOS

Posted on 2024-08-06 | In OC
Words count in article: 53k | Reading time ≈ 3:12
中文 / English

Background

When using ChatGPT or other LLMs, the model’s response is streamed out token by token instead of appearing as one complete paragraph. The model has to keep predicting what to output next, and if the client waited until the whole answer was generated before displaying anything, the experience would be poor.

To adapt to LLM streaming output, the client must also support streaming rendering. At the same time, to improve expressiveness, LLM output is usually rich text, such as Markdown or HTML, rather than plain text. Streaming output plus rich text puts real pressure on the client-side rendering capability.

This article discusses how rich text streaming rendering is implemented on the client side in a real business scenario. The rich text here includes both HTML and LaTeX.

How it works

Streaming request

AFNetworking-streaming provides an interface for chunked data responses. In simple terms, one request needs to handle multiple response callbacks and one final completion callback. When data first arrives, headerCallback is triggered once; as the server keeps sending data, dataCallback is triggered multiple times; and when sending ends, the final callback is triggered.

The client receives the data stream through dataCallback and parses it according to the separator agreed with the server.

Pseudo-stream parsing

To support streaming rendering, we first need to support streaming parsing for rich text such as HTML and LaTeX. However, there is no true streaming parser on the client, and implementing a truly streaming parser would involve many difficulties. So the client chose a “pseudo-stream parsing” solution:

Every time the parser receives streamed text, it appends that text to the previously received text and parses everything again from the beginning.

Incomplete tag rules

Rich text has a certain format, which means at any given moment, the streamed text may be incomplete or syntactically invalid. In a non-streaming scenario this would be treated as an error, but in a streaming scenario it is normal. Therefore we need some exception-handling rules:

  1. Closed tags are output, while unclosed tags are swallowed.
    1. <div> is considered closed.
      1. If the text is <div>123, the output is 123.
      2. If the text is <div><span>123</span><b>456, the output is 123**456**.
    2. But <div, <di, <d, and <img src="http:// are incomplete and are swallowed.
  2. Leaf nodes are output normally.

Here, “closed” means the opening half of an HTML tag is complete enough to be considered closed.

Incomplete formula rules

The tex tag is special because its inner text must still be parsed by the LaTeX engine. Therefore whether it is finally output depends on whether the LaTeX text itself is syntactically valid.

  1. <tex>\frac{1}{2} has no </tex>, but the inner text is complete, so it still renders normally.
  2. <tex>\frac{2}{</tex> has a complete tag, but the LaTeX text contains a syntax error, so it is swallowed.

Pseudo-stream rendering

iOS rich text rendering is based on YYText. If we implemented streaming rendering according to the true principle, we would need to heavily modify YYText so that it supports streaming rendering. That cost would be very high, so the client chose pseudo-stream rendering.

Core idea

The core of pseudo-stream rendering can be summarized in one word: “cover”.

Usually, given a piece of rich text, the parser generates an NSAttributedString, and the layout generated by YYLabel is deterministic. We can render everything first, add a mask above YYLabel, and then reveal one grid at a time like a scratch card. This creates the feeling of streaming.

The mask solution is shown in the videos below. Video 1 is the debug version, and video 2 is the normal version.

There is a red horizontal mask and a blue vertical mask. For every streamed character, the red mask shrinks to the right by one character width until the current line has fully streamed. At that point, the red mask moves to the next line, while the blue mask shrinks downward by one line height. During streaming, the loading indicator is always displayed at the leftmost edge of the red mask.

Note: the mask color must match the underlying view color and must not contain transparency.

Streaming rendering flow

  1. The client sends an SSE request, meaning the real stream has started. At the same time, it informs the rendering engine, which marks pseudo-stream rendering as started and begins loading.
  2. During the stream, multiple real data callbacks arrive. On the first callback, the engine generates layout information for the real streamed data and starts a timer for pseudo-stream rendering. Every time new stream data arrives, it appends the new text to the previously received stream text, regenerates layout information, and replaces the previous layout. Internally, the streaming renderer only checks whether the current progress has exceeded the end of the layout. If not, it “scratches open” one more grid.
  3. When the real stream ends, the final layout is generated and updated, and the real stream is marked as finished. When the internal pseudo renderer finishes the currently available layout, it checks whether the real stream has ended. If yes, pseudo rendering ends; otherwise the engine waits for new real stream data.
  4. In some cases, pseudo-stream rendering needs to be interrupted directly. The corresponding API can be called; internally the engine stops the timer and adds ...... after the current position to indicate that the stream was interrupted.

Card expansion

In business scenarios, streaming cards often appear inside scrolling lists. Unlike traditional cards, whose height is determined from outside to inside, the height of a streaming card is determined from inside to outside. Therefore, while streaming, the engine must constantly call back and notify the outer cell card of its width and height.

In fact, updating only the cell height is not enough. A container is also needed for clipping. A mask alone is not enough; the unrevealed area must also be clipped away.

If the streaming card is in a list, after updating the model height during streaming, do not call reloadData or reloadItemsAtIndexPaths: to refresh the cell. That will cause flickering. Use the following methods to update only the cell height without refreshing content.

Pitfalls

LaTeX text appears first, then renders normally

Because data is returned as a stream, a complete formula may be cut into an intermediate state. On the client, this causes rendering flicker: part of the raw text is rendered first; after the client receives the complete data, the correct rendered result appears, causing a visual flash.

The reason is this: if a formula nested inside HTML is expressed as $xxx$, before parser processing it is regex-matched into <tex>xxx</tex>. However, during streaming, if only the first half of the data has arrived, such as $(a-b), the match will not succeed. Therefore $(a-b) is treated as plain text and directly output. Later, when the data becomes complete, such as $(a-b)^{2}$, it is parsed and rendered correctly.

The strategy is: for incomplete $xx formulas, the regex replaces them with <tex>xx. At that point, if xx cannot be parsed and rendered by the LaTeX engine, it is swallowed; otherwise it is output.

But because some edge cases were not fully covered, iOS adopted a once-and-for-all solution: for incomplete <tex> tags such as <tex>xx, before encountering </tex>, the content inside no longer goes through the LaTeX engine and returns empty. The streaming effect is that the formula start stays in a loading state.

Text justified alignment

Usually, YYLabel provides a ready-made API for justified alignment: view.textAlignment = NSTextAlignmentJustified. However, this causes flickering during streaming rendering. The root cause is that justified alignment may adjust the position of text that has already been rendered. This creates text flicker. That alignment style is suitable for static cards, but not for streaming cards.

Display overlap

During streaming, the engine depends on YYTextLayout to get the position of the current character. However, in some line-wrap cases, the returned position information is wrong.

As shown in the figure, after the Nth grid finishes streaming, the current line has already ended, so the next position should be the N+2th grid. But YYTextLayout returns the N+1th grid. This grid area is very large: it not only repeats the already streamed area, but also exposes the not-yet-streamed area too early. This causes the content to appear first and then get covered again, producing flicker.

After investigation, this is related to the logic in YYTextLayout that calculates the union of Rects. Some Rects have width or height equal to 0, and they do not need to participate in union calculation. Excluding them fixes the issue.

Underline spacing

YYText cannot adjust the distance between text and underline, but this is a strong requirement in the business scenario. The solution is to modify YYTextDrawDecoration in YYText and add an underline offset.

Then include offset in the underline’s y coordinate inside YYTextDrawDecoration.

After the modification, the underline on the last line is often lost. The main reason is that if the underline spacing on the last line is too large, it exceeds the layout range and gets clipped. So the layout information also needs to be expanded. When the layout method finally determines the layout size, it should take this offset into account.

Underline attachment

Rich text contains formulas and images, which usually appear in NSAttributedString as attachments. In some cases, a formula or image is obviously taller than normal text, so the underline has problems. As shown below, the underline passes directly through the formula, which clearly does not meet product requirements.

Therefore, YYText layout logic needs to be modified again. The core logic is: during layout of each line, get the ascent and descent of the attachment, then apply an offset based on the maximum descent.

The premise of this fix is that Attachment must correctly set ascent and descent; otherwise the problem cannot be solved.

Flicker + misalignment

From the phenomenon, the layout information used during streaming seems to differ from the layout information actually displayed, causing misalignment and flicker. Investigation showed that the problem was caused by frequent YYText refreshes in a short period of time. Therefore the original solution needed to be changed:

When streamed text is received, do not immediately apply the newly generated layout information to the view. Instead, record that layout information. After the view finishes streaming the current layout, it checks whether layout information has been updated. If yes, it applies the new layout and continues streaming; otherwise pseudo-stream rendering is complete.

During streaming of the current layout, new layout information may be updated multiple times and overwritten. This avoids frequent view refreshes, solves flicker and misalignment, and also improves performance.

Syncing stream interruption progress to TTS

In the business scenario, the original rich text usually needs to be parsed by the rendering engine and converted into readable text, which is then fed to the TTS engine. Usually this is fine. But in a streaming interruption scenario, the final displayed text ends with ..., while the readable text may already have been fed to TTS as a whole. As a result, TTS reads more text than what streaming rendering displayed, and canceling the extra fed content is not easy.

Therefore, the final solution is: for every rendered character, the rendering engine emits the corresponding text to TTS (which has its own internal cache queue). When streaming rendering is interrupted, the text fed to TTS also stops at that point. IM also records this index, so future replay can locate the same position, ensuring consistency between rendering and the final TTS text.

$...$$...$ problem

This problem is complex, so let’s start with some background. Traditional TeX has two ways to typeset formulas:

  • inline math mode, where formulas are included in a paragraph. Early TeX used $...$.
  • display math mode, where formulas occupy their own line. Early TeX used $$...$$.

Today, the standard best practice is to avoid using $ characters to typeset formulas, and instead use LaTeX delimiters:

  • For inline math mode, use \(... \) or \begin{math}...\end{math}, instead of $...$.
  • For display math mode, use \[... \] or \begin{displaymath}...\end{displaymath}, instead of $$...$$.

Back to the business scenario: LaTeX formulas are usually nested inside HTML, so HTML parsing must happen first. For easier parsing, a custom tag <tex>...</tex> is used to represent LaTeX formulas.

Even so, LaTeX parsing is not painless. The reason is that LaTeX text may contain HTML syntax markers. For example: <tex>1\+2<5</tex>. The < inside the LaTeX text is meant for display; it is not an HTML tag marker. But the HTML parser treats it as a tag, causing parsing chaos. Therefore, before parsing, we need to regex-match <tex>...</tex> and replace < with &lt; for escaping. Similar symbols include >, &, ", and '.

After LLMs arrived, all the delimiter types mentioned above might be returned, so client rendering still had to support them. Taking $...$ and $$...$$ as examples, the initial client implementation was very simple: before parsing, first regex-match $$...$$, then match $...$, replace them with <tex>...</tex>, and keep the rest of the logic unchanged. Everything was peaceful.

There was actually an implicit assumption here: if HTML text wants to express the dollar sign $, it must use \$; otherwise a single dollar sign would misalign all subsequent parsing.

Until one day, the model returned $...$$...$, breaking that peace. Its intention was to express two consecutive formulas, but because the middle $$ became coupled, the client regex logic failed. The client first tried to match $$...$$ and failed, then matched $...$, and finally treated ...$$... as LaTeX text, causing an error.

The client eventually abandoned the regex matching approach and switched to a scan with stack push/pop:

  1. When encountering $, check whether the stack already contains $. If yes, pop it first, and one formula is complete.
  2. Otherwise, consider whether the next character is $.
    1. If yes, combine into $$.
      1. Check whether the stack contains $$. If yes, pop it first, and one formula is complete.
      2. Otherwise, push $$ to mark the start of a formula.
    2. Otherwise, push $ to mark the start of a formula.

This stack-based scan brings flexibility and freedom. It can solve $ and $$ issues, and can also handle \(...\) and \[...\]. It also handles escaping of HTML syntax markers. All problems can be solved in one scan, which is difficult with the regex approach.

In addition, the stack-based scan also brought a performance benefit: LaTeX preprocessing time dropped to 1/2 to 1/4 of the regex solution.

Summary

The streaming rendering discussed above is built on top of YYText. Thanks to YYText’s good layout mechanism, we can quickly implement a pseudo-streaming effect and satisfy business needs. But we also encountered many problems and stepped into many pitfalls. Even so, the current pseudo-streaming solution still has some natural defects:

  1. Because it is based on YYText, many problems still require modifying YYText source code. YYText cannot be treated as a black box, which raises the bar for future development and maintenance.
  2. The business side has weak layout control, especially for block elements such as tables and lists. The client struggles with these. Fundamentally, YYText is still mainly for text layout. For mixed image-text-table layout and nested layout, if we want to control details, YYText becomes limited, because attachment and YYText are separated, making it difficult to fully use YYText’s layout and rendering capability.
  3. HTML and LaTeX are split at the rendering layer. A formula is embedded into YYText as a whole attachment and can only be output as a whole View, making it hard to achieve a streaming rendering effect.

In the future, we may need to build a rendering engine that can integrate multiple rich-text syntaxes. Even though the upper-level syntaxes are different, the underlying rendering framework can be consistent. This would bring unified rendering capabilities and more flexible customization, providing greater possibilities for solving nested block rendering, formula streaming rendering, and similar problems.

Some questions to think about:

  1. Is it possible to build a truly streaming parser?
  2. Can the number of layout passes be reduced?
  3. Can we achieve truly streaming rendering?
