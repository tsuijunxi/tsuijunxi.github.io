Preface

Recently, to solve various tricky problems encountered during chapter splitting, I had to dig deep into TxtEngine and debug many implementation details. I had touched this engine before when solving card-layout issues, but each time I only saw isolated pieces rather than the whole picture.

To avoid being blocked by partial understanding, I decided to organize how this reading engine works from a more complete perspective, including file opening, layout, rendering, page turning, and related parts.

Encoding Detection

Before parsing the file stream, we need to determine its encoding. So how do we identify the encoding of a file?

Identifying Files with a BOM

BOM stands for Byte Order Mark. It usually appears at the very beginning of a file and adds several extra invalid bytes to indicate the file’s encoding type. In some cases, the BOM also carries endian information. By reading the first few bytes of a file, we can determine how the file stream should be decoded.

Common UTF encodings include the following. UTF-16 and UTF-32 also have big-endian and little-endian variants:

Why does UTF-8 not have an endian problem? Because when a character is represented in UTF-8, its Unicode code point is encoded into a byte array. When writing that byte array to memory, the bytes are simply written one by one in array order. There is no high-byte or low-byte issue. Therefore, the UTF-8 byte sequence for a Chinese character is the same on any kind of CPU.

On Microsoft Windows, UTF-8 files may include the BOM EF BB BF, even though UTF-8 does not need it. This does not mean UTF-8 needs byte order information; it only marks the file as UTF-8. In some cases, this extra marker can cause trouble, so encoding detection should account for it and avoid treating the BOM as part of the file’s actual text.

At this point, when opening a file, if we see a BOM, we can identify whether the encoding is UTF-16, UTF-32, or UTF-8, and whether it is big endian or little endian.

Identifying Files Without a BOM

For files without a BOM, how should we determine their encoding?

Here, let us use UTF-8 and GBK as examples. GBK has no BOM. UTF-8 allows a BOM, but usually does not include one.

First, UTF-8:

UTF-8, or Unicode Transformation Format 8-bit, is a multibyte encoding designed for international text. It uses 8 bits, that is one byte, for English characters, and usually 24 bits, or three bytes, for Chinese characters. UTF-8 contains the characters needed by countries around the world, so it is an international encoding with strong universality. It is a multibyte character set. A Unicode character may be represented by one or more bytes, and the byte patterns follow clear rules:

By identifying the leading byte, we know how many bytes should be parsed as one unit. The leading byte can only match one of these forms, and every subsequent byte starts with 10. The pattern is very obvious. So we can traverse the string according to these characteristics to determine whether it is UTF-8 encoded.

Now GBK:

GBK is an extension of the national standard GB2312 and is backward compatible with GB2312. GBK represents text using two bytes. Both Chinese and English characters are represented with double bytes, and the highest bit is set to 1 to distinguish Chinese. GBK encoding is based on location codes and uses double-byte encoding for Chinese characters and Chinese punctuation. The common encoding method is 0xA0 + area number, 0xA0 + position number. For example, the Chinese character “安” has the decimal location code 1618, so its GBK encoding is 0xA0 + 16, 0xA0 + 18, which is 0xB0 0xB2. Although GBK uses two-byte display, each byte also has a valid range. The overall GBK range is 0x8140 to 0xFEFE; the first byte is between 0x81 and 0xFE, and the second byte is between 0x40 and 0xFE, excluding the xx7F line.

From this, we can see that although GBK and UTF-8 files do not necessarily have markers, their encoded byte sequences have clear characteristics. We can usually identify whether a file is GBK or UTF-8 by examining the byte sequence.

ASCII Character Width

font_character_width determines whether the current font type is a system font. If it is not, it also needs to locate the font file, load it, and register it. Finally, it returns the corresponding CTFontRef, and the character width is calculated from that CTFontRef and the character.

Setting Chinese Character Width

CJK character width is basically fixed. Therefore, we only need to calculate and cache the width of one representative character instead of calculating every character’s width each time. Layout

After opening a file, the engine usually enters from an anchor. An anchor contains two parts: paragraph offset and line offset.

Paragraph Splitting

If the paragraph linked list for the anchor has not been built yet, paragraph parsing is triggered. Paragraph splitting is based on these separators: \n\r, \n, \r, and \r\n. Each time, the engine searches the current data stream for the next separator. Once one is found, the start offset and size of a new paragraph can be determined from the offsets before and after it.

Paragraph Line Breaking

For paragraph splitting, encoding conversion, and character-offset calculation, the work only needs to be done once. It does not need to be updated later because this information is relatively independent and does not depend on other layout conditions.

However, laying out paragraph text according to the current font, direction, and other settings does depend on layout-related settings, such as drawing area size, orientation, font size, font color, line spacing, and paragraph spacing. Once any of these settings changes, the layout here also needs to be updated.

The essence of layout is: according to the layout settings, generate line-by-line layout results from one paragraph. Note that height-offset information is not included here.

First, why is mid_off introduced here?

The main reason is that some paragraphs may cross page boundaries. In that case, if a rotation occurs, the current page continues to lay out from the starting anchor again. The last line of the paragraph that crossed into the previous page may not fill a full line. Therefore, this rule is introduced: for a paragraph crossing into the previous page, the last line is only laid out up to the character before the anchor. This means the last line of the previous page may break differently. For paragraphs that do not cross pages, mid_off is naturally 0, so the first half of the logic does not run.

The core of line breaking is calculating the width of each character and deciding, based on the page width, whether a given character is the last character of the current line. This produces one line inside the paragraph.

In addition to the normal calculation process, there are extra rules:

  1. Filter out emoji characters.
  2. Punctuation rules for avoiding punctuation at line heads and tails:
    • If the current line ends with a left quote, left parenthesis, left book-title mark, left single quote, em dash, or ellipsis, move it to the next line.
    • If the next line starts with two consecutive punctuation marks and the current line does not end with punctuation, move the last character of the current line to the next line to avoid punctuation appearing at the start of a line.
    • If the next line starts with only one punctuation mark, move that punctuation mark up to the previous line.
  3. A comma or period at the end of a line counts as half width.
  4. After each line is laid out, spaces need to be considered and character x positions and widths are recalculated.

English text has additional layout rules. Sometimes an English word or number is too long, and the last word or number of a line has not finished when the line reaches the edge. To avoid breaking a word or number across lines, the engine follows these rules:

  • If the first character of the next line is not an English letter or number, the current line can fully contain the last word. This is normal, so return directly.
  • If the first character of the next line is a number or English letter, check whether the last character of the current line is also a letter or number.
  • If it is, count the length of the last word or number on the current line. If the word or number length is limited, move the front part of that word or number to the next line. Otherwise, do nothing.
  • If it is not, do nothing.

Inserted Paragraph Handling

The business layer may insert data into the layout.

  • Some content needs to be inserted into the middle of a paragraph, such as “brilliant ideas”. Some needs to be inserted at the end of a paragraph, such as various business data at the end of a chapter: text ads, image ads, Q&A, cards, Guangdiantong data, and so on.
  • Some inserted paragraphs need to be laid out like normal text, such as author’s notes. Their layout rules are the same as body text, except that the font, font size, and color may differ. Page Turning

After the current page has been rendered, moving to the next or previous page requires finding the starting anchor of that page. TxtEngine mainly uses these methods:

The logic of the first two methods is roughly the same as the rendering method. The difference is that they only calculate the Y offset and do not actually draw.

  1. moveNextPage: starting from the current page anchor, lay out line by line to the end of the current page, then find the starting paragraph offset and line offset of the next page.
  2. movePrevPage: starting from the current page anchor, lay out backwards to the beginning of the previous page, then find the starting paragraph offset and line offset of the previous page.

There are several flaws here:

  • Since the current page has already been rendered, finding the starting anchor of the next page should be quick using the current page’s tail pointer. There is no need to run a large loop again. Unfortunately, although TxtPage was introduced long ago and already contains the tail pointer, it was not used. This is what Siyu is currently working on.
  • Determining whether the current page is the end of the chapter, isBottom, should also only require checking the tail pointer. Unfortunately, isBottom also runs a large loop.
  • None of these methods caches anything after finishing the loop, causing the large loop to run many times.
  • The two loops above and the rendering loop have certain differences, which sometimes leads to missing paragraphs or repeated layout.

If TxtPage can record the current page’s start pointer and end pointer, then each page’s layout and rendering process only needs to run once. This removes a lot of unnecessary performance cost, ensures that rendering and layout results are consistent, and avoids many annoying layout issues.

Paragraph Cache

When turning pages forward and backward, the engine often first needs to determine whether the paragraphs already built in memory are sufficient to construct the previous or next page.

  1. In some cases, the chapter file is large and cannot be read entirely at once.
  2. In some cases, the reader enters from an anchor in the middle of a chapter. At that point, only the data stream after the current anchor is loaded. When turning to the previous page, the engine needs to load the data stream before the anchor and build the previous paragraphs.

The threshold used here is cache_bytes = 8 * 1024.

The newly loaded cache is immediately parsed into a paragraph linked list, including paragraph splitting, encoding conversion, character-offset calculation, and line layout according to the current font, direction, and other conditions. Finally, the newly parsed prgf_group is merged into the global paragraph group _prgfGroup.

Online-book chapter files are usually small, so in most cases the paragraph linked list for a chapter can be cached in memory. But when the file is large, such as an imported book, the paragraph linked list cannot always stay in memory. The engine needs to cache paragraphs within a certain distance before and after the current reading offset, and paragraphs outside that range need to be cleared.

General Idea

For online books, chapter files are generally small, so we can try a new approach:

Read the entire chapter file at once, split paragraphs, convert encoding, break lines, paginate from beginning to end according to the current settings, and cache the pagination results. During rendering, use the page number to directly obtain the page’s start and end pointers and draw from them. This removes the difference between forward and backward page turning, and avoids missing paragraphs or repeated layout.

Chapter Splitting

What is chapter splitting? Some files may contain multiple chapters, and apart from the file itself there may be no other information. In that case, chapter information has to be determined from the file content, including the number of chapters, each chapter title, content, and starting offset.

This process is essentially searching for patterns like "第xxx章（章节回卷篇部）". The process of searching for these characters is very similar to searching for \n\r earlier.
