Priority Inversion in Practice

Posted on 2022-11-23
Words count in article: 83k | Reading time ≈ 5:03
中文 / English

This article also appears on WeChat: <>

Background

I recently hit a large number of deadlocks in production around read-write locks. After checking the stacks, I found that every problematic thread belonged to an NSOperationQueue and all of them were marked QOS:BACKGROUND. It looked like the worker threads that held the lock were still running, but they were not getting enough CPU time, which eventually caused the main thread to time out after 8 seconds.

Why would a thread that already owns a lock still need so long to finish? There are two possibilities:

  1. It really is that slow.
  2. Priority inversion is happening.

The following diagram shows the main thread waiting for the lock, and a background thread holding it.

How to deal with it

In this case, the low-priority thread that holds the read-write lock keeps getting scheduled too late, gets preempted, or simply runs out of time slices. Meanwhile, the high-priority thread keeps waiting for the lock. This is classic priority inversion.

Since iOS 8, Apple introduced QualityOfService, which is similar to thread priority. Different QoS classes get different CPU, network, and disk resource allocations, so we can use QoS to influence queue priority.

Option 1: Remove QoS settings from NSOperationQueue

Apple gives a clear warning in the Threading Programming Guide:

It is generally a good idea to leave the priorities of your threads at their default values. Increasing the priorities of some threads also increases the likelihood of starvation among lower-priority threads. If your application contains high-priority and low-priority threads that must interact with each other, the starvation of lower-priority threads may block other threads and create performance bottlenecks.

The advice is simple: do not arbitrarily raise thread priority, especially when high- and low-priority threads compete for the same critical resource. Removing the QoS tweak can solve the problem.

Option 2: Temporarily raise the worker thread priority

The pthread_rwlock_rdlock(3pthread) documentation says:

Realtime applications may encounter priority inversion when using read-write locks. The problem occurs when a high priority thread “locks” a read-write lock that is about to be “unlocked” by a low priority thread, but the low priority thread is preempted by a medium priority thread. This scenario leads to priority inversion; a high priority thread is blocked by lower priority threads for an unlimited period of time. During system design, realtime programmers must take into account the possibility of this kind of priority inversion. They can deal with it in a number of ways, such as by having critical sections that are guarded by read-write locks execute at a high priority, so that a thread cannot be preempted while executing in its critical section.

That is written for realtime systems, but it still gives a useful hint. In our case, once a thread acquires _rwlock through pthread_rwlock_wrlock, we temporarily boost its QoS, then restore the original QoS after releasing the lock.

One thing to note: this has to be done with pthread APIs. NSThread APIs do not work here.

Demo verification

To see whether manually adjusting thread priority helps, I ran a local demo: create 2000 operations to keep the CPU busy, set the queue QoS to NSQualityOfServiceUserInitiated, and downgrade every 100th operation to NSQualityOfServiceBackground. Each operation runs the same expensive work, and we measure the 10 selected operations.

Measured results:

Normal case: average time per task is 11.8190561. After lowering the operation priority: 94.70210189. After lowering the priority and restoring it inside the block: 15.04005137 (still a bit slower than the normal case, which is worth thinking about).

The demo shows that manual priority boosting can greatly reduce the total time spent on low-priority tasks. When a lock is held, this shortens the time the main thread stays blocked.

A deeper look at priority inversion

Does every lock need the same manual priority boost? Will the system automatically adjust thread priority? If so, can it cover all locks? To answer these questions, we need to understand priority inversion more carefully.

What is priority inversion?

Priority inversion happens when a low-priority process or thread owns a synchronization resource, while a high-priority process or thread is waiting for that resource. As a result, the high-priority thread is delayed behind the low-priority one. Depending on the blocking pattern, priority inversion is usually split into Bounded priority inversion and Unbounded priority inversion.

The diagrams below are adapted from Introduction to RTOS - Solution to Part 11 (Priority Inversion).

Bounded priority inversion

Here, the high-priority task (Task H) is blocked by the low-priority task (Task L) that owns the lock. The blocking time is bounded by how long Task L stays in the critical section. As long as Task L holds the lock, Task H stays blocked, and the low-priority task effectively runs ahead of the high-priority one.

Unbounded priority inversion

If a medium-priority task (Task M) preempts Task L while Task L is holding the lock, the bounded case turns into an unbounded one. Task M can keep taking CPU time away from Task L, which means Task H may remain blocked for an arbitrarily long time.

Common solutions

There are two classic ways to deal with unbounded priority inversion:

Priority ceiling protocol

Each critical resource is assigned a ceiling priority. When a task enters the critical section, the system temporarily raises that task to the ceiling priority. When the task leaves the critical section, its original priority is restored. The ceiling is chosen as the maximum priority of all tasks that may use the resource.

In the figure, the lock ceiling is 3. When Task L holds the lock, it is boosted to priority 3, the same as Task H, which prevents Task M from running until Task L and Task H are done with the lock.

Priority inheritance

With priority inheritance, if a high-priority task is waiting for a lock owned by a low-priority task, the low-priority owner temporarily inherits the higher priority so it can run sooner and release the resource. After the lock is released, the original priority is restored.

Both approaches restore the low-priority task’s priority when the lock is released. But they only prevent Unbounded priority inversion; they cannot eliminate Bounded priority inversion, because Task H still has to wait for Task L to finish the critical section.

Ways to reduce or avoid bounded inversion include:

  1. Shorten the critical section.
  2. Avoid using critical resources that block high-priority work.
  3. Use a dedicated queue to manage the resource instead of a lock.

Priority inheritance must be transitive. For example, if T1 is blocked by a resource owned by T2, and T2 is itself blocked by a resource owned by T3, then T3 must inherit the highest priority from T1 through T2. Otherwise, another thread with priority between T2 and T3 could preempt T3, causing an inversion relative to T1.

How do we avoid priority inversion?

QoS propagation

iOS mainly uses two mechanisms to propagate QoS across threads or queues:

  • dispatch_async
    • dispatch_async() automatically propagates the QoS from the calling thread, but it translates User Interactive to User Initiated so that non-main threads do not get that highest priority.
    • QoS is captured when the block is submitted. If the destination queue does not have a QoS or does not lower the QoS, the captured value is used.
  • XPC-based inter-process communication.

The QoS propagation rules are more complex and depend on:

  • the current thread’s QoS,
  • the arguments used when creating a dispatch_block with dispatch_block_create(),
  • the QoS of the destination queue or thread for dispatch_async or IPC.

The scheduler uses these inputs to decide which priority a block should run with.

  1. If no thread is synchronously waiting for that block, the block runs at the priority computed above.
  2. If there is synchronous waiting between threads, the scheduler may adjust priorities to avoid inversion.

When can the system trigger inversion avoidance?

If the current thread is blocked by work running on another thread, and the system knows which thread owns that work, it can boost the relevant owner and avoid inversion. If the system does not know the owner, it cannot decide whom to boost.

APIs that record owner information include:

  1. pthread mutex, os_unfair_lock, and higher-level APIs built on top of them:
    1. dispatch_once uses os_unfair_lock.
    2. NSLock, NSRecursiveLock, @synchronized, and similar APIs are based on pthread mutex.
  2. dispatch_sync and dispatch_wait.
  3. xpc_connection_send_with_message_sync.

Using these APIs allows the system to activate priority inversion avoidance when inversion happens.

pthread_rwlock_t

The pthread_rwlock_init documentation says:

Caveats: Beware of priority inversion when using read-write locks. A high-priority thread may be blocked waiting on a read-write lock locked by a low-priority thread. The microkernel has no knowledge of read-write locks, and therefore can’t boost the low-priority thread to prevent the priority inversion.

The rough meaning is that the kernel does not understand read-write locks, so it cannot boost the low-priority thread and therefore cannot avoid priority inversion. Looking at the definition, however, pthread_rwlock_s contains an rw_tid field used to record the thread that owns the write lock. This raises an interesting question: why does pthread_rwlock_s have owner information, but still cannot avoid priority inversion?

This Hacker News thread mentions:

xnu supports priority inheritance through “turnstiles”, a kernel-internal mechanism which is used by default by a number of locking primitives (list at [1]), including normal pthread mutexes (though not read-write locks [2]), as well as the os_unfair_lock API (via the ulock syscalls). With pthread mutexes, you can actually explicitly request priority inheritance by calling pthread_mutexattr_setprotocol [3] with PTHREAD_PRIO_INHERIT; the Apple implementation supports it, but currently ignores the protocol setting and just gives all mutexes priority inheritance.

In short: XNU uses the kernel-internal turnstile mechanism for priority inheritance, and this mechanism is applied to pthread mutex and os_unfair_lock.

Following that clue, I found _kwq_use_turnstile in ksyn_wait. The comment describes read-write locks somewhat cautiously and adds “at least sometimes”.

pthread mutexes and rwlocks both (at least sometimes) know their owner and can use turnstiles. Otherwise, we pass NULL as the tstore to the shims so they wait on the global waitq.

Looking at _kwq_use_turnstile, the code is more honest: only KSYN_WQTYPE_MTX enables turnstile priority-inversion protection. A read-write lock is KSYN_WQTYPE_RWLOCK, which means it does not use _kwq_use_turnstile and therefore cannot avoid priority inversion.

In _pthread_find_owner, we can also see that the owner of a read-write lock is 0.

The mysterious semaphore

dispatch_semaphore

I used to think binary semaphores and mutexes were basically the same. After researching, I found that dispatch_semaphore has no QoS concept and does not track the owner thread. So when a high-priority thread waits on it, the kernel has no idea which thread should be boosted. If the lock owner has a lower priority than the waiter, the high-priority thread can wait forever.

This is a warning from the system:

Semaphores are for signaling (same as condition variables, events) while mutexes are for mutual exclusion. Technically, you can also use semaphores for mutual exclusion (a mutex can be thought as a binary semaphore) but you really shouldn’t. Right, but libdispatch doesn’t have a mutex. It has semaphores and queues. So if you’re trying to use libdispatch and you don’t want the closure-based aspect of queues, you might be tempted to use a semaphore instead. Don’t do that, use os_unfair_lock or pthread_mutex (or a higher-level construct like NSLock) instead.

That is a pretty strong hint: semaphores are dangerous if you use them as locks.

Apple’s example:

  1. If this runs on the main thread, the current priority is QOS_CLASS_USER_INTERACTIVE.
  2. The async work triggered from the main thread gets elevated to QOS_CLASS_USER_INITIATED.
  3. The main thread is blocked by the semaphore, but the async task that signals it runs at a lower priority, so priority inversion may happen.

Clang even has a static checker for this pattern.

To enable this check, just turn on the corresponding Xcode setting.

dispatch_group behaves similarly to semaphore: when you call enter(), the system does not know who will eventually call leave(), so it cannot know the owner either. Therefore it does not participate in priority donation.

Some concepts

Turnstile

Earlier I mentioned that XNU uses turnstile for priority inheritance. Here is a simplified mental model.

There are many synchronization objects in XNU, such as lck_mtx_t. To solve priority inversion, each synchronization object would need its own separate structure to track all related state, including the queue of blocked threads. If every sync object allocated such a structure permanently, memory usage would be huge.

XNU solves this with the turnstile mechanism. The key idea is that one thread cannot block on multiple synchronization objects at the same time. Therefore each sync object only needs a pointer to a turnstile, and the turnstile itself can be allocated on demand. It stores everything needed for the lock, such as the blocked thread queue and the owner pointer. turnstiles are dynamically allocated from a pool, and the pool grows with the number of active threads. The number of turnstiles is therefore bounded and manageable. The first blocked thread allocates the turnstile; once no threads are waiting anymore, the turnstile is returned to the pool.

Priority values

The priority numbers in the experiments are Mach-level user thread priorities. A quick reference from Mac OS X and iOS Internals:

  1. User thread priorities are 0~63.
    1. NSQualityOfServiceBackground maps to 4.
    2. NSQualityOfServiceUtility maps to 20.
    3. NSQualityOfServiceDefault maps to 31.
    4. NSQualityOfServiceUserInitiated maps to 37.
    5. NSQualityOfServiceUserInteractive maps to 47.
  2. Kernel thread priorities are 80~95.
  3. Realtime thread priorities are 96~127.
  4. 64~79 are reserved by the system.

Summary

This article walked through the main ideas behind priority inversion and the common ways to handle it, then studied several iOS locking primitives in detail. With a deeper understanding, we can avoid unnecessary priority inversion and reduce deadlock-like stalls.
