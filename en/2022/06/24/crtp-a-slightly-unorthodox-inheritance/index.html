CRTP, a Slightly Unorthodox Form of Inheritance

Background

While writing some C++ code recently, I ran into a few repetitive patterns. While thinking about how templates could help, I remembered CRTP, a rather unusual form of inheritance.

What Is CRTP?

CRTP stands for Curiously Recurring Template Pattern. It is a common idiom in C++ template programming. It was proposed by James Coplien in 1995 and has two defining traits:

  1. a class inherits from a template base class;
  2. the derived class is passed as the template parameter of the base class.

So why does this work? And why would anyone design it like this?

Here is a small example:

At this point, many people start wondering about time travel, because the code looks quite strange. Derived seems to inherit from itself, and it is used before it is fully declared.

In practice, a base-class template can use the fact that a member function may be declared early, but is only instantiated when the derived class actually uses it. That allows the base template to call methods on the derived type.

In the example above, Base<Derived>::interface() is declared before Derived, but it will not be instantiated until it is used. By then, Derived::implementation() is already visible to the compiler.

Without virtual functions, a base class always calls its own implementation. If a derived class calls an inherited function, and that function calls another member function, the derived override is never selected.

With CRTP, however, the base class can route the call to the derived class at compile time, effectively simulating virtual dispatch without the runtime cost of a vtable lookup. This is usually called static polymorphism.

There are two things to keep in mind:

  1. A class template is a template; a class is a class. Here, Base is just the template.
  2. The base class is Base<Derived>, not Base.

Here are two questions worth thinking about:

  1. Does Base<Derived> actually implement implementation()? Would the following compile?
  1. What exactly does Derived inherit from Base<Derived>, or what promise is it following?

What Happens When CRTP Meets Design Patterns?

What can CRTP be used for? How should it be applied? Let us start with a few classic design patterns. When CRTP meets them, things get interesting.

Singleton

How is a singleton usually written in C++?

C++11 guarantees thread-safe initialization of local statics. In C++11, Effective C++ recommends the elegant Meyers’ Singleton, which creates the instance only on first call to getInstance(). Before C++11, locking was still needed.

What if another class also needs a singleton? The brute-force solution is to copy the code. But with CRTP:

The derived class becomes the template parameter, and the singleton is constructed directly from the derived constructor. This uses:

  1. variadic templates, so any number of arguments can be passed;
  2. std::call_once and std::once_flag, which are very similar to dispatch_once and dispatch_once_t.

Any class that wants a singleton only needs to inherit from Singleton and pass itself as the template argument:

  1. The subclass must make its constructor private.
  2. The subclass must declare Singleton<TestService> as a friend.

Clone Pattern

When you want to get a copy of an object through a base pointer, the usual approach is to add a virtual Clone method. With CRTP, the function does not need to be repeated in every derived class, as long as the derived class is copy-constructible.

Visitor Pattern

The visitor pattern itself is already fairly complex, and mixing it with CRTP makes things more interesting. I will use an example from the modern C++ design-pattern series.

Suppose there is an animal hierarchy: dog and bird derive from animal, and the base class has a pure virtual move() method. As requirements evolve, we add swim() to dog and fly() to bird. Since dogs cannot fly and birds cannot swim, those methods do not belong in the base animal class.

Now the question is: how do we call swim() and fly() through an animal object?

Downcasting

The most common approach is downcasting.

Many people have seen code like this, and many have written it, myself included. But the style is really not great:

  1. the if-else chain grows as requirements change;
  2. dynamic_cast is inefficient and should be avoided when possible.

Visitor to the Rescue

This is where the visitor pattern comes in: it adds new behaviors without modifying the visited object, and it removes the need for dynamic_cast.

This is the classic visitor pattern. For the animal hierarchy, the way you visit an animal can be extended freely through a visitor, and the animal hierarchy itself is not aware of it. In other words, you can add new behaviors without modifying the visited object. That is a great property.

This is also the classic double dispatch visitor pattern. Double dispatch means two dispatches, i.e. two virtual function calls:

  1. the first virtual call is animal::accept;
  2. the second virtual call is visitor::visit.

CRTP steps in

Do you notice one annoying method? Yes, accept. Both dog and bird implement it, and the code is identical. Following the clone-pattern trick from earlier, we can eliminate this duplication by moving accept into a visitable class derived from animal. From now on, the derived classes no longer inherit animal directly; they inherit visitable.

The derived classes immediately look much cleaner, right?

And now the magic

If we add another subclass fish, then the visitor base class needs a new virtual function, and all previous derived classes need to change. That makes this code unstable and violates the open-closed principle. The reason is that animal depends on visitor, and visitor depends on concrete animal types. SOLID constantly reminds us: depend on abstractions, not on concretes.

So we can make visitor a template class, so animal depends on a generic type instead of a concrete one. Because templates are contagious, and we do not want to template-ify animal as well, we introduce a visitor_token base class. It is just a helper base class with nothing but a default virtual destructor, but that is enough.

At this point, both visitor and animal depend only on abstractions, which achieves decoupling.

The biggest trick here comes from MultipleVisitor, which uses using-declaration to automatically generate a visitor inheritance hierarchy, instead of defining each derived visitor class by hand. This simplifies the code and makes it easy to define new visitor hierarchies: just add a new type.

Summary

This article covered:

  1. the CRTP concept;
  2. performance comparison with virtual functions;
  3. several design-pattern use cases;
  4. practical examples.

The strengths of CRTP are:

  • high performance;
  • code reuse;
  • easier extension than single inheritance in some cases.

The weaknesses of CRTP are:

  • it is hard to understand;
  • it does not fit traditional OOP very naturally;
  • template use can spread quickly through the codebase.

Postscript: The Ghost Sibling of CRTP

Does the 1995 vintage of CRTP taste good?

Then let us look at the ghost sibling of CRTP: Mixin. A mixin is a C++ template technique that combines multiple independent feature classes through inheritance to achieve module reuse. The basic idea is to treat template parameters as base classes:

Take Point as an example. Traditionally, if we want to extend it, we would derive LabelPoint, ColorPoint, LabelColorPoint, and so on. You can see that LabelColorPoint uses diamond inheritance, which requires virtual inheritance:

The mixin approach instead defines Label and Color as separate classes, and then combines them into LabelColorPoint by composition-like inheritance, like building blocks:

Mixin is called the ghost sibling of CRTP mainly because the inheritance direction looks opposite on the surface:

  1. CRTP passes the derived class as a template parameter, and the base template calls derived-class functionality;
  2. Mixin passes the base classes as template parameters, and the derived template calls base-class functionality through combined inheritance.
