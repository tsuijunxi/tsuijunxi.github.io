Understanding OC/C++ Closures

Posted on 2022-02-14 | In OC C++
Words count in article: 37k | Reading time ≈ 2:16
中文 / English

This article also appears on WeChat: <<Understanding OC/C++ Closures>>

Background

Apple’s Objective-C compiler lets you mix C++ and Objective-C in the same source file. The combined language is Objective-C++. Compared with ecosystems where Swift, Kotlin, or Dart have to bridge into C++ through separate files and interop layers such as JNI or FFI, the single-file Objective-C and C++ mix is very pleasant.

That said, mixed compilation does not mean the two languages gain each other’s features. Objective-C++ does not add C++ features to Objective-C, and it does not add Objective-C features to C++. For example, you cannot call a C++ object with Objective-C syntax, you cannot add a constructor or destructor to an Objective-C object, and you cannot swap this and self.

The class systems remain separate: C++ classes cannot inherit from Objective-C classes, and Objective-C classes cannot inherit from C++ classes.

This article explores the confusing interaction between Objective-C Blocks and C++ lambdas.

Environment: C++14, Objective-C under ARC only.

Memory management

Objective-C blocks participate in ARC and object lifetime rules, while C++ lambdas follow normal C++ object semantics.

Mixed capture problems

Conclusion

C++ lambdas are essentially anonymous struct types that store captured variables. ARC ensures that C++ structs containing Objective-C object fields still follow ARC semantics:

  1. The struct constructor initializes Objective-C object fields to nil.
  2. When such a field is assigned, the old value is released and the new one is retained (or copied for blocks).
  3. When the struct destructor runs, the Objective-C field is released.

C++ lambdas can capture Objective-C objects either by value or by reference:

  1. Reference capture is roughly equivalent to __unsafe_unretained, which is dangerous because of lifetime issues.
  2. Value capture is roughly equivalent to __strong, which can create retain cycles, so __weak may be needed.

  1. The weak reference count of monitor changes like this:
    • when monitor is created, weak_count = 1;
    • when weakMonitor is created, weak_count = 2;
    • after the Objective-C block captures it, weak_count = 4, because the weak pointer is copied twice:
      • once during capture;
      • once more when the block is copied from stack to heap.

Note that the C++ weak count is a bit strange: its value equals weak references + 1. The reason is a bit involved; see https://stackoverflow.com/questions/5671241/how-does-weak-ptr-work

If we do not use std::weak_ptr and instead capture std::shared_ptr directly, the strong reference count becomes 3, and the logic is otherwise the same.

With __block

We can conclude:

  1. Objective-C Blocks can capture C++ objects by reference.
  2. The weak reference count of monitor behaves like this:
    • when monitor is created, weak_count = 1;
    • when weakMonitor is created, weak_count = 2;

  1. The this pointer inside the move constructor is 0x0000600003b0c830.
  2. __r is also 0x0000700001d959e8, which matches the original monitor address.

After the block assignment finishes, printing monitor again shows that its address has changed and now matches the this pointer from the move constructor. That means monitor has become the object constructed at that new address.

During the whole process, the monitor variable changes address and becomes a different std::shared_ptr object, so it can still be accessed afterward.

When is the captured C++ object released?

When the Objective-C Block is released, the captured C++ object is released as well.

Capturing shared_from_this

C++’s this is just a pointer, so capturing it in an Objective-C Block is not fundamentally different from capturing an integer. The interesting case is shared_from_this, which is the smart-pointer version of this.

A C++ class must inherit from std::enable_shared_from_this and pass its own class type as the template parameter in order to use shared_from_this.

Conclusion

OC Blocks can capture C++ objects.

  1. If you use normal capture for a stack C++ object, the copy constructor is called.
  2. If you use __block to capture a stack C++ object, the move constructor is called, and the __block-qualified C++ object gets redirected during capture.

Summary

The article started with a simple comparison between OC Blocks and C++ lambdas across four dimensions: syntax, implementation model, capture rules, and memory management. It then focused on the mixed capture problems between OC and C++ closures.

The reason for going into this much detail is that I do not want to rely on guesswork or trial and error. Only by understanding the underlying mechanism can we write better OC/C++ mixed code. I also hope this helps readers who have had the same confusion.

For the whole OC/C++ mixed world, this is only the tip of the iceberg. There are still many difficult problems ahead, and I hope to explore more of them in the future.
