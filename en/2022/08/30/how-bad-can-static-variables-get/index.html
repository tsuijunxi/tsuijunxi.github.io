How Bad Can Static Variables Get?

Posted on 2022-08-30 | In Static Variables
Words count in article: 43k | Reading time ≈ 2:37
中文 / English

Background

In C++, the construction and destruction order of static variables across translation units is undefined, and it can even change from build to build. That leads to a lot of hard-to-predict bugs. If you put C++ code into an iOS project, the call timing can introduce another layer of trouble, which makes things even worse. This article summarizes a few static-variable issues I have run into before.

Within the same translation unit, the order is clear: static initialization happens before dynamic initialization, initialization follows declaration order, and destruction happens in reverse order. Across translation units, the order of initialization and destruction is unspecified.

Note: the experiments in this article were done with C++14.

What static Means

Before going further, let us revisit the meaning of static in C-family languages, mainly in OC, C, and C++.

qualified object language storage visibility initialization time
static global variable OC/C Data file-local before main
static local variable OC/C Data visible inside the function or block first use
static function OC/C Text file-local -
static data member C++ Data visibility is expressed with public/protected/private before main
static member function C++ Text visibility is expressed with public/protected/private -
  1. static changes the linkage or storage class of an identifier, which affects visibility and storage region.
  2. Aside from visibility, a global variable and a static global variable are otherwise the same.
  3. For C++ class members, static has a different meaning and does not hide symbols.

Initialization Types

In general:

  • If the memory of a global variable is all zero, or if its initialization depends on runtime information, it goes into __DATA, __bss.
  • If the initialization value can be determined at compile time, it goes into __DATA, __data and does not need a runtime __cxx_global_var_init.

Trivial default constructor

The default constructor for class T is trivial if all of the following is true:

  • The constructor is not user-provided.
  • T has no virtual member functions.
  • T has no virtual base classes.
  • Every direct base of T has a trivial default constructor.
  • Every non-static member of class type has a trivial default constructor.

Trivial copy assignment operator

The copy assignment operator for class T is trivial if all of the following is true:

  • it is not user-provided;
  • T has no virtual member functions;
  • T has no virtual base classes;
  • the copy assignment operator selected for every direct base of T is trivial;
  • the copy assignment operator selected for every non-static class type member of T is trivial.

The Google way

NoDestructor looks ordinary, so why does it solve the destructor problem?

Before that, we need to understand Trivial Destructor:

https://en.cppreference.com/w/cpp/language/destructor#Trivial_destructor

Trivial destructor The destructor for class T is trivial if all of the following is true: The destructor is not user-provided The destructor is not virtual All direct base classes have trivial destructors All non-static data members of class type have trivial destructors

  1. By definition, NoDestructor does not provide a user-defined destructor (= default), it is not virtual, and it has no base class. Its only member, storage_, is not a class type, so the destructor of NoDestructor is trivial. Nothing needs to run, and the process memory will be reclaimed on exit anyway.
  1. The constructor, copy constructor, and move constructor of NoDestructor all use placement new to construct the object directly inside storage_. Placement new does not give you an easy way to call delete, which means the rwlock object created this way never gets a chance to run its destructor unless you call it manually, which obviously we do not do here.

Summary

This article summarized several static-variable pitfalls. They are subtle and difficult to debug, so it is worth understanding the mechanism behind them and avoiding dangerous patterns as much as possible:

  1. Avoid class-level global static variables whenever possible. Because construction and destruction order is uncertain, they can cause hard-to-find bugs. They can also affect startup time. If you must use them, prefer localizing the static variable. That is thread-safe and does not affect startup.
  2. Objects with static lifetime, including global variables, static variables, static class members, and function statics, should ideally be POD types such as int, char, float, pointers, arrays, and structs made of PODs. Otherwise, make sure the class is trivial.
  3. Avoid using function return values to initialize static variables.
  4. Avoid static destructors whenever possible, because destruction may involve multithreaded races and can crash.
  5. Avoid assigning to static variables inside +load, because values may later be overwritten.
  6. Avoid triggering static-variable access inside +load, because the static variable may not be initialized yet.
