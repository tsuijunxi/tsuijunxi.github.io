Understanding C++ Exceptions from the Source

Posted on 2026-03-07 | In C++ Exception
Words count in article: 96k | Reading time ≈ 5:49

Brief overview

What is the C++ exception mechanism?

This article starts from a few questions:

  • When throw is triggered inside a try block, how does the runtime find the matching catch, especially across deep call stacks?
  • Since throw changes control flow, will the objects created inside the try block still be destroyed correctly?
  • If the call chain mixes different languages, such as C -> C++ -> C -> C++, can exception handling still work when plain C does not support exceptions?
  • Have you ever run into a case that could not be caught?

The rest of the article explains these questions from the source code level.

Design idea

Exception handling exists in many high-level languages. It can stop the current function immediately and hand control to a function that can actually handle the error.

Bjarne Stroustrup explained the basic motivation in The C++ Programming Language: a library author can detect a runtime error, but usually does not know how to handle it because that depends on the application. The application author knows how to handle it, but does not know when it will occur. Exceptions solve exactly that problem by separating error detection from error handling.

So the core idea is not “the exception” itself, but the handling path. The runtime must also clean up the execution context along the way.

Which implementation mechanisms exist?

There have been several C++ exception implementations over time.

  • SJLJ is older and simple, but not very efficient.
  • EHABI is mainly used on ARM32 and is tightly coupled to that architecture.
  • DWARF CFI is the most widely used mechanism today. It offers a good balance of performance and capability, and is the focus of this article.
  • Compact Unwind is an Apple-specific optimization. It only supports simple stack unwinding; for complex cases, the system falls back to DWARF CFI.

Layered model

The Itanium C++ ABI splits exception handling into two layers:

Level 1, the foundational ABI, is the cross-platform unwind library. Its APIs are usually Unwind*, and common implementations include libgcc and libunwind.

  • It captures and restores execution context and supports stack unwinding.
  • It exposes call stack information during exception handling and debugging.

Level 2, the C++ ABI, provides the C++ standard library ABI support, especially for exceptions and RTTI. Its APIs usually start with __cxa_*, and common implementations include libsupc++ and libc++abi.

  • It implements key pieces such as __cxa_throw, __cxa_rethrow, and __gxx_personality_v0.
  • It also provides dynamic type information support, such as typeinfo and dynamic_cast.

The Itanium C++ ABI is usually discussed in four areas. This article focuses on the exception-handling part.

We can split the mechanism into three stages:

  1. Throw the exception.
  2. Unwind the stack.
  3. Catch and handle the exception.

Throwing an exception

__cxa_allocate_exception

When user code executes throw, control first reaches __cxa_allocate_exception. This function allocates a piece of memory that contains an exception header, used by the C++ ABI, followed by the actual user-thrown object.

This looks like a simple allocation, but the constraints are subtle. Allocating on the stack is a bad fit because the stack is precisely what will be unwound. Allocating on the heap can also fail because an exception may need to be thrown under memory pressure. Static allocation is not enough either because the operation must be thread-safe. Most implementations therefore allocate from thread-local storage, and use an emergency storage area when ordinary allocation fails.

__cxa_throw

After the memory is ready, execution enters __cxa_throw. It initializes the __cxa_exception structure, pushes the exception into the thread-local exception-management stack __cxa_eh_globals, and finally calls _Unwind_RaiseException.

The layout of __cxa_exception, _Unwind_Exception, and the actual thrown object matters because the runtime frequently converts between those pointers. For example, from an _Unwind_Exception *, libc++abi can recover the surrounding __cxa_exception *.

The thread-local __cxa_eh_globals stores the top exception and the number of uncaught exceptions:

Every new exception links its header to the current top exception through nextException, then updates caughtExceptions. Exception handling therefore behaves like a stack: the newest exception is handled first. __cxa_begin_catch decreases the uncaught count and pushes the current cxa_exception; __cxa_end_catch pops it back out.

Stack unwinding

_Unwind_RaiseException

_Unwind_RaiseException is the entry point into libunwind. It uses the classic two-phase unwinding model: unwind_phase1 and unwind_phase2.

unwind_phase1, the search phase, walks the stack looking for an exception handler. If no handler is found, libunwind returns _URC_END_OF_STACK; the caller decides how to terminate.

unwind_phase2, the cleanup phase, walks frames again, runs cleanups, destroys out-of-scope objects, and eventually transfers control to the handler frame. If phase 1 fails, phase 2 never runs, which means stack objects do not get destructed by the exception path.

unwind_phase1

The core loop in phase 1 repeatedly steps to the next frame, fetches frame metadata, and asks the frame’s personality routine whether this frame wants to stop the unwind.

The search itself also performs type matching through RTTI, so a call chain with many catch clauses can make phase 1 more expensive.

unwind_phase2

Phase 2 looks very similar, but its purpose is different. It walks the stack again and tells each personality routine that cleanup is now happening. When the stack pointer equals the value saved in exception_object->private_2, the current frame is the handler frame found during phase 1.

In short, phase 2:

  1. Calls __unw_step_stage2 to move to the previous frame.
  2. Reads the current stack pointer and frame metadata.
  3. Invokes the personality routine with _UA_CLEANUP_PHASE.
  4. If the personality routine returns _URC_INSTALL_CONTEXT, libunwind resumes execution at the generated landing pad.

Others

__unw_step

Both phases rely on __unw_step or __unw_step_stage2 to move one frame upward. A single step needs to solve two problems:

  1. Restore callee-saved registers.
  2. Correctly set pc, lr, fp, and sp.

On DWARF CFI, the actual logic eventually reaches stepWithDwarfFDE, and then DwarfInstructions::stepWithDwarf. That function decodes CIE and FDE, interprets DWARF instructions, calculates the CFA, restores registers from the previous frame, and sets IP to the return address.

The CFA, Canonical Frame Address, is the caller’s stack pointer value when entering the current function. In practice, libunwind calculates the CFA, reads saved registers from locations relative to it, sets the previous IP, and then replaces the in-memory register snapshot. These are not hardware registers yet; they are a saved register state that will later be loaded into real registers when resuming.

__unw_get_proc_info

__unw_get_proc_info fetches unw_proc_info_t for the current frame. This structure contains the function range, LSDA address, personality routine pointer, compact unwind format, and the DWARF unwind-info address.

Catching and handling exceptions

Personality routine

During both phases, libunwind obtains the personality routine with get_handler_function:

The personality routine is a callback. This is the key reason libunwind can remain language-independent: C++, Objective-C, SJLJ, Windows SEH, and other systems can provide different personalities.

Common examples:

  • __gxx_personality_v0: C++
  • __gxx_personality_sj0: SJLJ
  • __gcc_personality_v0: C with -fexceptions and cleanup attributes
  • __CxxFrameHandler3: Windows MSVC
  • __gxx_personality_seh0: MinGW-w64 SEH exceptions
  • __objc_personality_v0: Objective-C on macOS

For libc++abi, the personality routine is __gxx_personality_v0. It receives the exception context, the exception object, and the current frame’s exception table information.

During the search phase, it scans LSDA to find exception-handling information for the current frame. If no match is found, it returns _URC_CONTINUE_UNWIND; if a handler is found, it caches the result inside __cxa_exception for phase 2.

During the cleanup phase, there are two paths. If phase 1 already cached a handler result, the personality routine can reuse it directly. Otherwise, it scans LSDA again and updates the context from the new result.

When a landing pad is selected, set_registers sets the exception object into argument register 0, the type index into argument register 1, and the instruction pointer to the landing-pad address.

After __gxx_personality_v0 returns _URC_INSTALL_CONTEXT, unwind_phase2 calls __unw_phase2_resume. On ARM64 this eventually loads the prepared register snapshot and jumps to the landing pad.

Landing pad

Every time unwind_phase2 steps through a frame, it may jump into a landing pad. There are three common landing-pad patterns:

  • cleanup clause: calls destructors for out-of-scope variables, then calls _Unwind_Resume to return to unwind_phase2.
  • catch clause: calls destructors, enters __cxa_begin_catch, runs the catch handler, and then calls __cxa_end_catch.
  • rethrow: calls __cxa_end_catch, destroys objects inside the catch clause, then calls _Unwind_Resume to continue unwinding.

The rethrow case is easy to misunderstand. It means the previous exception has already been caught and is being thrown again while still inside the current frame. Before the new unwind proceeds, the runtime must clean up the current catch block correctly.

CFI, CIE, and FDE

CFI, Call Frame Information, is the DWARF data and instruction set that describes how to restore a stack frame to its caller. It records how the return address and caller registers are saved, allowing the unwinder to walk the stack.

CFI has two important structures: CIE and FDE.

  • CIE stores shared entry information, including personality routine and augmentation data. A CIE can be shared by multiple functions.
  • FDE stores unwind information for one function. The most important part is its CFI instruction sequence, which tells the unwinder how to recover register values at each address inside that function.

LSDA

Earlier we said that the personality routine scans eh_frame to obtain LSDA. LSDA, Language Specific Data Area, is the per-function language-specific exception table. It records:

  • Which instruction ranges may throw.
  • Which landing pad should handle a range.
  • Which typeinfo pointer should be used for matching.

The instruction range decides whether the current throw belongs to this frame. The typeinfo match decides whether the frame’s catch can handle this exception. If both match, control can transfer to the landing pad.

LSDA structure

LSDA parsing

The core parser is scan_eh_tab. Its job is to parse LSDA, iterate the Call Site Table, obtain the Action Table index, read ttypeIndex from the Action Table, and then use ttypeIndex to find a typeinfo entry in the Type Table. Finally it checks whether the thrown type matches the catch type.

The parsing flow is:

  1. Get the LSDA pointer with _Unwind_GetLanguageSpecificData(context).
  2. Parse the LSDA header: lpStartEncoding, ttypeEncoding, callSiteEncoding, and classInfoOffset.
  3. Parse the Call Site Table. Each entry records start, length, landingPad, and actionEntry.
  4. Parse the linked list of action entries. Each entry contains ttypeIndex and the offset to the next action.
  5. Use the Type Table to get typeinfo, then call catchType->can_catch(excpType, adjustedPtr).

RTTI

RTTI is the last critical piece. Exception matching depends on runtime type comparison.

Defects of type_info

std::type_info is the standard RTTI interface. It can represent the dynamic type of an object and expose basic information such as the type name, but by itself it does not describe type relationships. It cannot answer questions such as:

  1. Whether two classes form an inheritance relationship.
  2. Whether that inheritance is public or virtual.
  3. How to adjust a base-class subobject pointer so it points to the derived object.

So each ABI extends RTTI beyond the standard surface.

std::type_info::operator== is backed by ABI-specific implementations:

  1. __unique_impl::__eq: under the Itanium ABI, a given RTTI object is usually unique, so pointer equality is enough.
  2. __non_unique_impl::__eq: when the linker fails to merge RTTI copies, either pointer equality or string equality can make two types equal.
  3. __non_unique_arm_rtti_bit_impl::__eq: Apple ARM64 uses a high bit in the type-name pointer to mark whether the RTTI is non-unique.

The Apple ARM64 design avoids weak-symbol problems. Hidden typeinfo can still be deduplicated within a linked image, while separate images can keep separate RTTI copies without being unexpectedly redirected.

bullet2: __dynamic_cast_info

If the types are not directly equal, the runtime must check inheritance. It uses dynamic_cast-style metadata and __dynamic_cast_info to verify whether thrown_type publicly and unambiguously derives from the catch type.

Summary

This article followed the C++ exception path from the source-code level: throwing, two-phase unwinding, frame stepping, personality routines, LSDA parsing, landing-pad selection, and RTTI-based type matching. The key takeaway is that throw is not a direct jump to catch. It is a cooperation between compiler-generated metadata and runtime stack-unwinding logic.

QA

A tricky C++ exception debugging case

From real-world debugging posts, type_info mismatch is one of the most common causes of failed catches. The root cause is often duplicated RTTI.

Case 1: Shocking! The try-catch statement stopped working?

The rough story is this: an Objective-C component used exceptions but disabled RTTI. To keep exception type information available, the compiler generated another copy of type_info. Because the component was a static library, that type_info ended up in the main binary. As a result, the main binary and libc++ both had same-named type_info, and can_catch failed to match.

In iOS projects, CocoaPods usually builds components as separate targets. If any target disables RTTI, it may affect exception handling in the host app. If RTTI is disabled, exception handling should usually be disabled too, namely -fno-rtti together with -fno-exceptions.

Case 2: A satisfying debugging story about C++ standard-library exceptions

On Android, ANDROID_STL defaults to c++_static in CMake. The C++ standard library is linked statically into the business .so, so related type_info symbols are local, and can_catch may fail. Switching to c++_shared, or exporting typeinfo and vtable symbols so that they depend on libc++.so or libstdc++.so, can solve the issue.

Is two-phase unwinding necessary?

Not strictly. The Itanium C++ ABI Exception Handling document explains that the two-phase model is not required for C++ semantics, but it provides benefits. In particular, phase 1 allows an exception system to dismiss or handle an exception before the stack has actually been unwound. C++ does not support resumptive exception handling, but other languages do, and the two-phase design lets C++ coexist with those languages on the same stack.

So destructors should not let exceptions escape. If cleanup may fail, catch the exception inside the destructor and either swallow it deliberately or terminate explicitly.

Does Objective-C exception handling work the same way?

Objective-C exception handling is very close to the C++ mechanism. Many Objective-C exception APIs wrap the same C++ exception machinery.

What about Swift exceptions?

Swift’s error model is based on try, catch, throws, and throw. A throws function declares that it may return an error, and throw produces that error at runtime.

The important difference is that Swift errors are values, not stack-unwinding control-flow interruptions. Conceptually it is closer to Result<T, E> or Objective-C’s NSError pattern than to C++ exceptions. In pure Swift projects, relying on Objective-C exceptions should be avoided; in mixed projects, it should be handled with extra care.

Is Java exception handling similar?

At the language level, both Java and C++ have try-catch, exception propagation, and stack unwinding. But their implementation models are different. C++ heavily depends on ABI-level metadata, LSDA, RTTI, and compiler-generated landing pads. Java exceptions are managed by the VM, where the runtime owns the stack metadata and exception tables.

How should we treat C++ exceptions?

Different ecosystems have made different tradeoffs.

Google’s C++ style guide says not to use exceptions, but it also says the reason is largely historical: too much existing Google C++ code was not prepared for exception safety.

Qt also avoids exceptions. Its documentation mentions historical and practical reasons, including binary-size cost. Turning on exceptions can increase library size significantly.

Modern languages have also been rethinking error handling. Go and Rust both return to the idea of “errors as values”; Rust’s Result<T, E> makes error flow explicit and composable.

My personal view is that C++ exceptions are neither magic nor evil. They are a powerful ABI feature with real cost and real failure modes. In codebases that choose to use them, exception safety and RTTI consistency must be treated as part of the engineering contract.
