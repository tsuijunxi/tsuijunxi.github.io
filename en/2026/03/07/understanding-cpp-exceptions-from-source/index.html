Understanding C++ Exceptions from the Source

Brief overview

What is the C++ exception mechanism?

This article starts from a few questions:

  • When throw is triggered inside a try block, how does the runtime find the matching catch, especially across deep call stacks?
  • Since throw changes control flow, will the objects created inside the try block still be destroyed correctly?
  • If the call chain mixes different languages, such as C -> C++ -> C -> C++, can exception handling still work when plain C does not support exceptions?
  • Have you ever run into a case that could not be caught?

The rest of the article explains these questions from the source code level.

Design idea

Exception handling exists in many high-level languages. It can stop the current function immediately and hand control to a function that can actually handle the error.

Bjarne Stroustrup explained the basic motivation in The C++ Programming Language: a library author can detect a runtime error, but usually does not know how to handle it because that depends on the application. The application author knows how to handle it, but does not know when it will occur. Exceptions solve exactly that problem by separating error detection from error handling.

So the core idea is not “the exception” itself, but the handling path. The runtime must also clean up the execution context along the way.

Which implementation mechanisms exist?

There have been several C++ exception implementations over time. The most common ones are SJLJ, EHABI, DWARF CFI, and Apple’s Compact Unwind optimization.

  • SJLJ is older and simple, but not very efficient.
  • EHABI is mainly used on ARM32 and is tightly coupled to that architecture.
  • DWARF CFI is the most widely used mechanism today. It offers a good balance of performance and capability, and is the focus of this article.
  • Compact Unwind is an Apple-specific optimization. It only supports simple stack unwinding; for complex cases, the system falls back to DWARF CFI.

Layered model

The Itanium C++ ABI splits exception handling into two layers:

Level 1, the foundational ABI, is the cross-platform unwind library. Its APIs are usually Unwind*, and common implementations include libgcc and libunwind.

  • It captures and restores execution context and supports stack unwinding.
  • It exposes call stack information during exception handling and debugging.

Level 2, the C++ ABI, provides the C++ standard library ABI support, especially for exceptions and RTTI. Its APIs usually start with __cxa_*, and common implementations include libsupc++ and libc++abi.

  • It implements key pieces such as __cxa_throw, __cxa_rethrow, and __gxx_personality_v0.
  • It also provides dynamic type information support, such as typeinfo and dynamic_cast.

The Itanium C++ ABI is usually discussed in four areas. This article focuses on the exception-handling part.

Exception overview

The figure summarizes the full flow: __cxa_throw, _Unwind_RaiseException, unwind_phase1, unwind_phase2, landingpad, and the supporting metadata such as eh_frame, unw_proc_info_t, CIE, FDE, exception table, and call site table.

We can split the mechanism into three stages:

  1. Throw the exception.
  2. Unwind the stack.
  3. Catch and handle the exception.

Throwing an exception

__cxa_allocate_exception

The runtime first allocates storage for the exception object.

__cxa_throw

__cxa_throw stores the type information, attaches the exception object, and hands control to the unwind runtime.

Stack unwinding

_Unwind_RaiseException

This is the entry point into the unwind library. It begins walking the call stack to find a handler.

unwind_phase1

Phase 1 only searches for a matching handler. It does not run cleanup yet.

unwind_phase2

Once a handler is found, phase 2 actually unwinds frames, runs cleanups, and transfers control to the landing pad.

Others

__unw_step

This is the step used to move from one frame to the previous one.

__unw_get_proc_info

This fetches metadata for the current frame.

Catching and handling exceptions

Personality routine

The personality routine is the core decision-maker during unwinding. It inspects the metadata for each frame and decides whether the current frame can catch the exception or needs cleanup only.

Landing pad

The landing pad is the destination code generated by the compiler for exception handling. When the runtime decides that a frame should catch or clean up, control is transferred there.

CFI, CIE, and FDE

These are the unwind metadata structures stored in the binary. They describe how to restore registers and move across frames.

LSDA

LSDA means Language Specific Data Area. It stores language-specific exception metadata.

LSDA structure

LSDA parsing

The runtime uses LSDA to match a thrown type against the handlers declared in the source code.

RTTI

RTTI is needed so the runtime can compare the thrown type with the catch clauses.

Summary

The C++ exception mechanism is a combination of compiler-generated metadata and runtime stack-unwinding logic. throw does not simply jump to catch; it first goes through object allocation, unwind phase 1 to search for handlers, phase 2 to run cleanup, and finally lands in the compiler-generated handling code.
