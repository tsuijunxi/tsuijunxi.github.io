C++ 异常机制的设计理念

异常处理是许多高级语言都具有的特性，它可以直接中断当前函数并将控制权转交给能够处理异常的函数。C++ 之父 Bjarne Stroustrup 在《The C++ Programming Language》中讲到：一个库的作者可以检测出发生了运行时错误，但一般不知道怎样去处理它们（因为和用户具体的应用有关）；另一方面，库的用户知道怎样处理这些错误，但却无法检查它们何时发生。提供异常的基本目的就是为了处理上面的问题，其基本思想是：让一个函数在发现了自己无法处理的错误时抛出（throw）一个异常，然后它的（直接或者间接）调用者能够处理这个问题，核心就是将问题检测和问题处理相分离。所以，异常处理的核心不在异常，而在处理。不管抛出的是什么异常，它只是一个信息承载的方式，异常处理最关键的是如何把这个异常传递给能够处理它的人。还有最重要的一点，在这个过程中把现场“清理干净”。

有哪些 C++ 异常实现机制？

到目前为止，有多种 C++ 异常实现机制。

  • SJLJ 主要用于较老的系统或者嵌入式系统，其优点是实现简单，但效率较低；
  • EHABI 则主要用于 ARM32 架构，其特点是与 ARM32 架构紧密结合，性能较好。
  • DWARF CFI 则是目前应用最广泛的机制，其效率和功能都比较均衡（本文重点）
  • 除此之外，Compact Unwind（表格比较老，无该项）是苹果平台的专属优化，只能做简单的栈展开，不能处理异常匹配、清理代码等复杂场景，遇到复杂情况时，系统会自动回退到功能完整的 DWARF CFI

C++ 异常机制分层

Itanium C++ ABI：异常处理分为一级基础 ABI 和二级 C++ ABI。

一级基础 ABI 用于堆栈展开、异常处理和回调的库，提供了一种跨平台的 API 来处理堆栈展开，其 API 形式为 Unwind*。常见实现有 libgcc 和 libunwind。

  • 允许捕获和恢复程序执行上下文，并支持函数调用栈的展开。
  • 在异常处理和调试过程中，能够访问调用栈信息。

二级 C++ ABI 主要负责为 C++ 标准库提供应用二进制接口（ABI）支持，特别是在异常处理和运行时类型识别 (RTTI) 方面。其 API 形式是 __cxa_*，常见的实现方式有：libsupc++ 和 libc++abi。

  • 实现了 C++ 异常处理中的关键功能，如 __cxa_throw、__cxa_rethrow、__gxx_personality_v0 等。
  • 提供动态类型信息的支持，例如 typeinfo 和 dynamic_cast。

关于 C++ Itanium ABI，主要分为四大板块（本文讨论的就是板块三） 内存布局（Data Layout） 调用约定（Calling Convention） 异常处理机制（Exception Handling） 定义输入到链接器的对象文件的格式（Linkage & Object Files）

抛出异常

__cxa_allocate_exception

当用户代码使用 throw 抛出一个异常时，代码首先流转到 __cxa_allocate_exception。该方法负责申请一块内存，该空间会包含一个 exception header，用来存储一些 C++ ABI 需要的信息，偏移后的空间用来存储用户数据。

这里看起来是一个简单的内存分配，但其中的机制远比想象的复杂：当一个异常被抛出时，会对栈进行一些操作，所以在栈上进行分配可能不是个好主意。同时，在堆上分配内存可能也不是个好主意，因为可能需要在内存耗尽的情况下抛出异常。静态分配也不是一个好主意，因为我们需要这个操作是线程安全的（否则，如果两个线程同时抛出异常，那就麻烦了）。考虑到这些限制，大多数实现似乎都是在本地线程存储（堆）上分配内存，但如果内存耗尽，就会使用紧急存储（可能是静态的）

__cxa_throw

当完成异常内存申请后，代码流转到 __cxa_throw，它首先完成 __cxa_exception 结构体的初始化，然后将异常压入异常管理栈 __cxa_eh_globals 中，最后调用 _Unwind_RaiseException。

这里需要注意下 __cxa_exception、_Unwind_Exception 和 exception_obj 的内存分布，后文中将会看到一些指针转换的操作，例如：__cxa_exception* exception_header = (__cxa_exception*)(unwind_exception + 1) - 1，将一个 unwind_exception 类型的指针转换为一个 __cxa_exception 类型的指针。

此外这里还有个异常管理栈 __cxa_eh_globals。

__cxa_eh_globals 里面保存了栈顶的 exception，以及未处理的 exception 数量。每次有新的 exception 时，当前 exception 的 header 中的 nextException 会指向当前的 caughtException，然后更新 __cxa_eh_globals 里面的 exception header 为这个新的 exception header。

异常处理过程优先处理最新的 exception，处理完后会处理之前一个旧的 exception，按照处理顺序来说也就是下一个。简单总结下，begin_catch 的时候减少计数并且把 cxa_exception 放到栈上，而在 end_catch 的时候将对象从 globals 中取出，而在 catch 以及 throw 的过程中通过增减 uncaughtExceptions 来管理当前未处理异常对象的数量。

栈回溯

_Unwind_RaiseException

如代码所示，_Unwind_RaiseException 采用了经典的两段式回溯：unwind_phase1 与 unwind_phase2。

**unwind_phase1（Search）**会遍历整个栈以查找 Exception Handler。如果没有找到 Exception Handler，则应当终止程序。不过 libunwind 本身不会直接调用 std::terminate()，而是返回 _URC_END_OF_STACK 并由调用者决定如何终止程序。

**unwind_phase2（Clean）**会逐帧回溯并清理栈，直到最后的 Exception Handler。从代码中也可以看到，如果unwind_phase1 阶段没有找到 Exception Handler，那么根本就不会进入到第二阶段，也就是不会进行栈回溯，栈上对象的析构函数不会被执行。

unwind_phase1

在 unwind_phase1 中，代码会不断循环查找 Exception Handler，直到找到 Exception Handler 或者到达栈底：

  1. 使用 __unw_step 函数，使 cursor 指向下一个栈帧；
  2. 使用 __unw_get_proc_info 函数，检查当前栈帧是否有需要执行的代码；
    • 如果找到了要执行的代码，则检查是否要停在当前栈帧（可能找到了 Exception Handler）；
    • 如果找到了 Exception Handler，标记当前栈帧并返回；
    • 否则继续循环。
  3. 如果没有找到要执行的代码，则继续循环。

在检查 catch 块是否与当前异常对象所匹配时，会对比 RTTI 信息等，所以如果回滚过程中找到了很多 catch，会对 unwind_phase1 的性能有较大的影响。

unwind_phase2

unwind_phase2 与 unwind_phase1 的代码非常类似，也是在循环中回溯栈，只不过它所做的事情要多一点：

  1. 使用 __unw_step_stage2 函数，使 cursor 指向下一个栈帧；

  2. 使用 __unw_get_reg 获取当前栈帧的 sp 寄存器；

  3. 使用 __unw_get_proc_info 函数，获取当前栈帧的信息；

  4. 如果当前栈帧有要执行的代码，则告诉它目前正在进行 _UA_CLEANUP_PHASE | _UA_HANDLER_FRAME。

    • 如果这段代码执行后应当继续回溯，则继续循环；

    • 如果这段代码执行后回溯到此为止，则尝试 resume 控制权

Others

__unw_step 退栈

unwind_phase1 和 unwind_phase2 都调用到了 __unw_step 或者 __unw_step_stage2 进行 1 次或者多次栈回退。栈回退操作，就需要改变当前的 PC 指针。__unw_step 函数会改变备份在 cursor 中的寄存器信息，完成一层退栈操作。发生退栈操作时，需要解决两个问题：

  1. 恢复 callee saved register

  2. 正确设置四个重要寄存器 pc、lr、fp、sp

__unw_step 这个函数的实际逻辑最后定位到了 libunwind 的 stepWithDwarfFDE。

  • 首先会从栈帧上拿到保存的 ip（instruction pointer，即函数的返回地址）；

  • 然后调用 DwarfInstructions::stepWithDwarf。

来到了 DwarfInstructions::stepWithDwarf 方法，该方法会解码 CIE 和 FDE 信息，并依赖这些信息还原 x19 - x28，d8 - d15 这些 callee saved register（关于 CIE 和 FDE 这个后文会有描述）。

CFI_Parser<A>::decodeFDE 负责解码 FDE（Frame Description Entry），CFI_Parser<A>::parseFDEInstructions 负责解释执行 FDE 中的 DWARF 字节码，得到指定 PC 位置对应栈上保存的值的位置偏移量表。

  • 拿到栈底基准地址 CFA
  • 根据位置偏移量表获取到栈上保存的寄存器的所有值，恢复到拷贝的寄存器状态中
  • 设置 IP 为 returnAddress（跳到上一层函数）
  • 切换寄存器状态 register 为 newRegisters

其中 CFA (Canonical Frame Address) 指的是上一级调用函数的栈指针（SP）在进入当前函数时的值。简单说，它是当前函数的调用者的栈顶位置

需要留意的是：这里的寄存器并不是真正意义上的寄存器，而是一块内存，等真正需要的时候将这块内存里面的值加载到真正的寄存器中进行跳转

__unw_get_proc_info 获取栈帧信息

unwind_phase1 和 unwind_phase2 都调用到 __unw_get_proc_info 函数，获取当前栈帧的信息 unw_proc_info_t。unw_proc_info_t 结构体包含函数的起始与结束地址、LSDA、personality routine 函数指针（用于寻找异常对应的 landing pad），还有包含了如何恢复 callee saved register 的信息。

Landing Pad

unwind_phase2 每次退栈过程中，都可能会涉及到一次 landingpad 的跳转，landingpad 有 3 种类型：

  • cleanup clause：调用 destructors of out-of-scope variables，然后调用 _Unwind_Resume 跳转到 unwind_phase2；
  • catch clause：调用 destructors of out-of-scope variables，跳转到 __cxa_begin_catch 调用，然后是 catch handler 块，最后是 __cxa_end_catch 调用；
  • rethrow：调用 __cxa_end_catch，执行 destructors of out-of-scope variables in the catch clause，然后调用 _Unwind_Resume 跳转到 unwind_phase2。

注意：这里关于 rethrow 有一些疑惑性：它代表着上次的异常已经被捕获处理，并且在处理的过程中再次抛出。从 API 的调用链来看，它会在当前帧栈再次调用 _Unwind_RaiseException 进行栈展开处理，那么当前帧栈尚且没有处理完毕，所以必须确保在开始新的展开之前，做好当前 catch 块的清理：先调用 __cxa_end_catch，再调用 destructors。

CFI & CIE & FDE

CFI（Call Frame Information）是 DWARF 标准中定义的一组数据结构和指令，用于描述程序执行过程中如何从一个函数的栈帧（stack frame）恢复到其调用者的栈帧。CFI 通过描述调用栈帧的布局，特别是返回地址和调用者寄存器值是如何保存的，来实现栈的“展开”（unwinding）。

CFI 内部有 2 个重要的结构体：CIE 和 FDE。

  • CIE 中记录的是一些公用的入口信息，包括异常的 handler、数据增强信息等。每个函数都会对应一个 CIE，一个 CIE 可以供多个函数共用，如果两个函数拥有相同的初始化指令序列，那么它们通常指向同一个 CIE。

  • FDE 中记录了此函数栈回溯相关的信息，最主要的是记录了一系列指令序列（CFI, Call Frame Information），此指令序列可用来确定此函数执行到其每个地址时其各个寄存器的值应该如何获取/计算，每个函数都有且仅有一个 FDE 结构体。

LSDA （Language Specific Data Area）

在 Personality Routine 环节提到：“为了寻找对应帧栈的异常处理信息，需要先扫描 eh_frame 来获取 LSDA”。那么什么是 LSDA 呢？LSDA 是每个函数的“语言特定扩展表”，其中包含：

  • 哪些指令范围可能抛出异常；
  • 对应的 landing pad 地址；
  • 匹配类型信息（typeinfo 指针）。

指令范围可以用来判断该异常是否在该帧栈的管理范畴内，typeinfo 匹配决定该异常是否在自己的 catch 范围内，如果前两者都满足的话，可以跳转到对应的 landing pad 地址。

LSDA 解析

整个流程中少不了的是 scan_eh_tab 这个过程，而这个函数主要的用途就是去解析 LSDA 的结构信息。解析的核心逻辑，就是遍历 Call Site Table，获取到 Action Table Index，然后在 Action Table 中获取到 ttypeIndex，然后根据 ttypeIndex 在 type_info Table 中开始搜索和匹配异常对象和 catch 对象是否匹配。如果匹配则返回，如果不匹配，循环遍历 Action Table 中的 action 链表，直到处理完。

  1. 获取 LSDA 指针：
    • lsda = _Unwind_GetLanguageSpecificData(context);
  2. 解析 LSDA 头部：
    • lpStartEncoding：landing pad 起始编码方式；
    • ttypeEncoding：类型信息编码方式；
    • callSiteEncoding：调用点表编码方式；
    • classInfoOffset：类信息表偏移量。
  3. 解析 callSiteTable：每个 try 块对应一个表项，包含：
    • start：try 块起始地址；
    • length：try 块长度；
    • landingPad：landing pad 地址；
    • actionEntry：action 表项偏移量。
  4. 解析 actionEntry 链表：每个 actionEntry 包含：
    • ttypeIndex：类型索引（SLEB128 格式）；
    • actionOffset：下一 action 项偏移量，链表结构。
  5. 类型匹配检查：
    • 对每个 ttypeIndex，通过 typetable 表找到对应的 typeinfo；
    • 检查 catchType->can_catch(excpType, adjustedPtr)。

RTTI

type_info 的缺陷

前文中 can_catch 需要对类型进行动态比对。为了实现运行时类型检查，C++ 标准提供了一套名为 RTTI 的接口，这套接口的核心是 std::type_info 类，它用于在运行时表示某个类型的相关信息。但这套接口提供的功能过于简单，它只支持查询一个多态对象的动态类型以及类型的基本属性（例如类型的名称等），并不支持动态查询不同的类型之间的关系（例如查询两个 std::type_info 所表示的类型是否构成继承关系等）

因此，各个 ABI 都需要对 RTTI 定义的功能进一步扩充以满足以下三点：

  1. 需要能够动态查询两个类型是否构成继承关系；
  2. 在两个类型构成继承关系的基础上，需要能够进一步查询这两个类型构成何种继承关系：是否为公开继承、是否为虚继承等；
  3. 在两个类型构成继承关系的基础上，需要能够进一步查询如何对基类子对象指针施加一定的偏移才能使其指向子类对象指针。

其中 __impl 有 3 种类型：

  1. __unique_impl::__eq

在遵循 Itanium ABI 的编译器中，对于给定类型的 RTTI，只有一个唯一的副本存在，因此可以通过比较类型名称的地址来判断 type_info 是否相等，无需使用字符串，可以提高性能并简化代码

  1. __non_unique_impl::__eq

由于各种原因，链接器可能没有合并所有类型的 RTTI（llvm.org/PR37398）。在这种情况下，如果两个 type_info 的地址相等或者它们的名称字符串相等，这两个 type_info 被认为是相等的。

  1. __non_unique_arm_rtti_bit_impl::__eq

这种方式是 Apple ARM64 的特定实现，给定类型的 RTTI 可能存在多个副本。在构造 type_info 时，编译器将类型名称的指针存储在 uintptr_t 类型中，指针的最高位表示 non_unique，默认为 0（false）。如果最高位被设置为 1，表示 type_info 在程序中不是唯一的。如果最高位没有被设置，表示 type_info 是唯一的。这个设计的目的是为了避免使用 weak 符号。它将原本会被作为弱符号生成的默认可见性的 type_info，转而使用隐藏可见性的 type_info，并把 non_unique bit 位设置为 1，表示非唯一。这样做的好处是，在链接镜像内，hidden 可见性的 type_info 仍然可以认为是唯一的，可以继续通过 linker 进行去重，而在不同的镜像间，会被视为不同的类型，避免了 weak 符号被重定向，导致 RTTI 类型信息混乱。

bullet2: __dynamic_cast_info

涉及到继承关系，需要使用 dynamic_cast 和 __dynamic_cast_info 构建动态转换信息，检查 thrown_type 是否以公共方式继承自 this（catchType）。

这部分逻辑和 C++ 继承方式密切相关，例如单继承、多继承、虚继承，逻辑比较复杂。

案例一： 震惊！try catch 语句竟然失效了？

总结一下：由于某个 OC 组件该组件内使用了异常，但是禁用了 RTTI，为了能继续获取异常类型的 type_info 信息，编译器会重新生成一份。由于 OC 组件是静态库，最后该 type_info 信息会一起进入主二进制，这样就导致了主二进制和 libc++ 动态库同时拥有同名的 type_info 信息，进而导致 can_catch 匹配失败。

iOS 工程通常使用 CocoaPods 集成不同的组件，这些组件在编译时会作为一个独立的 target，任意一个 target 的编译选项禁用 RTTI 后都会影响到宿主 App 的异常处理流程，继而可能引发 try catch 失效，所以禁用 RTTI 的同时需要禁用 exception handling，即 -fno-rtti 和 -fno-exceptions 一起使用，这样单独的 target 不会影响到宿主 App 的 exception handling。

案例二： 一次酣畅淋漓的问题排查（C++ 标准库异常实现原理）

总结一下：ANDROID_STL 在 CMake 中默认是 c++_static 的，此时 C++ 标准库以静态库的方式链接到业务的 so 文件，因此 so 文件中相关的 type_info 是 local 的，进而导致 can_catch 匹配失败。此时将 c++_static 修改为 c++_shared 可以解决问题，或者手动把 typeinfo/vtable 的符号都导出为依赖 libc++.so 或者 libstdc++.so 也可以解决。

两段式回溯是必需的吗？

并非必需，《Itanium C++ ABI: Exception Handling》文档提到：

A two-phase exception-handling model is not strictly necessary to implement C++ language semantics, but it does provide some benefits. For example, the first phase allows an exception-handling mechanism to dismiss an exception before stack unwinding begins, which allows resumptive exception handling (correcting the exceptional condition and resuming execution at the point where it was raised). While C++ does not support resumptive exception handling, other languages do, and the two-phase model allows C++ to coexist with those languages on the stack.

翻译过来：两个阶段的异常处理模型对于 C++ 并不是严格必需的，但是它可以带来一些好处。比如，第一阶段允许异常处理机制在栈帧展开之前消除异常，这样可以进行恢复式异常处理(对异常情况进行修复，然后在抛出异常的地方继续执行)，虽然 C++ 不支持恢复式的异常处理，但其它语言支持，两阶段模型允许 C++ 与那些语言在堆栈上共存。

为什么 C++ 的析构函数禁止抛出异常？

可能会导致双重异常：

抛出第一个异常 –> 开始栈展开 –> 析构 obj –> obj 析构抛出第二个异常 –> 现在有两个活跃异常 → 无法处理。

所以析构函数禁止抛出异常。如果析构函数发生异常，不要让异常逃离析构函数，析构函数应该捕捉任何异常，不传播或结束程序。

Swift 的异常机制又是怎样的呢？

Swift 的错误处理模型是基于 try、catch 以及 throws 和 throw 关键字的。throws 声明一个函数可以抛出错误，而 throw 则是在实际运行时抛出错误。throws 关键字本质上是通过引入异常控制流来实现的。当一个 throws 函数被调用时，Swift 在内部生成一段额外的代码，用于检测函数是否抛出了错误。如果没有错误发生，函数会像普通函数一样返回结果；如果发生了错误，则会跳转到调用方的 catch 块进行处理。

这意味着 throws 和普通函数的调用在编译器层面有着不同的处理方式。在编译生成的中间代码中，throws 函数的返回值不是直接返回，而是封装在一个类似于 Result 类型的结构中，附带一个可能的错误对象。只有在 do-catch 块中，错误对象才会被解封和处理。

Swift 的错误是值，不是控制流中断，并不涉及栈回溯的行为，这与 C++ 的异常有本质区别，它和 OC 的 NSError 机制更像。在纯 Swift 项目中应该避免依赖 OC 异常，在混合项目中应该小心处理。

对待 C++ 异常的态度？

  • Google 编码规范说不使用异常，但它也说了主要是历史原因，老代码太多。

Because most existing C++ code at Google is not prepared to deal with exceptions, it is comparatively difficult to adopt new code that generates exceptions. Things would probably be different if we had to do it all over again from scratch. Google C++ Style Guide

  • Qt 也不使用异常，原因主要是历史原因和二进制尺寸。

Qt itself will not throw exceptions. Instead, error codes are used. In addition, some classes have user visible error messages, for example QIODevice::errorString() or QSqlQuery::lastError(). This has historical and practical reasons . Turning on exceptions can increase library size by over 20%. Exception Safety | Qt 6.6

  • 现代语言的反思：回归“错误即值”

近年来如 Go 和 Rust 等语言开始回归“返回值”模式（如 Rust 的 Result<T, E>）， 将错误视作数据（值），鼓励通过组合子（如 map, and_then）处理错误，使程序结构更加预测和类型安全
